## Outcome and scope

A member imports one recipe PDF through the familiar file action or Android share sheet, adds rating/notes, and saves it. The server retains the unchanged PDF, renders ordered page images using PDFtoImage and feeds the normal photo-import workflow. Photo acquisition remains primary.
This document is the current acceptance checklist; design.md owns approach and open seams, tasks.md owns planned work. review.md contains current review status and clearly separated historical evidence. Superseded review recommendations are not requirements.

New PDF submissions are gated on established member identity and API effective enablement before conversion or import persistence. Exact flag key/env spelling is the design proposal until contract/config synchronization. |

Extend the existing recipe-file picker for PDFs only when enabled, keeping .txt bundles separately dispatched by validated format. | PDF-R03 | Installed Android Chromium PWA is a required PDF share target from any source app exposing a compatible PDF file share, without source-app restrictions. Share opens PDF confirmation directly, never auto-saves. Preserve existing text/link POST and legacy GET shares. iPhone/iPad uses the file picker; no native iOS extension or equivalent PWA PDF share guarantee. Actual Android OS cold/warm registration and representative originating apps must be qualified. |
| PDF-R04 | Confirmation shows the selected PDF filename, one-recipe guidance, rating and notes controls with existing photo semantics, and Save recipe. Rating defaults to unknown (0), supports the same choices/validation (currently 0–3), and supplied rating/notes survive server creation/workflow. Blank notes follow existing trimming/omission behavior. No photo selection alongside the PDF, no cooked-dish image designation, no PDF Cancel action, no additional required title/instructions. Images are generated server-side; finishedDishImageIndex=-1. |
| PDF-R05 | Exactly one recipe per PDF is supported, including text/scanned PDFs and a single recipe spanning pages. Multi-recipe PDFs are unsupported, with no automatic detection, splitting or page selection/editor added. Input limits are 20 MB and 10 pages; exceeding either rejects the whole document from extraction/readiness, never truncates pages. A stored pending import may exist before page count/content validation. Encrypted/corrupt documents fail the conversion processor and remain failed jobs until the user retries or deletes them in Settings. No automatic deletion or password-entry flow. Exact byte threshold remains OQ-02. |
| PDF-R06 | Browser/share worker never renders PDF pages or calls Gemini. Dedicated authenticated POST /api/recipes/capture-pdf takes one PDF plus rating/notes; existing photo route remains image-only. A separate PDF conversion processor at the start of existing recipe-import uses PDFtoImage server-side to render ordered readable images, then normal extraction continues. Photo jobs skip that processor's PDF work. No separate PDF workflow, direct Gemini PDF input, new sourceType or PDF-specific recipe columns. Approved architecture decision: API stores unchanged PDF/rating/notes with a pending recipe and launches existing recipe-import before conversion. Workflow manages conversion retries/failure; no separate PDF workflow. |
| PDF-R07 | Retain accepted original PDF bytes unchanged as an internal artifact, separate from image enumeration. View original displays readable ordered page images through the existing viewer; no PDF viewer/download/export. Reimport and bundle export must not decode the PDF as an image. Soft delete/restore and backup/recovery preserve it; permanent purge removes it and the pages. Temporary cleanup must not delete accepted artifacts or retained failed-job retry sources. |
| PDF-R08 | After Save, show Preparing your PDF… during upload/persistence using existing photo-import progress conventions; do not wait for workflow conversion. After accepted recipe ID, register existing session pending state and return Home while normal extraction continues. No new PDF countdown/screen. Accepted ID proves persistence, not readiness or verified workflow launch. Save tap/incomplete upload alone is not receipt. No new durable queue/recovery infrastructure. |
| PDF-R09 | Interruption, leaving capture, unlock or member change resets local selection/rating/notes and requires restart/reselection/share. Android staging bridges only delivery to foreground capture; no preservation through unlock/member change, abandoned-token recovery or 24-hour draft resume window. No client/server cancellation action; received server work is not cancelled by navigation. Initial locked share may require unlocking then sharing again. Existing ordinary photo flow is not otherwise redesigned. |
| PDF-R10 | Submitted rejected/failed PDF imports appear in existing Settings import-job recovery with Retry/Delete like link/photo failures. The conversion processor uses existing workflow retry behavior; after failure, the job uses existing Settings Retry/Delete. Corrupt/encrypted jobs stay failed for the user to delete, with no automatic cleanup of their retained retry source. Retain enough source and metadata for supported retry; user Delete cleans the job's artifacts through existing semantics. Retrying cannot guarantee an invalid source becomes valid. Conversion/content failures now occur inside recipe-import after pending source persistence; verify existing failed-task listing and cleanup during implementation. Abandoned/never-received selections are not failed jobs. |
| PDF-R11 | Session-only feedback may be missed, uncertain retry may duplicate recipes, and another member may see household completion feedback on a shared device. Keep local active-request Save lock and existing duplicate flag/delete controls. No durable client pending state, reconciliation, server idempotency, cross-tab deduplication, draft persistence, discard dialog or member-specific notification filtering. Accepted recipes remain attributed to the authenticated submitting member. Completed recipes are browseable under existing rules without a notification. |

Import alone casts no votes, assigns no meals, changes no groceries and adds/promotes no GOTO entry. Pending/failed recipes follow existing readiness rules. |

## Non-goals and preserved boundaries

No cookbook splitting/detection, page editor, passwords, PDF export/viewer, native wrappers, capture redesign, new flag framework, extraction prompt/model change, dedicated PDF workflow, durable submission queue or unrelated cleanup. Existing creation can persist a recipe even if enqueue fails; retain honest acceptance semantics and record that inherited limitation. Existing model routing/extraction configuration remains authoritative.

## Source constraints carried into acceptance

Pinned source reconnaissance for this revision: 9eb64bb06339b25861e45b559284629064c30f7a.
- CAP-01 requirements and useCapture ownership constrain PDF-R02/04/08/09/11: photo rating 0–3/unknown 0, trimmed optional notes, local lock/session pending state, and accepted-ID launch caveat. PDF return Home after acceptance is approved; this does not promise literal parity with the legacy photo countdown.
- CapturesController/CaptureFailureService and CAP-07 constrain PDF-R10: Settings GET list uses paused url-import/recipe-import workflows with failed tasks; Retry re-pends a failed task, Delete queues existing maintenance cleanup. They do not represent a PDF rejected before workflow creation; the approved processor approach intentionally creates the pending import/workflow first, then records conversion failures as workflow-task failures.
- FeatureFlagService constrains PDF-R01/13: reuse registry/Resolve/snapshot and existing member overrides; do not build a second flag framework.
- Existing image-only photo creation and recipe-import constrain PDF-R06/07: server pages enter existing image handling; source PDF must be excluded from image counts.
- Existing Synology compose/.env.example and photo-upload documentation constrain PDF-R15: add the PDF switch to the existing templates and revalidate process contracts instead of copying stale documentation.
Some capture/workflow observations in the original design came from main/feature-flag branch reads; T01 revalidates the remaining insertion points at a pinned implementation checkout. Static source review is not runtime qualification.
