# Recovery exports

The existing authenticated `POST /api/management/backup` operation queues an export. Whenever that workflow runs, it now refreshes current member names/preferences and membership, supported recipe content, weekly plans, calendar events, and the versioned `grocery-extras.json` occurrence history. Empty member, planning, or grocery-extra collections replace older files with empty arrays. This prevents an older export from replaying values that have since changed or been cleared. The existing workflow/task status reports completion separately from request acceptance; no new schedule is introduced.

Recipe content files use `backupContentVersion: 1` to distinguish the exported database envelope from legacy raw recipe JSON. Restore decodes its raw content without repeatedly nesting envelopes. Unversioned ingredient-array and serialized-array formats remain accepted. Unsupported envelope versions are reported as recipe-load errors. Category CSV supports quoted multiline fields and invariant confidence values across machine cultures.

Version-1 recipe envelopes retain nullable positive `servings` as the stored ingredient basis, together with raw recipeYield metadata. A present count or explicit null is authoritative on merge restore and disk sync. Legacy envelopes without the member and direct raw recipe JSON derive the count conservatively from decoded recipeYield. A malformed present count is a whole-record load error. Neither field is added to recipe.info, and quantities are never scaled. Deploy the additive column before application rollout; see [serving projection rollout and explicit backfill](recipe-servings-backfill.md).

Recipe editing can correct a known count or add a missing one with `PATCH /api/recipes/{id}` and `{ "servings": 3 }`. A supplied count must be a whole integer from 1 to 2147483647; null is invalid, and omission preserves the saved count or null. Saving changes the database count and export freshness, leaving raw recipeYield, ingredient quantities and recipe.info unchanged. A current export with corrected servings 3 and raw yield “4 portions” restores/synchronizes as 3; compatible exact snapshots retain the saved column directly. Repeated restore remains authoritative. Deliberate new extraction replaces the ingredient basis and derives its count again; backfill preserves known manual counts, including concurrent saves.

Use `POST /api/management/seed` for the existing intentional merge/import behavior. It keeps unrelated destination rows and preserves history and grocery extras when a legacy export omits their artifact. An explicit empty version-1 history sidecar clears its aggregate scope; an explicit empty grocery-extra artifact adds no occurrences and does not turn merge/import into exact replacement. The existing disaster-recovery attribution helper remains a separate member-file repair operation.

These in-place exports are **not yet an independent disaster-recovery backup**. This slice does not establish complete recipe membership, media reconstruction, whole-set validation or recoverable database/filesystem publication. Keep a separately verified backup of data and media; a second directory on the same disk does not protect against disk loss. The separate online exact-snapshot operation is documented in [Online exact household recovery](exact-recovery.md) and tracked in [issue #244](https://github.com/AlexandreBrisebois/whats-for-supper/issues/244). Do not run restore against household data to test this change.

Grocery-extra artifacts also retain the original accepted creation name when known, so a creation retry can survive a later rename. Legacy rows or artifacts without that fact preserve their retained name; the original pre-rename spelling cannot be reconstructed. A merge that would invalidate retained destination lineage is reported and skipped before extra rows change.
