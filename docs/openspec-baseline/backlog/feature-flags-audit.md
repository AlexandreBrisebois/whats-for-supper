## Executable coverage and actual assertions

- Registry/startup: `api/src/RecipeApi/Program.cs:158–159` registers singleton FeatureFlagRegistry / scoped service. Create trims/lowercases, maps missing/blank/off/invalid to Off, warns on invalid, and accepts on/opt-in. Global precedence is configuration mode, not a global persisted override endpoint or Settings control. Runtime hot reload is not implemented. Owner/graduation/date metadata are internal records, not an operator graduation workflow.
- Resolution/persistence: `FeatureFlagService.Resolve`, `GetSnapshotAsync`, `SetOverrideAsync`: fixed modes dominate stored values; opt-in uses member boolean default false; snapshot iterates registry and ignores unknown stored keys; registered opt-in member/key rows upsert with UpdatedAt. Fixed modes reject before mutation, retained overrides are not deleted. `RecipeDbContext` composite key/member cascade and `api/database/schema.sql:186` agree statically. No verified PostgreSQL enforcement or concurrent upsert outcome claim.
- Identity/API: protected routes use existing household middleware and `FamilyMemberIdModelBinder`; `FeatureFlagsController.GetSnapshot` requires bound existing member; Update requires bound identity, unknown key/member 404, fixed mode 409, opt-in saves. Existing response wrapping yields generated-client `data` / `data.items`. `specs/openapi.yaml:3010–3066` owns GET/PATCH; `pwa/src/lib/api/featureFlags.ts` maps missing nullable metadata and Kiota responseStatusCode to mutation status. No distinct admin flag panel was found.

Configuration is in-memory; persistence is EF InMemory. Tests do not assert flags HTTP wire shape, PostgreSQL cascade or deployed configuration.
