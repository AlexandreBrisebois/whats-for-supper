# Recipe Purge 500 Fix

## Summary

Fix the API 500 returned when a user permanently deletes a soft-deleted recipe from the Recycle Bin with a valid elevated PIN.

The intended behavior is contract-bound: `DELETE /api/recipes/{id}/purge` should return `200` for a valid purge, `403` for a missing/incorrect PIN, `409` when the recipe is not in trash, `404` when missing, and `503` when elevated purge is not configured. It should not leak unhandled filesystem or database failures as ordinary user-facing 500s during expected purge conditions.

## Key Changes

- Add focused API integration coverage for realistic purge state:
  - soft-deleted recipe exists
  - recipe directory exists under `RecipesRoot`
  - search document exists
  - recipe votes exist
  - past calendar event exists, if current product rules permit purging historical planner references
- Update `RecipePurgeService` so purge is explicit and resilient:
  - validate PIN, recipe existence, and `DeletedAt` before destructive work
  - remove known dependent rows that may block hard delete before removing the recipe
  - perform database deletion in a transaction
  - keep filesystem cleanup from creating a half-deleted recipe state
- Preserve the existing public API shape unless implementation proves a new contract response is required.
- Keep PWA behavior unchanged: `purgeRecipe` already treats non-2xx responses as failures and leaves the item visible.

## Test Plan

- Run targeted purge tests first:
  - `task test:api -- --filter RecipePurgeIntegrationTests`
- Run schema/API integrity checks if any contract-facing code changes:
  - `task agent:drift`
- Run impact validation:
  - `task agent:test:impact`
- Run `task gate` if the purge fix touches shared API/database behavior beyond `RecipePurgeService` and its tests.

## Assumptions

- Valid PIN plus a recipe in the Recycle Bin must permanently delete the recipe and return `200`.
- A purge must not leave the recipe row deleted while recipe files remain in an unexpected failed state, or vice versa.
- No frontend contract change is desired for this bug.
