# Design

> **Selected — 2026-11-12:** Bilingual identity is included in this release with an app-owned model-authored bounded vocabulary and durable JSON/full recovery. **Historical, superseded — 2026-11-10:** it was deferred from the first portions baseline. The history remains evidence of sequencing, not a current prerequisite or exclusion.

## Context and Existing Ownership

Canonical shopping fields already retain nullable FoodId/MappingRevision and protected names; ordinary Save rejects unqualified association changes. `SupperIngredientProjection` fingerprints a saved FoodId or fallback name plus package. `GroceryRecomputeService` currently groups normalized names/unit/package rather than food IDs. `IngredientNormalizer` provides mechanical fallback, not bilingual semantic authority. Reuse their exact numeric, saved-contributor, split/merge and checked-baseline rules.

`CurrentRecoveryHouseholdState.Dictionary.cs` validates internal releases, exact aliases, qualifiers, per-line mappings and household overrides; it explicitly is not live catalogue adoption. `Infrastructure/CurrentRecoveryArchive.cs` recognizes required food-dictionary/household-food-overrides artifact kinds. `LocalStorageProvider.SaveAtomicallyAsync` supplies durable whole-file publication. However, `RecoverySnapshotService` currently captures selected DB tables/media/weekly interest, and restore rejects unknown nonrecipe artifacts: placing JSON under DataRoot alone does not integrate full backup/restore. The selected [sources policy](sources.md) replaces external dataset adoption.

## Decisions and Tradeoffs

### Bounded authored vocabulary and exact evidence

Create a small model-authored draft, then review and pin its actual UTF-8 JSON bytes, format version, release revision and SHA256. No JSON is generated by this planning update. Each food has an app-owned stable ID, food revision, EN/FR labels or explicit missing label, exact aliases with locale/text/match key/relation, purchase qualifiers, status and local authoring/review provenance. Record model identifier and authoring/review revision separately from recipe source/protected human provenance; do not invent external codes, citations or independent semantic validation. Model confidence cannot make an alias exact.

Use explicit full-phrase aliases. The exact-match key uses NFC, trimmed/collapsed whitespace and invariant case while retaining accents and purchase words; it is separate from the existing lossy fallback normalizer. Viewer locale is presentation, never evidence of source-language identity. Cross-locale candidate matches must agree on one reviewed purchase identity; collisions/ambiguity abstain. Do not strip every preparation adjective or infer broader/narrower equivalence. Start with fresh bulb onion, fresh tomato and canned tomato; review any onion/onion diced/onion sliced/oignon/oignon émincé aliases individually. Ambiguous échalote, poivron/piment, coriander leaf/seed, cream percentages and alternatives can remain unmapped.

Food qualifiers preserve fresh/canned, salted/unsalted, dietary and product distinctions. Package count label/capacity/unit/net-drained basis and explicit unit definitions remain outside food equivalence. Same food in400g/800g packages stays separate; no regional cup/mass-volume/count-kind conversion is inferred.

### Deterministic mapping and independent labels

One common qualified publication/correction owner resolves reviewed exact aliases against a captured vocabulary revision and saves FoodId plus mapping/dictionary/food revision evidence coherently with contentRevision. New URL/photo/PDF and later synthesis/share use this same seam; no channel-specific translation resolver or caller-supplied association trust. External recipe extraction may still use its existing provider, but labels/identity are never guessed during reads, recomputation, restart or restore.

EN/FR label selection occurs on read without rewriting persisted Shopping.Name, contentRevision, demand identity, contributors or checked baselines. Two members can read the same list in different locales. Missing label uses saved source shopping spelling. A label-only revision keeps stable food/purchase identity; remapping is a separately reviewed affected-set transition, not a rename shortcut. Null→FoodId changes purchase meaning under the existing fingerprint: do not suppress that guard. Ordinary split/merge/new-meaning rows start unchecked and continuing rows retain the established proven-increase policy; locale-only changes never reset them. Requalify the accepted400-clear/untouched800 lineage case.

### Private corrections, global releases and category scopes

A household name/association correction is private and protected. A proven same-food display override can retain its association; a changed or ambiguous purchase meaning clears/revalidates FoodId/MappingRevision instead of leaving an onion ID behind a canned-tomato name. An explicit clear cannot be revived by provider work, label updates or restore defaults. Quantity-only Saves keep content/mapping references coherent without silently remapping.

Global aliases/labels change only through a reviewed pinned vocabulary release, never from a private correction or model suggestion. Food/fallback household category correction is distinct from extra-occurrence category mutation. Preserve the existing normalized-key endpoint until the shared food-scoped revision contract/client transition is implemented; no silent key reinterpretation. A unique prior manual category retains provenance; conflicting alias categories remain unresolved, never selected by source/alphabetical order or provider confidence. Keep revision checks, stale-week UI guards and protected human precedence.

## First Observable Slice

A reviewed minimal vocabulary → real EN/FR import/publication → persisted mapping/reference revisions → ordinary scheduling and exact grocery recomputation → generated-client EN/FR reads of the same saved rows. Compatible onion aliases group once; fresh/canned tomatoes and incompatible units/packages remain separate; ambiguous inputs remain source-named. Switch locale/source order without changing amounts, row/check/baseline identity or recipe originals, while a provider spy proves zero runtime lookup/translation calls.

Continue through an ordinary private correction, explicit association clear and stale producer rejection, household category conflict/fallback, then durable restart/full backup→isolated restore→re-export. Fixtures that seed FoodIds directly qualify consumers only, not this producer. Mapping and label acceptance must precede final qualification of later intake channels and final migration/recovery cutover; PDF freshness itself receives no bilingual code.

## Persistence, Concurrency and Recovery

Persist the app-owned vocabulary as versioned UTF-8 JSON beneath DataRoot using the existing `IStorageProvider` named partition and atomic publication owner; the concrete path/manifest shape is bound with Root's shared contracts before code, not a new filesystem framework. Retain every referenced release/definition and its exact revision/hash. The reviewed model draft is initial installation input only; persisted/restored JSON is the subsequent authority. No runtime AI, external fetch, implicit reseed or generation substitutes for missing/corrupt referenced data.

Initial installation distinguishes genuinely absent new membership from a missing file required by saved references. Replacement validates the entire proposed document and compares expected current revision/hash before atomic publication; stale/different existing valid data is not overwritten. A release manifest records food/alias/qualifier/label changes, affected mappings/rows/manual category conflicts, protected corrections, counts measured from current data and reversal mapping. Relabelling cannot delete an older referenced release. Interrupted publication resumes the retained accepted bytes, not model regeneration.

Capture vocabulary bytes once with coherent DB mappings/overrides under the existing snapshot/write fence. Archive food-dictionary and household-food-overrides retain stable IDs, release/mapping/content revisions, provenance and explicit clears. Extend ordinary full snapshot capture/manifests, required-artifact/hash/dependency validation, staged restore/publication and recovery journal; adapt the existing internal archive facts rather than treating them as a completed live API. Demo/disposition handling is explicit. A quantity Save and its mapping contentRevision must commit coherently; file/DB races cannot yield dangling references.

Missing required JSON, unsupported format, checksum mismatch, unknown food/release or inconsistent mapping/override membership rejects before any restore writes. Full backup→isolated restore→re-export preserves exact definitions/references and human facts without network/model calls or bundled-seed substitution. Label/restart/recompute/restore does not reset checks. Mapping/category API shapes, expected revision scopes and old-client conflicts remain owned by [shared contracts](../canonical-ingredient-correction/contracts.md) and synchronized OpenAPI/generated clients/method-sensitive mocks before implementation.

## Compatibility, Rollout and Reversal

A compact model-authored reviewed vocabulary plus honest fallback avoids the external acquisition/licence/attribution pipeline and a broad noisy automatic crosswalk. Reusing current storage/archive/check owners is smaller than a new dictionary/export framework. Merely adding translations to IngredientNormalizer would merge meanings without saved authority and make locale affect identity; do not take that shortcut.

Adoption/reversal is a captured release operation with exact prior/new revisions, hashes and affected-set manifest. Disabling new matching does not delete saved IDs/protected corrections or erase already checked demand. Do not silently downgrade files or rewrite mappings to an older bundled seed; reversal must retain referenced releases and reconcile affected meaning changes explicitly.

Crosslink the [migration companion](../migrate-canonical-recipe-model/design.md) and [rollout owner](../canonical-ingredient-correction/rollout.md): preserve **all** planned meals/events and their identities/intent; recompute **all** stored/required grocery lists. Bulk check/baseline reset is permitted only in that migration epoch, with retry fences preventing a repeated reset of later shopping work. Manual extras/corrections/history remain protected. There is no empty-list gate or plan-clear prerequisite. Detailed mutation sets, epoch manifest and operational acceptance belong to that companion, not a second migration implementation here.

## Qualification and limits

Keep model-authoring/review, deterministic resolver units, actual producer/API/PostgreSQL, locale/check browsers, durable restart, full backup/restore and migration evidence separate. Test collision/false-merge/qualifier cases, unsupported units/packages, private/global scope, stale revisions/clears, missing/corrupt/stale JSON, interrupted publication and file/DB snapshot races. All tasks remain unchecked until their actual acceptance. Existing external research is historical/not adopted; no source download, model runtime, implementation, schema application or deployment occurs in this planning revision.
