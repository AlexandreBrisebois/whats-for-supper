## Established path and representation

1. [RecipeDetailSheet](../../../pwa/src/components/recipes/RecipeDetailSheet.tsx) `action-find-similar` calls its parent with the loaded `recipe.id`.
2. [Search](https://github.com/AlexandreBrisebois/whats-for-supper/blob/2a5ff0b62484993c14d551aac6e035cf72caec29/pwa/src/app/%28app%29/recipes/page.tsx) initializes `similarTo` separately from `open`. `handleFindSimilar` closes detail, empties text and calls `runSearch('', recipeId)`. Active filters/preferences and parsed planner parameters are retained; continuation and invalidation refresh retain context too. Browse and Cooking navigate with `similarTo`. [Planner](https://github.com/AlexandreBrisebois/whats-for-supper/blob/2a5ff0b62484993c14d551aac6e035cf72caec29/pwa/src/app/%28app%29/planner/page.tsx) previously navigated with `open` instead. The correction changes only this query key; no implied day assignment.
3. [searchRecipes](../../../pwa/src/lib/api/recipes.ts) uses generated `RecipeSearchRequestDto` types but sends a JSON `fetch` POST using `requestAdapter.baseUrl`; it is not an invocation of the generated request builder. It accepts raw or `data`-wrapped responses and maps DTOs into display state. The [OpenAPI](../../../specs/openapi.yaml) POST search shape includes nullable Similar UUID, filters/preferences, planning context and cursor. [RecipeController](../../../api/src/RecipeApi/Controllers/RecipeController.cs) validates the request and delegates to the service.
4. [RecipeSearchService](../../../api/src/RecipeApi/Services/RecipeSearchService.cs) builds a ready/nondeleted recipe query with shared predicates. Similar takes precedence over text/concepts for retrieval. Source lookup requires ready/nondeleted, independently of candidate filters. A missing/deleted/unready source returns no candidates.
5. Compatible source embedding requires semantic enabled, ready index/embedding, matching fingerprint, configured model/version and dimensions (default 1536). [Semantic repository](../../../api/src/RecipeApi/Services/RecipeSemanticSearchRepository.cs) selects nearest compatible current indexed candidates with hard filters/source exclusion before its configurable limit (default 50). The 300 ms budget surrounds semantic retrieval, not the whole request. A successful empty semantic pool does **not** trigger lexical recovery or a pool union. Public `resultPath` is `similar` for both paths; candidate reason sources distinguish `semantic-match` from `lexical-match`, so `resultPath` alone cannot identify fallback.
6. Without a compatible embedding/repository, or on semantic failure, fallback builds name + first 12 ingredient strings + cuisine/category + up to 6 meal types, deduplicates up to 20 values and truncates to 300 characters. [Lexical repository](../../../api/src/RecipeApi/Services/RecipeLexicalSearchRepository.cs) admits phrase/individual token substring matches over ready document text, orders `word_similarity` and limits to 50 after filters/source exclusion. Any token can admit a candidate, including pantry words; bounded retrieval can omit useful alternatives before structural scoring. The in-memory test fallback is a different trigram approximation, not evidence of PostgreSQL recall.
7. [Scorer](../../../api/src/RecipeApi/Services/RecipeSimilarityScorer.cs) combines normalized cosine 40%, ingredient Jaccard 25%, cuisine/category equality 10% each, meal-type Jaccard/known vegetarian equality/time proximity 5% each. Fallback supplies raw cosine zero, giving constant semantic 0.5 and weighted 0.2; that constant cannot by itself reorder fallback candidates. No execution-diversity input exists. Names and instructions are not scorer inputs.
8. [Document builder](../../../api/src/RecipeApi/Services/RecipeSearchDocumentBuilder.cs) reads JSON ingredient strings and legacy object `name`; malformed JSON contributes nothing. Normalization is Unicode FormKC, whitespace and lower-case. It does not remove quantities/preparation wording, stem, translate, map synonyms, identify defining ingredients or weight pantry terms. Document text includes name/description/ingredients/notes/category/cuisine/meal/time/vegetarian facts, but not recipe instructions. [Recipe](../../../api/src/RecipeApi/Models/Recipe.cs) has raw metadata and ingredients but no canonical technique/form field. Category is not a guaranteed dish-form taxonomy. Semantic text might indirectly encode execution in names/descriptions; its model quality is unmeasured here.
9. Similar skips family rating, votes and weekly-history boosts. With both week/day parameters, persisted-week recipe membership still adds the existing -10.0 demotion. This demotion is larger than the scorer’s entire 0–1 range, so retained planning context can dominate otherwise similar candidates. Final ties use creation descending then ID. The first report-free candidate becomes Top Pick unless review filters are active; there is no Similar usefulness threshold. Reported recipes can remain ordinary alternatives. Top Pick is separate from the requested alternative count. Ranked continuation snapshots order and rechecks eligibility; no fresh rerank is promised.

## Constraints to preserve

Ready/nondeleted, source exclusion and supported filters are real eligibility boundaries. `SupperSuitable`, rotation/Human OFF and cooldown are **not implicit Similar exclusions**; do not accidentally import Discovery eligibility into library search. Vegetarian/cuisine/meal/discoverable/review filters apply as requested. PostgreSQL applies Quick from indexed minutes; the general recipe predicate lacks that clause, so in-memory and continuation qualification must not be conflated with the SQL path. Accepted but ineffective preference/filter concerns belong to #265; do not fix them incidentally here. Concepts are retained but do not drive Similar retrieval. No new rotation, report, promotion, time or planner rules are authorized by “different execution.”

## Settled requirements for the eventual ranking change

These express the owner's intent; they do not settle thresholds, extraction or weights and are not synchronized into the current runtime spec yet.

- Favor candidates sharing defining ingredients but offering a different technique, meal form or meaningful flavor treatment over the same dish repeated with trivial variation.
- Sharing salt/oil alone must not establish a useful core-ingredient match. Do not globally discard ingredients that can define particular dishes (e.g. oil-based sauce, bread, rice, onion dishes).
- Preserve explicit constraints, source/readiness/deletion exclusions, report handling, planner context, pagination and purpose separation. Ordinary Search, Browse, Discovery and Quick Find retain their algorithms.
- Missing metadata is unknown, not evidence of different execution. Explain uncertain or unavailable alternatives honestly; do not label an inferred difference as a fact.
- Evaluate retrieval membership before ranking. Measure component changes and pairwise/list-level outcomes, including no-useful-alternative cases, before claiming quality improvement.

## Morning decisions — recommendation, alternatives and consequence

1. **When only near-duplicates are available, show them or return no useful alternatives?** Recommend prefer evidenced different executions, with an explicitly described related-recipe fallback; alternative: strict empty result. This changes thresholding, Top Pick semantics, copy and sparse-metadata behavior. Do not silently return unrelated dishes to fill the page.
2. **What counts as different enough?** Recommend technique or form as strong evidence; seasoning-only change is weaker and needs examples. Alternative: any cuisine/flavor change qualifies equally. Review stir-fry → baked rice/stuffed peppers, curry → patties, omelette → casserole, roast salmon → fishcakes; compare with merely changing a stir-fry sauce. Also decide whether the first several alternatives must differ from one another, not just the source (pairwise relevance versus list diversity).
3. **How should execution evidence be obtained for existing recipes?** Recommend an explicit, auditable canonical technique/form representation with unknown values retained, only after assessing existing raw-metadata/instruction coverage. Alternatives: conservative title/description inference (less work, language/ambiguity risk) or request-time model judgment (latency/cost/non-determinism). No provider, credentials, extraction, reindex or paid service is started. This is a substantive architecture decision, not a weight tweak.
4. **Does Similar mean library alternatives or supper-eligible alternatives?** Recommend retain current library eligibility and explicit filters in this task. Alternative: require `SupperSuitable`/rotation eligibility, which would hide recipes and needs a separate explicit contract decision. A ready dessert or Human OFF recipe is not automatically invalid in today's library search.
5. **Household examples for qualification:** review a small selection together in the morning, without production writes: source + returned IDs/order, exact entry surface, request/context, deployed SHA and index/embedding status. Label core ingredients and execution for source/candidates; distinguish unavailable candidates from bad ordering. Start with the original disappointing example, bilingual names and one empty/near-duplicate-only collection. Synthetic fixtures cannot substitute for these judgments.

Pantry weighting recommendation: diagnose ingredient canonicalization and actual candidate recall first, then compare a bounded pantry policy versus corpus-frequency weighting on household-labeled examples. Frequency alone can wrongly discount the family's staple proteins/starches. C4/C8 justify testing reduced pantry influence, not choosing arbitrary constants or changing shared search-document normalization.
