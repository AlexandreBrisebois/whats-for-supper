# Design

## Context and Existing Ownership

This cross-layer corrective change needs a design. `ScheduleService.MoveScheduleEventAsync` currently scans through index thirteen then swaps; `MoveCrossWeekAsync` scans only the target week and can return without moving. `AssignRecipeAsync` can then overwrite Monday during Sunday replacement. These are source observations, not runtime reproduction. Home's `handleRecoveryAction` validates Order In before movement. The shared `pwa/src/lib/planner/slotAssignment.ts` owns Planner/Search/Browse recovery request construction. Existing tests cover ordinary pushes, explicit source selection, legacy skipped sources and grocery recomputation, but do not establish multi-week relational conservation.

`CalendarEvent` carries identity, recipe, date, status, meal slot, vote count, candidate IDs and non-cooking details. `api/database/schema.sql` enforces immediate uniqueness on `(date, meal_slot)`. Existing `DeploymentCalendarPostgresTests` supplies isolated PostgreSQL, authenticated HTTP, fixed calendar and real browser/live fixtures; reuse its fixture pattern without copying its private helpers indiscriminately. Calendar ownership, grocery policy and stream transport stay with their existing services.

## Decisions and Tradeoffs

- Accepted: one-day contiguous push across weeks; move future Planned/Locked/Skipped entries, reject any Cooked source or displaced entry, preserve non-cooking details and locked status. An empty supper slot ends displacement; later entries stay put.
- Extend `MoveScheduleDto.intent` with `tomorrow` and optional `sourceDisposition: order_in`. Require explicit `fromIndex`, verify `recipeId` at supper slot zero and require the resolved target to equal source date plus one. Reject an Order In disposition for other intents. Existing `swap` and `push` paths remain unchanged, including Plan later and Save for Next Week callers. Reusing `push` would silently change these separate operations.
- Use existing POST `/api/schedule/move` with an additive Tomorrow result under `data`: `message`, `moved: true`, `sourceDate`, `destinationDate`, `affectedWeekStartDates`, and `refreshComplete`. Existing clients can retain the message-only contract for legacy intents. Tomorrow clients must require `moved: true` before replacement; a missing result is not success. Return 400 for invalid targeting/options and 409 with the existing error envelope and a user-safe message for missing/stale, Cooked, AwaitingConsensus or concurrent conflict. Authentication is unchanged.
- Conservative compatibility guard: AwaitingConsensus is rejected rather than inventing a transition for pending voting content. Only supper slot zero is addressed; another meal slot neither blocks nor moves. A source index never falls back to another recipe occurrence. Date overflow rejects without writes; no arbitrary week horizon is introduced.
- Source Order In disposition is part of the same transaction, avoiding a compensating request that could overwrite a concurrent change. A legacy recipe-backed Skipped source retains its non-cooking source entry and transfers its recipe/votes to a new Planned destination; displaced Skipped entries move intact. Ordinary source identity moves with its complete content. Candidate IDs remain with the original non-cooking source when splitting a legacy Skipped source; the new Planned recipe destination has no pending candidate list.

## First Observable Slice

Sunday October 11, 2026 contains A, October 12–25 are occupied and October 26 is empty. In a Toronto deployment with a Tokyo browser, Home Pick Something Else → Tomorrow calls generated client → authenticated move controller → real service → isolated PostgreSQL → grocery recomputation → stream publication → authoritative schedule reads. A reaches October 12; all fourteen displaced entries advance exactly one day. Assert exact event identities, recipe occurrence multiset, content and three affected Monday dates October 5, 12 and 19 plus final spill week October 26. The subsequent replacement is still a separate assignment and is not claimed atomic. Only after this tracer is green extend to collision rejection and Order In.

## State, Concurrency and Recovery

Capture deployment context once at entry. In a serializable relational transaction, read/validate exact source and contiguous supper chain. Determine the complete plan before writing. Apply moves from the empty end backwards, flushing each date change inside the transaction so the immediate unique constraint is never violated; a single unordered EF save is insufficient. Ensure missing affected weekly plans inside the same transaction, retaining existing week status. Rollback all mutation on conflict or cancellation before commit. Map serialization/unique conflicts to 409 rather than automatically rerunning movement. Two requests for the same exact source cannot both succeed; the loser must reread. No new idempotency store or universal reservation framework is proposed.

The UI suppresses duplicate actions while pending. Tomorrow explicitly disables Kiota retry middleware for this non-idempotent request; a gateway timeout after commit must reach reconciliation rather than silently reposting. A known 409 retains recovery and shows its reason. A lost response blocks blind retry and replacement until source/destination rereads reconcile the operation; if ambiguous, keep recovery blocked with refresh feedback instead of guessing. A known committed result never repeats movement. General replacement failure handling remains WFS-BL-002; this change only gates replacement on a real committed move.

## Persistence and Side Effects

The calendar transaction includes source disposition, all shifts and missing plan creation. Grocery recomputation and publication follow commit using the sorted distinct Monday dates of every changed source/destination entry. Recompute every touched week, preserving grocery check maps under existing policy; publish refreshed snapshots and fill-the-gap invalidations through existing publisher methods with captured calendar context and request exclusion/echo identity where supported. Attempt remaining weeks even if one fails. `refreshComplete` is true only if all required follow-ups complete; failures return a committed result with false and affected week identities. Existing logs record failures without claiming rollback or guaranteed event delivery. No outbox or automatic postcommit replay infrastructure is added.

## Compatibility, Rollout and Reversal

Update OpenAPI first, regenerate Kiota, then update only Tomorrow branches in Home and `resolveOccupiedSlot`. Inspect all direct move callers: Planner Plan later continues using legacy push. No schema migration or constraint weakening is planned. Stateful mocks implement the new intent/result and reject blocked movement without mutation; they retain legacy behavior. Deploy API support before a new PWA if releases are separated. Old clients retain their old behavior until updated; this increment does not claim to repair old cached clients. Reverting code does not reverse already accepted meal-date changes; never restore household data as a code rollback.

## User Experience

Retain existing recovery dialog, Solar Earth controls and navigation. Show pending action state, disable duplicate activation, and keep the pending replacement on rejection. Cooked conflict feedback explains that a completed meal blocks the move and offers refresh/back without silently dropping anything. Order In is displayed only after committed Tomorrow disposition. Refresh failure is distinct from move rejection. Preserve accessible status/error announcements and keyboard focus in the existing dialog; no new configuration or collision choice is exposed to the household.

## Acceptance and Limitations

Exact multiset conservation must count occurrences, not unique recipe IDs. Check every moved field, unchanged adjacent gaps/other slots/week statuses, grocery content/check state and all affected publications. Real PostgreSQL tests must establish immediate-constraint safety, rollback after intermediate flush, and concurrent duplicate behavior. Browser mocks test caller states only; pair the tracer with a real API/PostgreSQL browser and two independently connected clients. Abort before dispatch writes nothing; cancelling transport after commit does not imply rollback. Existing legacy swap, Plan later, defer, Drop, calendar and skipped-source tests remain regression boundaries. No runtime acceptance has yet been run.
