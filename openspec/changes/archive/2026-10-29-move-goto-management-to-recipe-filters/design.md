# Design

## Context and Existing Ownership

This is a source-based design review, not a rendered acceptance claim. See [proposal](proposal.md) for scope and revision status.

- `pwa/src/app/(app)/browse-all-stack/page.tsx` has a single All/Discovery toggle followed by presentation, recycle and Close controls. A second Filters row opens BrowseFiltersSheet. Its stack wrapper combines `min-h-[740px] md:min-h-[860px]` with viewport maximums, allowing minimum height to defeat the available height. Existing request/history generation and membership-version guards own collection refresh.
- RecipeFiltersSheet mounts FamilyGOTOSettings; both pages coordinate GotoAcquisitionSheet. RecipeDetailSheet already owns star membership saves, pending disablement and success/error feedback through the family store. Keep this owner rather than introducing another membership editor.
- TonightPivotCard uses a 5:4 image area with a 28 px Utensils fallback. Its settled empty helper says “Tap the GOTO star…” and links to Browse. HomeCommandCenter’s `onDiscover` calls `startAction('quick_find')`; changing only the label would leave the wrong flow.
- Planner’s `handleSearchForDay` in `pwa/src/app/(app)/planner/page.tsx` opens `/recipes?addToDay=<dayIndex>&weekOffset=<offset>&referenceWeekStartDate=<reference>`. Search’s `assignWithRecoveryGuard` handles empty/occupied slots and returns to planner with success/day/week/reference parameters for this context. Reuse it. `meal-assignment` owns commit/recovery; this change supplies today’s target only.
- `ROUTES.GOTO_MANAGEMENT` currently includes `gotoOnly=true&manageGoto=true`; MinimalCapture uses it for Back to GOTOs. Capture tracks pendingRecipeId and existing ready notifications. Their processing lifecycle survives management retirement.

## Decisions and Tradeoffs

1. **Amend this active change.** Its earlier implementation is recorded in Git and historical verification references below; it has not been synced/archived. Replace contradictory current deltas and future tasks together, preserving server requirements. A second active change would leave contradictory toolbar/management instructions until archival. No archival or implementation is part of this pass.
2. **One toolbar, immediate star.** Order is All/Discovery toggle → Star filter → cards/list → recycle → Close. Reuse the recipe Star glyph and established selected/unselected tokens. Accessible name is “Go-To recipes only” / “Recettes incontournables seulement”, with aria-pressed. It is a filter, so it never toggles a displayed recipe’s membership. No Apply or management flyout on Browse. Keep Search’s ordinary filter drafts/Apply/Clear/dismissal and Go-To option.
3. **Preserve normal-phone size; adapt only with less space.** Remove the extra Filters row first and retain the current preferred stack/card width, height and photographic presence on the normal phone viewport. Do not replace the 740/860 px sizing with a globally smaller preferred height or a shrinking image region on every phone. Constrain the tall minimum only where genuinely smaller available space requires it, using available dynamic viewport height after toolbar/safe areas, min-height:0 boundaries and intentional content scrolling as needed. Retain preferred dimensions whenever they fit. At ordinary short portrait size, expose recognizable imagery, title, a recipe-opening/selection action and navigation; in short landscape/enlarged text, retain readable content and reachable controls rather than forcing a tiny card. Avoid competing scroll traps. Compact toolbar spacing/pill padding without shrinking touch targets/fonts or hiding Close/recycle.

   The user’s actual phone dimensions are not established. Use **390×844 CSS px as an explicit provisional normal-phone reference**, consistent with the prior Home comparison size, not as a claim about their device. Before implementation changes, capture current Browse stack/card and image dimensions at that reference with fixed content, locale, text scale, safe areas and browser chrome assumptions. Compare matched after captures and bounding boxes: preferred stack/card width and height must remain unchanged (allow at most 1 CSS px rounding), with no reduction of image area solely to accommodate the toolbar change. Removing the row may move the stack upward, which is expected and must not be mistaken for resizing. If the actual phone viewport becomes available, repeat this preservation comparison there. Test 320×568 and 390×667 separately as smaller-height cases; their adaptation must not change the preferred-size result at the reference. Exact small-screen constraints are bounded implementation tuning, not permission to shrink all phone layouts.
4. **Membership lives on recipes.** Retire both management disclosures, pending-management rows and Add a Go-To acquisition sheet/entry points. Keep recipe-detail stars, immediate save semantics, existing saved memberships and Settings absence. Search’s Go-To filter remains visible with other filters; no acquisition action is substituted there. Empty filtered results offer Clear Go-To/clear filters and guidance to star recipes, never a dead link to management.
5. **Home Search uses planner selection.** On the unplanned pivot, resolve fresh authoritative Today calendar context, derive today’s day index and open the existing Search route with `addToDay`, `weekOffset=0`, `referenceWeekStartDate`. Do not use device weekday alone, fabricate a reference, launch Quick Find or add a Home/Today search mode. Successful selection follows the planner’s current success return, not a new Home return. Cancel/back makes no assignment. If today becomes occupied, use existing recovery. Saved Mystery and other non-cooking/planned presentations retain their existing alternate actions; this revision does not reroute those states.
6. **State-specific cookbook invitation.** Ordinary empty state: retain white rounded shell, cream/soft depth, Outfit/Inter hierarchy and terracotta primary; enlarge the existing fork-and-knife illustration in the local pivot composition (initial design target 96–128 px at ordinary mobile text size). It is deliberate decorative artwork, never a recipe photo. Bound its height so Search and Order In remain useful on short phones; reduce illustration space before reducing control readability. Do not enlarge shared TonightRecipeImage fallbacks. Ready Go-To keeps its real photo, title and Make this tonight as primary; Search/Order In are quieter alternatives. Represented checking/pending keeps truthful feedback; no fake ready image/action. Saved Mystery or other non-cooking/planned states never receive the ordinary-empty invitation.
7. **Teach without another destination.** Below immediate choices, use short charcoal helper copy with the same inline recipe Star in place of the word GOTO, and remove Choose GOTO recipes. Proposed EN: “Tap the [Star] on favourite recipes so we can suggest one here.” FR: “Touchez l’[Star] sur vos recettes préférées pour que nous puissions vous en proposer une ici.” Localize accessible text (“star” / “étoile”) with the icon; do not announce an unnamed symbol, raw GOTO or duplicated icon text. It is explanatory, not another membership control. Preserve settled-read gating and avoid claiming that failed active retrieval means no saved memberships.

## First Observable Slice

Browse’s immediate filter is the first slice: toolbar activation → existing gotoOnly state → current GET `/api/recipes` → filtered totals/cards/list. It exercises the UI-to-client boundary without API changes. A method-sensitive mock using existing response shapes proves the browser path; existing server membership filtering is preserved, not reimplemented. Short-screen rendered visibility is part of this slice, not deferred to a scroll-only check.

## State, Concurrency and Recovery

Keep existing generation/history guards, first-page reset on filter change, all continuation/prefetch/wrap/retry inputs and mounted membership-version refresh. A rejected recipe-star save retains confirmed membership/results. A successful save followed by failed retrieval offers read Retry without resubmitting membership. Closing unchanged detail retains position.

Home Search waits for authoritative calendar availability and exposes existing calendar retry if unavailable. Capture/navigation/filter activation makes no meal assignment. Assignment guards stay with the planner owner; stale calendar or concurrent occupancy does not authorize overwriting a meal.

## Compatibility, Rollout and Reversal

- Legacy `/browse-all-stack?gotoOnly=true&manageGoto=true`: honor gotoOnly, ignore retired manageGoto, render normal filtered Browse. Empty state offers clear; no management or acquisition sheet opens, no save occurs.
- Remove application links that create `intent=goto`. A newly loaded stale `/capture?intent=goto&mode=describe|photo` uses ordinary capture with the requested mode, without automatic membership registration. It does not create on navigation.
- For an already submitted legacy capture, preserve the accepted recipe, confirmed pending membership and background processing. Do not resubmit acquisition, replay list replacement or clear membership to normalize the route. Keep existing ready notifications and in-place transition while present; offer localized Done → Home explicitly, without auto-navigation or a ready-only filtered destination that hides pending work. Pending status remains truthful after departure; ordinary capture/background processing owns ready/error recovery. These compatibility cases do not restore a separate pending-management list.
- Backend/data remain intact. Reverting the frontend revision can restore the prior presentation without migrating data. New empty-state artwork is local, avoiding changes to planned/ready fallback geometry.

## User Experience and Acceptance

Search is the ordinary unplanned pivot’s primary terracotta/light-text action. Order In stays visibly enabled and secondary; its existing non-cooking-plan persistence/error behavior remains and must never imply delivery ordering. Ready Go-To keeps Make this tonight dominant. Other state actions retain their established meaning.

First compare normal-phone Browse stack/card/image baseline dimensions at the provisional 390×844 reference under the matched conditions above, preserving preferred size. Separately compare smaller-screen Browse captures for useful content and controls; do not treat small-screen fit as evidence of normal-phone size preservation. Compare matched before/after captures for Browse stack/list and Home empty/ready/checking/pending/planned/Mystery/non-cooking states. Cover EN/FR at 320×568, 390×667, 412×915, 667×375, iPad 820×1180 and 1180×820; 100%/200% text, long titles, safe areas and reduced motion. Exercise iPhone WebKit and Android Chromium emulation, distinguishing this from physical-device evidence. At ordinary short portrait size, record initial viewport bounding boxes/screenshots before scrolling for recipe content/actions and both Home CTAs. At 200%/landscape, exercise actual scroll/reflow and reachable controls. scrollIntoView alone is insufficient.

Check keyboard order matching visual order, Space/Enter activation, localized accessible names, aria-pressed star state, selected meaning beyond color, visible focus and pressed/pending states, modal focus restoration for remaining Search Filters/detail, no horizontal overflow, and at least 48×48 CSS px touch targets for changed controls. Measure actual text/indicator/focus contrast against rendered composites; no dark text on yellow action field. Reduced motion must preserve state without essential animation. No broad accessibility certification is inferred.

## Risks and Deferrable Questions

Adding a star crowds the existing phone toolbar; compact gaps/padding and inspect French expansion before declaring fit. Normal-phone size preservation is a required boundary: a blanket card/image shrink is not an acceptable toolbar fix. Larger empty artwork competes with CTAs; available-height behavior takes precedence over target illustration size. Removing management removes a dedicated overview of pending Go-Tos intentionally; preserve accepted processing, notifications and ordinary recovery rather than inventing a replacement management screen. No unresolved product decision blocks this plan; final illustration dimensions and wrapping are bounded implementation tuning.
