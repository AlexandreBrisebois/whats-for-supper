## Decisions and Tradeoffs

### 1. Reuse standard delivery; keep custom code at explicit policy boundaries

The user approved bounded SDK memory batching/transient retries. Prefer the direct standard Node SDK: one global tracer/server logger registration plus one **non-global browser log provider** with its separate credential/resource. Explicit provider handles prevent accidental context or credential inheritance; this is producer separation, not duplicate observation. Do not install `@vercel/otel` as well, a Node auto-instrumentation bundle, a browser OTel agent, Sentry, PostHog, a Collector or a proprietary Sentrame SDK.

Minimum custom code is: existing safe admission/config/document scope; a small event-to-standard-log adapter; a stateless safe span projection before the standard batch processor; telemetry self-suppression; static surface declarations; and a two-method typed API issue observer. SDK owns serialization, protocol, batching, retry/backoff, flush and shutdown. Do not subclass transport, implement a retry scheduler, persist telemetry, build a generic event registry/framework or add annotations to every product method. Delete old HTTP/envelope code when parity is accepted; no permanently selectable parallel exporter.

### 3. Standard OTLP export with unchanged evidence authority

Node uses explicit `/v1/logs` and `/v1/traces` HTTP Protobuf exporters, no compression, server-held authorization and no implicit env-selected extra exporters/resource detectors. Browser logs keep `service.name=wfs-pwa-browser`, server diagnostics/traces `wfs-pwa-server`, resource version from trimmed `WFS_VERSION` or `unknown`; logs keep `wfs.anonymous` scope. Browser log calls use explicit root/no ambient trace context. Preserve event names, fixed bodies, field allowlists, event/occurrence identity, source sequence and original occurrence/observed timestamps using standard SDK fields. Never substitute batching/export time.

API extends the existing tracer provider with one selected safe trace export. For the two semantic facts use the **already installed native .NET OTel log exporter** behind one narrow explicitly owned LoggerFactory/provider, not the ambient Serilog application logger. This is an isolated telemetry producer, not a second globally registered logger/trace pipeline or another exporter for the same records. A two-method typed observer emits fixed body, fixed `event.name` and random `event.id`; disable scope/formatted diagnostic capture and resource detectors, pass no Exception and temporarily use a null Activity context only for the synchronous log call, restoring it in finally. No private ambient diagnostic state reaches buffering. The SDK handles transport/deadline/batch settings. Keep Serilog operational logging intact; its broad legacy sink must not be pointed at Sentrame (refuse that unsafe path if destinations coincide). Qualify actual standard name or retained `event.name` fallback, not assumed EventId conversion. This choice avoids custom sink serializers or HTTP deadline/retry handlers.

API receives only `WFS_TELEMETRY_ENABLED`, `SENTRAME_OTLP_BASE`, `SENTRAME_SERVER_TOKEN`, `WFS_VERSION`; browser token never goes there. Use existing origin validation semantics (HTTPS, or explicit local HTTP; no userinfo/query/path/hash), fail closed on invalid config, and suppress library environment overrides for these exporters. No public runtime secrets. Change private env/recreate container only in a separately selected disposable/real deployment; the implementation itself never enables production collection.

Configure the installed .NET exporter's supported `HttpClientFactory` with `AllowAutoRedirect=false`; a redirect is terminal, including a same-origin redirect. Select standard `in_memory` retry through explicitly owned SDK configuration, never an ambient retry setting. Override ambient disk-retry configuration before constructing either selected exporter; no disk retry directory, reflection, SDK fork or custom HTTP/retry implementation is permitted.

The sole API trace provider may be host-managed through `Sdk.CreateTracerProviderBuilder()` with its own `IConfiguration` containing only owned in-memory settings and no environment providers. Retain ASP.NET/HttpClient instrumentation; remove the hosted `.WithTracing` registration when integrating this provider, rather than creating a second provider. Its private configuration must not replace application configuration or alter operational logging/metrics. The narrow LoggerFactory likewise owns private configuration. API deployment settings are an immutable process-start snapshot: changing opt-in, destination, token or version requires process/container recreation, which discards old memory. No live API reconfiguration or batch-entry reread of reloadable application configuration is advertised; the Node dynamic admission/export-entry checks remain unchanged. This follows the approved private-configuration and recreate-to-change design, without using the SDK internal decorator hook or a custom transport. This composition is an implementation detail within approved M3, not an unresolved product decision. The inherited stock 1.20.0 probe and its fresh rerun prove identical-byte 503 retry, same-origin 307 refusal and no disk queue under hostile ambient retry settings; they do not qualify the WFS producers.

**Approved .NET SDK limitation (2026-10-30 23:46 UTC).** Keep stock OTel 1.20.0 on the pinned Linux .NET 11 RC2 runtime despite the diagnostic-response-body inactivity gap. HTTP Protobuf uses `ResponseHeadersRead`; with exporter Error diagnostics enabled by another listener, an unsuccessful response body can be read synchronously beyond two seconds. The owned Linux probe remained inactive through 3,209 ms despite the configured two-second exporter/client/connect/drain settings and 1 KiB response limit. `ForceFlush(2000)` returned true while that read remained active. This proves a >3.2s limitation, not an indefinite hang or termination after a particular interval; shutdown was measured only after deliberate body release. Exact controls remain in `.task/otel-apply/m3b-sdk-body/` and `m3b-sdk-body-linux.txt`.

Two seconds bounds supported .NET caller/processor waiting, not total network lifetime or diagnostic body inactivity. Flush completion does not prove that all I/O terminated. Preserve bounded queues, one connection per selected exporter, admission and pre-buffer privacy, no redirects and private memory-only retry configuration. Do not recover a hard deadline using a fork, custom cancellation/transport, global diagnostic/HTTP changes or new dependency/service. Node timeout B and shutdown A remain separate decisions. A materially different privacy/resource risk remains a blocker requiring explicit reconciliation. This approval resolves the pending M3 policy; actual WFS producer qualification is recorded separately in the implementation tasks.
Supported pre-batch privacy is separately source-qualified: a privacy processor registered before `AddOtlpExporter` can clear `ActivityTraceFlags.Recorded` for unsafe immutable events/links, and the stock batch processor tests that flag before buffering. A mere return from the privacy processor does not stop later processors. WFS policy tests exercise this standard batch admission boundary; actual native/exporter/receiver evidence is recorded separately in M3 tasks.

### 4. Boundedness, SDK lifecycle and privacy projection

Semantic logs retain 100 ordinary/20 error admissions/minute/producer/process; browser caps remain opening once/document, navigation/surfaces 60/minute and errors 10/document. New detail records cap at 20/document, originals at 20 combined/document and issue Save results at 10/document, shared across component instances. No individual semantic-log sampling. Admission consumes identity/cap before async work. Keep distinct SDK log queues for producer and ordinary/error category where needed to preserve capacity; each queue has maximum 256 records, batch 64, delay ≤1 second, one active batch. These at most four log batches satisfy the existing producer concurrency ceiling. Trace queue has separate capacity and the same queue/batch/wait bounds, with Node inactivity and the approved .NET diagnostic-body limitation.

SDK exporters own finite transient retries with original IDs/timestamps. Under user-selected **option B (2026-10-30)**, two seconds limits the standard processor/caller wait and Node socket inactivity, **not total network lifetime**. Terminal rejection/redirect drops; queue overflow and SDK timeout/retry exhaustion can drop. Active streaming responses and a retry after backoff may outlive two seconds; caller completion does not prove cancellation or receipt. Configure SDK settings only; no application cancellation layer, transport fork, global HTTP patch or custom retry loop. Each category exporter has concurrencyLimit=1 and an ordinary Node Agent with keepAlive=false, maxSockets=1 and maxTotalSockets=1. Together with four bounded category queues this keeps at most four active log requests even after a processor wait expires. A busy exporter can reject subsequent batches; never replace it or create fresh Agents/providers to evade its occupied slot. Trace export has its separate single bounded transport slot. Standard response byte limits remain SDK-owned. Qualify these actual resource bounds under streaming and retry pressure, rather than asserting network termination at caller timeout.

Normal logs enqueue without waiting. Browser Action `after()` owns admission, without per-action forceFlush. Next's error hook uses supported provider forceFlush with a two-second caller-wait limit. Under user-selected **shutdown option A (2026-10-30)**, retain Next standalone deployment and best-effort shutdown delivery: pending queued records may be lost even on normal SIGTERM/SIGINT cleanup. There is no guaranteed normal-host flush attempt. The existing natural Node beforeExit hook can attempt a bounded flush wait of at most five seconds, but Next's explicit signal exit skips it. No custom server host, competing process.exit/signal handlers, browser unload flush or custom cancellation is added. Neither a flush wait nor host drain guarantees active network cancellation. Crash/forced termination can also lose memory. Admission and export entry recheck configuration; already-started requests may continue under SDK inactivity/retry policy. Deployment setting changes use process recreation, not provider/Agent churn.

This shutdown choice is separate from earlier timeout option B. The owned copied-Next SIGTERM/SIGINT/streaming/duplicate-signal probe (`m1-next-shutdown-red-final.json`) demonstrated queued-tail loss under the superseded guaranteed-flush expectation; it remains evidence of that delivery limitation, not a successful flush test. The probe exercised next start; production standalone follows the same installed start-server lifecycle by source inspection, without a separate standalone container shutdown pass. Do not infer delivery from an incidental keepalive drain. M1 task 1.3 retains the non-green broad gate status. The user separately authorized bounded M2 work after this contract reconciliation; that authorization does not make the M1 gate pass or qualify new native signals.

The superseded hard-total-deadline probe remains diagnostic evidence: official 0.300.0 and prior 0.223.0 Node transports, supported Agent options, and retry/backoff failed that earlier assertion. The browser build's fetch cancellation is not a supported Node replacement and followed redirects. `.task/otel-apply/compatibility-report.json` records the bounded investigation. This approved decision changes delivery semantics only; privacy, finite queues, producer authority, redirect refusal and failure isolation remain required. Any inability to retain the concurrent-request/memory caps is a new material blocker, not permission to add cancellation or relax those caps.

Before batching, project only reviewed fixed fields; do not pass SDK-readable spans unchanged to a queue and strip them later. A thin SDK processor delegates safe span views to the standard BatchSpanProcessor; .NET uses existing instrumentation controls plus a pre-batch safe Activity processor at its supported SDK boundary. Remove unapproved tags, fix DisplayName and clear status description before forwarding to the standard batch processor; drop an Activity entirely if immutable events/links contain unsupported data rather than cloning/fabricating its identity. Do not serialize native span structs yourself or fabricate timings/IDs. Preserve within-process technical identity/kind/start/end/parentage; set safe fixed names `next.request`, `next.render`, `next.fetch`, `api.request`, `api.http`. Permit only allowlisted HTTP method, numeric HTTP status and static route classification; drop raw URL/path/host, status description, events, links, baggage, exception details and unknown attributes. Resources allow service/version and fixed SDK name/language/version only; no host/process/container/user/device detector. SDK internal transient operation state is not an export buffer or permission to retain it.

If a registered framework's API cannot meet pre-buffer projection/suppression, its slice remains incomplete: adjust that SDK integration within scope, never quietly weaken privacy or write a custom transport. Library diagnostics stay off or fixed local diagnostics; they never flow into the WFS telemetry error observer.

### 5. Native traces have process-local technical meaning

Use Next's `register()` to initialize the Node SDK once before requests; no provider in Edge/client/build execution, no duplicate registration on development reload. Retain `onRequestError` and the existing AsyncLocalStorage suppression owner. Reuse API ASP.NET/HTTP instrumentation. Do not add generic database/profile/AI/file instrumentation in this increment.

Standard parent-based trace-identity sampling selects 10% of local roots and retains the local child decision; trace capacity is independent from semantic logs. Test sampling deterministically; disposable qualification can inject a deterministic SDK ID generator yielding sampled local synthetic roots through the fixture's composition, not add a production trace-ID override or reuse business IDs. It must still use the same sampler/exporter code and record that fixture identity.

Disable Node remote extraction/injection/baggage for this selected pipeline using the standard no-op propagator. In API sampling exclude remote-parent traces and their children from this export rather than reusing supplied roots or rewriting their IDs; use supported framework/SDK controls and verify actual behavior. No new propagation to API/providers or adoption of existing foreign context. Within-process async context is useful; browser/session/background/cross-process joining remains excluded. Dropped remote-parent requests are a disclosed coverage limit. Existing operational propagation outside this export must not be broadened or confused with Sentrame evidence.

Conservatively admit native Node GET/HEAD root requests only; non-GET/HEAD, Server Action and unclassified roots/children are unsampled. This intentionally excludes all Node POST Action requests, avoiding inspection of Action IDs/bodies or a custom trace-correlation buffer just to suppress telemetry Actions. Framework classification is checked in real M2 qualification; unknown roots fail closed. API POST requests remain eligible under their separate provider policy. Explicitly suppress telemetry checks and every exporter request, including failures; dropping raw exception events avoids duplicate automatic error messages while native status remains technical. A technical 200/202, error status or native span completion never establishes product persistence, page presentation or background success.

The installed SDK3 graph exposes the direct trace provider/processors as `@opentelemetry/sdk-trace` 3.0.0, with `@opentelemetry/context-async-hooks` 3.0.0 for ALS. Use these explicit providers rather than `NodeSDK` auto-configuration, which could register an ambient log provider. Native M2 recognizes exactly scope `next.js` types `BaseServer.handleRequest`, `AppRender.getBodyResult`, `AppRender.fetch`; other types are dropped, and no dynamic route classification is retained. Supported technical method/status and original local parent IDs remain; no manual reparenting fills a missing intermediate. A framework can create separate native roots for one HTTP request, so exported root counts are not request counts. Actual SDK queue drain may reject a batch while its one exporter slot remains occupied; bounded admission is not guaranteed receipt.

### 6. Adopt inventory presentation owners through one shared mechanism

Add a static optional surface declaration to shared visual components only where it removes repetition; the semantic consumer selects the identity. Never attach data attributes/listeners to every button or infer identity from DOM/text/props. Structural containers do not emit in addition to their consumers. Extend the existing coordinator's map with per-instance opaque registration tokens/refcounts so nested or concurrent same-identity surfaces survive replacement/cleanup. Tokens stay memory-local and are never exported. Aggregate identity transitions are zero→one open and one→zero close; this measures presentation availability, not number of instances or which recipe.

Preserve visibility/gate/effect replay semantics. Native dialogs declare presented only after successful `showModal()`/open state; CSS-hidden/mounted-only elements do not open. Covered/inert content can remain mounted/presented as a surface, but is not evidence of focus or attention; do not invent an exclusive screen sequence or close/reopen underlying cooking/detail just because an original modal covers it. Actual hide/unmount closes only if observed while the document can report; no unload/OS-discard closure or return inference.

### 7. A small business pilot rather than inventory-wide instrumentation

Use `RecipeDetailSheet.handleSaveImportIssue` for browser `pwa.recipe_issue.save_result`. Fixed reason priority: valid explicit launch failure → `saved_launch_failed`; valid started+import ID → `processing_acknowledged` (new/reused indistinguishable); valid authoritative detail with both flags false → `saved_manual` (includes unchanged terminal feedback); rejected/unusable/inconsistent response → `unconfirmed`. Claimed once before deferred admission. A deliberate launch-failure throw must not also emit unconfirmed. Keep request/private recipe/generation in local guards only; emit solely for current visible mounted detail. Later close/replacement/hidden/superseded settlement is dropped, no replay. No changed product pending/error/poll/retry behavior, no save-result from automatic status refresh.

`lib/api/recipes.ts` must derive a minimal local telemetry validity/classification from the generated response before its existing boolean coercion and recipe mapping discard information. Missing/non-boolean flags, inconsistent flags/import identity, or invalid/mismatched authoritative detail cannot become `saved_manual` through defaulting. Preserve the wrapper's existing product return/error behavior; carry only a closed local classification/validity value to the current response owner, without forwarding response content or identifiers. Wrapper tests must exercise generated-client responses directly; component mocks alone cannot qualify this seam. No OpenAPI/generated-client edit is required.

API uses a small injectable issue observer with `Saved()` and `Resolved()` only, called after successful ordinary persistence at `PersistAsync` and the report-existed branch of `DeleteAsync`. Skip emission under an uncommitted local/ambient outer transaction, on uncertain thrown save or no-op resolution; do not add transaction callbacks/outbox to make unsupported cases observable. Emit saved before subsequent query/launch/link/compensation can fail. No report success from `MarkSucceededAsync`, workflow processor or SSE in this change. Body is fixed, INFO, resource `RecipeApi`/version, event ID random; no reason selection/note/IDs/trace/activity. New explicit saves are distinct observations even with unchanged content. All telemetry calls contain failures without modifying the database/workflow response or locking policy.

## First Observable Slice

M1: a fresh disposable PWA presents Home→Search→Home, opens/closes Quick Find, observes a controlled browser error and a controlled Next failure, then emits through actual standard log providers to fresh disposable Sentrame. Exercise real root gates/coordinator/Action/after/Node/provider/exporter, not mocked Actions or inserted receiver rows. Assert clocks/resource/service/name/authority/IDs/sequence and forbidden sentinels in protected reads, exact captured-batch replay and storage reopen. Receiver rejection/slow/transient/lost-ack paths prove bounded SDK behavior and noninterference. Remove the hand-built transport only as part of this working slice; subsequent slices do not start from unqualified foundations.

## State, Concurrency and Recovery

Old browser scopes, native error episodes and UI state remain owned by their current modules. The new SDK queue is process-memory delivery state, not a document/workflow database. Duplicate SDK delivery retains identities; independent business attempts create new IDs. No guarantee ties telemetry emission atomically to a domain commit: a crash after save can lose the fact. No count of received facts is a unique-operation/person count.

Separate provider/category capacities avoid trace traffic starving browser or error logs. Batch order is not business order; source sequence/native parentage preserve only their documented meanings. Pre-buffer privacy projection is synchronous/bounded and never performs network or domain reads. Failure there drops the observation. Existing same-origin/clock/payload validations and no arbitrary relay remain intact.

## Persistence and Side Effects

No product schema, business endpoint, queue payload or stored telemetry token changes. API facts occur only at confirmed ordinary database boundaries; lost replies/launch failures can coexist with a saved fact. Browser acknowledgement, server save, review, resolution and background correction remain independent. Image viewer/detail observations never imply persistence or attention. No future shopping all-checked or cooking completion semantics are approved.

## Compatibility, Rollout and Reversal

Proposed order: M1 log migration; M2 native Next traces; M3 API safe native export plus saved-report fact; M4 detail/original/recipe popup adoption; M5 remaining inventory surfaces; M6 issue-response/resolution pilot and consolidated qualification. Each slice includes tests, real exporter qualification and documentation; all task boxes stay unchecked until their required cells pass. Do not defer all integration to a final giant gate.

The three existing capability deltas explicitly supersede JSON/no-compression/no-retry/no-queue behavior with Protobuf/no-compression/bounded memory retry. All other opening, navigation, minimized-error and prospective mapping meanings stay. No dual write, data migration, receiver reset or fallback to the old transport. Before rollback restore the earlier release/disable flag and recreate only selected resources; queued memory may be lost. Preserve original F-series and inventory checkpoint hashes/statuses; new source/config/build/exporter/protocol evidence is new qualification, not a retroactive rewrite.

Applying code does not enable a real deployment or mutate Sentrame. Docker qualification uses owned disposable resources and synthetic data. Public proxy/tunnel and physical installed-phone sessions are reported separately and require selected disposable targets; their absence cannot become a runtime pass or block a narrower local-qualification claim. Do not sync/archive/commit/deploy without separate authorization.

Every new or renamed E2E spec must belong to exactly one capability suite or explicit live qualification in `scripts/ci/e2e-suites.cjs`; run its inventory and selection tests.
