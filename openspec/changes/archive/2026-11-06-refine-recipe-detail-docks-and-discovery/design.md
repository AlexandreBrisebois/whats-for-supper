## Decisions and Tradeoffs

- **Resolved:** Planned is a white navigation control. Alex explicitly chose “bring me to the planner on that date.” Its visible label includes Planned and its date; its localized accessible name communicates opening Planner. It is not disabled status, date mutation or a new save. No arrows or duplicate Already planned message appear with it.
- **Preserve date ownership:** Planned means a confirmed saved occurrence in the current entry context: Planner's captured source, or Recipes' verified displayed target. Another occurrence elsewhere does not override an explicit target. Untargeted Recipes keeps its existing suggested-target policy; this change introduces no global schedule scan, “planned anywhere” promise or new occurrence-priority policy.
- **Keep planning in Planner:** Remove the recipe footer's direct Plan another day copy and the bottom Cook copy. Planned opens Planner for further decisions; unplanned detail retains its existing explicit dated planning journey. This intentionally removes that detail shortcut, not the ability to plan another occurrence through Planner. No date arrow moves an existing meal.
- **Accent follows the permitted next action:** unplanned → dated Plan primary, top Cook quiet; confirmed ordinary planned → top Cook primary, white Planned secondary. Failed/uncertain/review states emphasize their safe Retry/Review action and retain operation ownership. Never make color grant an otherwise forbidden action. Preserve existing separate recovery surfaces.
- **Restore rating styling, not old accessibility defects:** use main's neutral selected surface/shadow and larger emoji/selected emphasis; no terracotta selection or checkmark. Retain current localized labels/names, 48 px targets, visible focus, pressed semantics and legible inactive text. Do not restore whole-button 35% opacity, literal untranslated labels or tiny text that fails the inspected layout. Use static emphasis/reduced-motion-safe treatment and compare actual renders; do not promise pixel identity while deliberately preserving accessibility.
- **Visible Similar belongs with the overview:** place one quiet Search-icon/label action near recipe information before Ingredients, not in either dock. Reuse its existing function and omit the menu duplicate. Planner’s currently misrouted callback must enter `/recipes?similarTo=<recipeId>` rather than reopen `/recipes?open=<recipeId>`; test the visible result from both callers. Preserve the ending Rating → Notes → Ask the Family sequence. The static rating board illustrates control appearance only, not final Similar placement.

## State Matrix

| Starting state | Top Cook | One bottom action row | Preserved behavior |
|---|---|---|---|
| Recipes, ordinary unassigned displayed target | Quiet Cook | Accent Plan for date + existing quiet target-date arrows | Chooser changes proposal only; separate guarded Plan writes |

| Recipes explicitly targets Friday but recipe exists Wednesday | Quiet Cook | Friday's ordinary dated planning controls | Do not silently replace Friday with Wednesday |
| Different recipe or non-cooking target | Existing Cook under safe availability | Existing permitted planning/recovery/confirmation entry in one row | No direct overwrite; guarded replacement/non-cooking consent remains |
| Cooked/prepared/consensus context | Existing readable Cook behavior only | Existing truthful completed/review state, never a false uncompleted Planned claim | No new completion, date invention, frozen-count mutation or consensus reset |
| Target loading, failed read or uncertain save | Existing safety/operation ownership | Loading/Retry/Review as appropriate; no false Planned | Necessary feedback can wrap above the single controls row |
| Grocery original review | Existing Cook at top-left | Existing deliberate Plan transition | Original evidence, source-week return and separate later assignment remain |
| Editing/loading/unavailable recipe | Preserve existing Cook eligibility | Save/Cancel or existing unavailable state; never duplicate planning controls | Keep edit/draft/focus/retry protections |

Here, an unplanned target means the candidate recipe is not already assigned to the displayed date; the destination may still contain a different recipe or non-cooking plan. Its existing guarded replacement/confirmation flow remains available. Routing changes to the shown saved occurrence through Planner does not remove that unplanned selection flow.

The saved destination includes absolute date, captured reference Monday and matching index/week. Reuse the existing Planner route/read/scroll mechanism; recompute or pass offsets against that reference, never the browser's current week. Across Sunday, later weeks and deployment rollover, navigation still opens the captured date. Do not append `success=1` or a synthetic save confirmation. A stale/mismatching occurrence is reviewable as changed, not silently presented as still Planned. Recipe identity alone or a date label alone does not prove status.

## State, Recovery and Accessibility

No new planning API, status DTO or persistence is proposed. Reuse existing confirmed schedule/projection data, occurrence IDs, date/reference helpers, close/draft handling and navigation callbacks. Do not derive Planned from `sourceDayLabel`, `editable=false` or a recipe ID without its date/status. Target checking and later state changes must retire stale claims. Cook and Similar cannot silently discard pending Notes, staged recovery or an uncertain write.

The bottom contains one **row of controls**; labels may wrap inside buttons and explanatory/error text may wrap above. Keep targets at least 48 CSS px, with no horizontal clipping at 320 px/200% text. The top may reflow when needed, retaining Cook at its leading edge and reachable Close/GOTO/share/menu. Preserve original-viewer/nested cooking focus and dock reservations once; do not shrink controls to force a single top row.

Use existing Cook/Cuisiner and Find Similar/Trouver similaire labels. Add localized Planned navigation wording and selected-date names. Verify visible label/accessible name consistency and screen-reader pressed state for rating. Single visible status does not mean hiding required ingredient portions, projection uncertainty, a preview-return control or actual preparation facts; those explain different data.
