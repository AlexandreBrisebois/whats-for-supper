# Ordinary logging that removal would leave

This is the actual residual source inventory for the removal working tree based on `e4cd725dfbd0092667d04ddaa4062dea3846b843` on `review/solar-earth-continuation`, 2026-10-31. Application-owned Sentrame/OTel producers, providers/exporters, forwarding Actions and active configuration have been removed. Ordinary log callsites in modified production files were compared with HEAD and remain unchanged. Focused API host checks preserve console/file/search/request/error logging with obsolete telemetry settings and a reachable sink receiving zero export. Final aggregate acceptance is recorded separately in implementation evidence; this document does not claim deployment changes.

Runtime overrides, enabled deployments, external collectors, actual log rates and retention were not probed. Every retained category below reflects the changed source. Representative shapes use placeholders, not captured user data. [Source index](source-index.md) provides current path/line callsite navigation; historical line positions in the original review are superseded.

Serilog `FromLogContext` remains; configured machine/environment enrichers also remain (`api/appsettings.json`). The explicit templates mainly print time, level, SourceContext, rendered message and exception, rather than every enrichment property. Request logs include method/path/status/elapsed; service logs use recipe/task/workflow/command IDs and dates for practical joins. Search uses its own random per-search `correlationId`. These can correlate product operations and are not anonymous document identity. Framework request/activity IDs may still exist internally; removing an OTel subscriber does not disable framework `Activity`/diagnostic infrastructure. No browser session/tab/source-sequence, Sentrame event/occurrence ID or new cross-service correlation is retained by this cleanup.

## Logs versus other state

- **Removed semantic logs:** `pwa.telemetry.check`, `pwa.app.opened`, `pwa.screen.presented`, `pwa.surface.opened/closed`, `pwa.recipe_detail.presented`, `pwa.original.presented/requested`, `pwa.recipe_issue.save_result`, `pwa.browser.error`, `pwa.server.error`, `wfs.recipe_issue.saved/resolved`. These include the dedicated telemetry logging the owner asked to remove.
- **Removed spans:** native `next.request/render/fetch`, `api.request/http`, their provider/projection/sampling/export. Technical timing/trace views are lost; ordinary request latency logs remain.
- **Removed metric delivery:** OTel ASP.NET/HTTP instruments/subscriptions and OTLP export, including subscription to `RecipeApi.Search`. **Retained independent instruments:** .NET `Meter` histograms `recipe.search.{response,lexical,semantic_attempt,reranking}.duration` and fallback counter in `ISearchTelemetry.cs`; without a separate listener they are not stored logs or exported records. No new listener/exporter is introduced.
- **Retained exception handling/report state:** framework diagnostics, console/Serilog errors, task `AiErrorDetail` and failure fields. Dedicated Sentrame exception reports disappear, while ordinary raw exception exposure remains.
- **Business/audit-like state remains:** recipe import reports, workflow execution/retry/failure records, database changes, maintenance receipts/backups, cooking/meal outcomes and SSE business publications. These are operational application state and behavior, not a disposable logging subsystem. No deletion or schema migration was made.
- **Build/test output remains:** Next/.NET/npm/Task/CI console and result artifacts. SDK/CLI telemetry opt-outs are unrelated privacy configuration. Historical `.task`, test results and archive evidence remain history, not active telemetry producers.

## Choices for a later decision

Recommended follow-up order, without changes now:

1. Remove or development-gate full recipe/URL browser debug output; retain short failure/event categories. Smallest noise/privacy improvement, but less immediate inspection detail.
2. Decide redaction and size limits for AI descriptions/output/body samples, URL query strings and raw exception details. This reduces sensitive-data retention while trading away some diagnosis detail; include persisted workflow error fields in that separate scope.
3. Decide whether request completion and per-task Information logs justify their volume, then adjust category levels rather than blanket-disable errors. Measure actual deployment rates first.
4. Confirm effective file/container retention and access, including seven-file rollover versus size/daemon limits. Existing file cleanup or deployment changes need explicit authorization.
5. Decide whether independent search meters should remain for local diagnostic listeners or be retired separately. They are not Sentrame collection and cost/utility differs from log volume.

These choices remain separate from the approved integration removal. Re-run this inventory if later implementation edits change ordinary logging; deployment volume, retention and external collection require separately authorized operational review.
