# Design

## Context

See [proposal](proposal.md) for motivation and [delta](specs/recipe-library/spec.md) for the bounded behavior. This extraction design resolves ambiguities between UI feedback, transport and persistence; it proposes no application design change. A54 permits drafting, A10 permits implementation-supported extraction and A34 defers runtime/database qualification.

## Goals / Non-Goals

**Goals:** keep the established fact/read/update and household-access owners; trace a single loaded-library-detail slice; map each scenario to inspected source and actual assertion coverage in BSL-recipe-library-012–014 of the [plan](../../../../docs/openspec-baseline-plan.md).

**Non-Goals:** error-recovery design, timer/race repair, contract alignment or runtime qualification. No implementation, migration or deployment is applicable.

## Decisions

1. **Extend recipe-library with six missing requirements/15 scenarios.** Main owns retrieval, displayed content and five-field partial updates, but does not own rating/notes controls or their update semantics yet. Add narrowly to that owner rather than creating a second persisted-fact capability. Recipe.Rating/Notes are columns on the recipe, not member-keyed facts; controller/service use ID/DTO without member binding. Reuse household-identity access/member context without inventing personal ownership. Discovery votes/consensus remain separately owned and untraced.
2. **Follow the connected slice through real integration boundaries.** Library page handleCardTap/detailRecipeId → mounted RecipeDetailSheet → existing getRecipe/DTO mapping → setRating/setNotes → rating handler or notes effect → updateRecipe → generated byId PATCH/UpdateRecipeDto/JSON writer → OpenAPI → RecipeController.Update → RecipeService.UpdateRecipe/ValidateRating → recipe assignments/EF SaveChangesAsync → index trigger attempt → ImageService.UpdateRecipeInfo/recipe store → DTO response discarded by adapter → existing local controls. This is source evidence; mocks do not establish a live path.
3. **Separate exact notes input from loaded-snapshot comparison.** Notes are controlled text with no trim/null normalization, blur handler or dedicated Save action. When notes differ from recipe.notes normalized to empty, an 800 ms effect timer dispatches `{notes}`. Cleanup cancels an unstarted timer on dependency change/unmount. The recipe snapshot is not updated by this submission, so equality to its original notes can suppress a restoring update after another dispatch. Document U38 rather than claim every edit is eventually saved. Closing clears the pending submission timer; it neither flushes nor proves cancellation of an already dispatched request. Reopening uses the existing detail GET, without a freshness/ordering guarantee.
4. **Separate local feedback from confirmed completion.** Rating changes locally before awaiting PATCH; clicking the same value submits 0. Notes dispatch with void updateRecipe, immediately set Saved, and reset a 2000 ms dismissal timer. The Saved timer has no unmount cleanup; typing again does not immediately clear Saved. Neither path catches rejection, displays a save error, rolls back or automatically retries; controls remain usable. Unlike excluded detail editing/discovery, no pending guard exists. Keep Saved/error/timer limitations non-normative (U38/U39); do not propose confirmed-success UI or recovery requirements. Successful completion leaves local values and the sheet intact, with no response application, GET or library callback.
5. **Bound persistence and side effects using established partial-update evidence.** Non-null rating is validated 0–3; non-null notes are assigned exactly, including empty/whitespace strings. Null/omission preserves either fact. Unrelated supplied fields are undefined in the adapter object and omitted by the installed serializer; the server's guards retain their content. UpdatedAt and search-sidecar pending state can change; indexing is attempted after save with trigger exceptions logged/caught. The recipe.info read/modify/write then applies supplied notes/rating and is awaited without that catch. Ordinary LocalRecipeStore serializes to disk, but this session does not execute it. No direct event publication is present in the inspected update method; no downstream/global event absence or delivery guarantee is inferred. Failure can follow database commit; no atomicity, ordering, idempotency or rollback claim follows.
6. **Record contract/test limits rather than repair them.** OpenAPI/generated PATCH expects a data object, while RecipeDetailResponseDto bypasses response wrapping; the adapter discards it. Validation supports out-of-range ArgumentException→400 and missing record→404, neither documented on this PATCH operation. Keep those HTTP claims non-normative (U36/U40), while retaining the agreed range and supported success path. The Search browser test asserts a notes body and open sheet against stateless substituted responses; validation tests assert the range but not the connected PATCH path. No inspected assertion establishes rating toggles, debounce duration, notes clearing, unrelated-field preservation, saved/error feedback, close/reopen persistence or overlapping requests.

## Risks / Trade-offs

- Premature Saved or optimistic selection can resemble durable success → explicitly distinguish local display from conditional successful persistence; withhold confirmed-save guarantees.
- Loaded-baseline comparisons and overlapping requests can lose intended final state → record precise source limits without repair or a concurrency-order requirement.
- Source-supported persistence exceeds test assertions → label source-only scenarios, InMemory/store/orchestrator substitutions and deferred PostgreSQL qualification separately.
- Completed extraction tasks can resemble acceptance → tasks cover documentation only; review, acceptance, main promotion and archival remain separate actions.

## Evidence and status (non-normative)

Documentation-only draft under A54 and BSL-recipe-library-012–014 in the [durable plan](../../../../docs/openspec-baseline-plan.md). Implementation-supported under A10; runtime browser/API/database checks not-run under A34. Not accepted, promoted or archived. Main recipe-library remains 25 requirements/48 scenarios and household-identity remains 36/92; the six prior changes remain active.

Reuse existing library requirements “Retrieve the selected library recipe for detail reading”, “Return persisted recipe detail for an available record” and “Apply supplied non-null recipe-detail update fields”. These additions cover only missing rating/notes facts and controls after successful detail loading. Household-identity retains “Gate protected page entry with household access”, “Apply member context after household access” and “Authenticate protected API requests independently”. The recipe rating is a shared recipe fact, distinct from member-specific discovery votes and household consensus; no personal ownership or new access rule is added.

U38–U40 retain unsupported/disputed guarantees outside the requirements. Notes compare with the loaded recipe snapshot, which is not advanced by notes submission: returning to that original text can skip a needed restoring PATCH after another text has been sent. The sheet shows Saved at dispatch, without awaiting success, and schedules its removal after 2000 ms; it is local feedback, not confirmed persistence. Neither handler implements save-error feedback, rollback or automatic request retry. Rating/notes controls remain usable pending. Pending notes submission timers are cleared on dependency change/unmount, but the Saved-removal timer has no unmount cleanup. No flush-on-close or cancellation of dispatched transport is established. Repeated or overlapping requests have no serialization or response-order guard.

The adapter discards PATCH responses and performs no completion GET or library refresh. The stored recipe update precedes a caught indexing-trigger attempt and an uncaught recipe.info write. No atomicity, rollback, idempotency, concurrency ordering, freshness, synchronization, indexing completion or event-delivery guarantee is inferred. PATCH response wrapping and undocumented errors remain U36/U40 discrepancies; no repair is included. Stored notes clearing below means replacement with an empty string on successful persistence, not conversion to null or confirmation by Saved.

Reuse BSL-recipe-library-001–011 and preserve U29–U37 non-normatively. BSL-018–025, U23–U28 and historical member-creation limitations remain unchanged and non-normative here. Historical BSL-015/U22 limitation retained:

> However, archived tasks claim completion while PostgreSQL qualification remains unresolved and later implementation/archive authorization is absent from the plan.

That sentence records the earlier review state. The user's report of later authorization remains recorded; its original reference is pending. It is not a recipe-library requirement, new lifecycle approval or runtime result.

Detail-field editing, discoverability changes, discovery voting/consensus, reporting/re-import, sharing, originals, hero generation, cooking mode, planning assignments, search ranking, capture, deletion/restore/purge, preference policy and demo/preview/deployment variants are excluded.
