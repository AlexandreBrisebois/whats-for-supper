# Extraction design

## Context

See [proposal](proposal.md) for motivation and scope. This is documentation extraction, not an application implementation design. A50 authorizes the loaded ordinary-household library → selected detail → GET → persisted returned content → close slice. BSL-recipe-library-004–006 in the [plan](../../../../docs/openspec-baseline-plan.md) records source identity, assertions and discrepancies.

## Goals / Non-Goals

**Goals:** Preserve the connected read boundary and representation changes; map every added requirement/scenario to actual source and assertion coverage; validate a bounded draft for review.

**Non-Goals:** No runtime changes, new tests, SQL qualification, data access or lifecycle actions. Adjacent controls identify ownership boundaries only. Instructions are not displayed inline; cooking mode stays excluded.

## Decisions

1. **Extend the existing owner with additions only.** Main library's loaded-item activation already requests detail. Begin at that requested sheet and describe its request ID, result and dismissal. Repeating list activation/eligibility or adding a separate detail capability would duplicate approved owners. Household-identity owns authentication/member context; member preferences owns browse-mode selection.
2. **Trace actual retrieval, not list policy.** BrowseAllStackPage.handleCardTap stores detailRecipeId; RecipeDetailSheet fetches getRecipe(recipeId) in an effect. recipes.ts calls generated byId.get; GET metadata and OpenAPI use RecipeDetailResponse. RecipeController.Detail uses SkipWrapping and RecipeService.GetRecipeDetail uses db.Recipes.FindAsync(id), then an import-report lookup, MapToDto and response-time UTC UpdatedAt. The ordinary fresh query has RecipeDbContext's non-deleted global filter, no readiness/discoverability/attribution restriction. FindAsync's tracked path makes a universal deletion claim unsafe. Alternative of copying the list predicate is rejected as unsupported; predicates remain explicit evidence, not new eligibility policy.
3. **Separate stored facts and representations.** Recipe entity/EF/schema map name, description, total_time, cuisine_type, meal_types and ingredients. MapToDto preserves scalar facts; DeserializeIngredients tolerates legacy JSON strings/objects and may return raw text, not guaranteed canonical quantities. ExtractRecipeInstructions reads raw_metadata.recipeInstructions or returns null. Hero URL is derived from ID; sourceType is derived; neither establishes asset availability or provenance qualification. recipes.ts defaults missing text to empty strings and ingredients to []; unwrapUntypedNode maps instructions. Local sheet state, not browseStackStore, holds detail.
4. **Describe only connected reading.** Read mode renders name, conditional description/cuisine/meal badges, formatted total time and ingredient rows; it does not render instructions. Editing's resolveMealTypes fallback to Supper is not a reading default. The image uses getImageUrl and an empty-reference placeholder; a nonempty broken URL has no delivery guarantee. Other DTO facts (category, vegetarian, creation/attribution, source metadata) do not become new read badges merely because the API returns them.
5. **Bound loading, errors and close.** New mount shows loading until success; caught failure logs and ends isLoading but null recipe keeps loading text. No error alert or Retry. Missing recipe payload throws in the adapter; missing server record maps to undocumented 404. Document U32–U34 and withhold normative failure recovery. Both Close buttons call onClose; library clears detailRecipeId and unmounts. Effect cleanup prevents a late result from updating that sheet but does not abort transport. Closing does not itself refetch the library or change its view/index/filter. No general scroll/focus restoration, Escape or browser-history promise is extracted.
6. **Use assertion evidence at its actual scope.** Controller detail test checks 200 and ID with auth disabled, InMemory persistence and substituted providers. Library unit tests stub detail; library browser tests route detail to a fixed recipe and omit required updatedAt. Component metadata tests mock getRecipe/localization/images/family settings. Search browser test supports shared name/time/close presentation with API mocks, not library persistence. No test is run here; no suite establishes full content completeness or successful image delivery.

## Risks / Trade-offs

- [Incomplete/error behavior] → U32–U34 stay non-normative under A12; no repairs or universal retry requirement.
- [FindAsync semantics versus list eligibility] → Record the exact query and tracked caveat; successful available-record response only is normative.
- [Substituted tests overstate integration] → Record each assertion and substitute in BSL-recipe-library-005/006; qualify as implementation-supported under A10, runtime not-run under A34.
- [Historical drift or collateral edits] → Preserve BSL-015 exact sentence/caveat, BSL-018–025/U23–U31, main specs, active changes, staging and deletions; compare a per-file before manifest plus index bytes after work.

## Migration Plan

No deployment, migration or rollback is applicable. Draft only the delta; validate selected/all OpenSpec items and six documentation paths. Stop for review. Acceptance, promotion, archival and any successor extraction require separate authority.

Implementation-supported under A10; browser/API/database checks are not-run under A34. Not accepted, promoted or archived. Existing main recipe-library (nine requirements/18 scenarios) and household-identity (36/92) remain unchanged.

The main library requirement “Display successfully returned library items” already owns activation of the loaded recipe button. These additions start with its requested detail sheet. Household-identity retains page access, API authentication and member context; member preferences retains browse-mode policy. No attribution ownership or list eligibility is redefined. The detail query uses FindAsync by ID, with no IsReady, IsDiscoverable or AddedBy predicate. The ordinary database lookup uses the context's DeletedAt == null filter; an already tracked entity can be returned by FindAsync without another filtered query. No universal deletion exclusion or not-ready rejection requirement is inferred from list behavior.

U32–U34 record detail-specific limitations: missing records become server 404 although GET documents only 200; first-mount failures leave Loading recipe... with no error/retry UI; no inline instructions are rendered. Raw-metadata instructions are mapped through the response/adapter but their display is a cooking-mode boundary excluded here. Missing optional fields are not synthesized into complete recipe content. An image reference or mocked 200 does not prove successful image delivery. No freshness, synchronization, cancellation of transport or complete-content guarantee is made.

Reuse BSL-recipe-library-001–003 and preserve U29–U31 non-normatively. BSL-018–025, U23–U28 and historical member-creation limitations remain unchanged and non-normative here. Historical BSL-015/U22 limitation retained:
