### Preview is a read model, never preparation authority

Propose additive **GET `/api/recipes/{id}/ingredient-preview?targetServings=2|4|6`**, using existing household access and demo boundaries. Keep `/ingredient-projection` and its date/assigned guard contract unchanged. This avoids weakening occurrence guards or introducing fake dates into the current dated DTO. Reject unsupported/missing targets with 400 and unknown recipes with 404. Missing basis is a successful unresolved read with null factor, not an invented yield. Existing authorization failures remain unchanged.

Define a small `IngredientPreview` response: `recipeId`, positive-or-null `baseServings`, requested `targetServings`, finite-or-null `factor`, opaque recipe-input `version`, `status` using the existing scaled/partial/unresolved vocabulary, and existing ordered projection line shape. It carries no date, occurrence, serving-write version, editability or preparation token. Snapshot recipe input coherently and call `SupperIngredientProjection.Read(recipe, target)`; reuse source-coherence checks, intentional-unquantified handling, finite math and display formatting. Do not extract numbers from text in the PWA, add a client calculator, round package purchases or rewrite instruction quantities.

Local detail state is only the chosen preview target and request identity. Default is the original or dated projection; selecting 2/4/6 immediately starts a read and shows selected/busy state. Latest selection/recipe identity wins; a known recipe correction or projection invalidation retires old preview results. An error hides stale preview numbers and offers retry plus return to original/planned quantities. A quiet text action restores the canonical view. A day change, recipe change or detail dismissal resets the preview. Switching edit/original-review modes must not carry a temporary preview into saved or original evidence. No new browser persistence is needed.

Keep the selected supper date and planned/frozen count visible as saved facts even while previewing another number. For a prepared supper, the temporary projection is explicitly a preview of the current saved recipe; it is not a reconstruction or correction of its historical preparation snapshot. Cook never receives preview count/version. Existing original-instruction limitation feedback remains one concise note, not per-step warnings.

Missing basis: show **Set original yield** (proposed French **Indiquer le nombre de portions d’origine**) leading to the existing recipe editor focused on its servings field. Explain that this changes the saved recipe basis; it is not a saved Planner count. Existing recipe correction can recompute future grocery needs, so its ordinary consequences/recovery remain and must not be described as preview-only. Cancel/failure does not unlock a guessed preview. A saved correction invalidates/reloads current projections. Prepared portions and preparation metadata remain frozen under their existing owner. Do not add a separate yield wizard or infer yield from household size.

### Reuse Planner titles and resolve only missing contributors

Alex's normal-path premise is supported by source: Planner initializes each selected week, and `weekStore.init` installs its recipe-bearing days and grocery items from one schedule response. Ordinary supper recipe names are already available; the existing disclosure looks them up there. Use an explicit subscribed ID-to-name view of the loaded schedule rather than fetching every source again. Preserve contributor order and deduplicate IDs across rows/occurrences. Titles are metadata, not per-recipe quantity/completeness evidence.

Two source-backed exceptions prevent assuming complete title coverage. `SupperProjectionInputs.ReadWeekAsync` includes recipe-bearing entries from every meal slot, whereas `ScheduleService.ReadScheduleAsync` returns only slot-zero supper cards. A lunch-only recipe can therefore contribute an ingredient without appearing in Planner even after a successful load; existing other-meal PostgreSQL tests preserve this behavior. Separately, grocery entry and `grocery_updated` call `refreshGroceries`, which installs derived grocery data but deliberately does not replace schedule cards. Its latest contributors can differ from the loaded name index. A failed week load retains prior data, and stale/failed recomputation can retain an ID no longer in current cards. A title field would not fix incorrect week orientation or grocery freshness; those existing boundaries remain authoritative.

On disclosure expansion, show nonblank loaded names immediately. Resolve only IDs missing a usable name through the existing `getRecipe(id)` / **GET `/api/recipes/{id}`**, using the established client/auth boundary. No `recipeSources` field, new title endpoint, grocery DTO, schedule/SSE shape, backend enrichment or generated-model change is needed. Manual extras/no-ID rows make no request. Duplicate IDs share one in-flight read within the selected-week disclosure session, including across ingredient rows; successful resolved names can be reused for that session. No persistent/global cache is introduced. While unresolved, show quiet localized loading text; failed/not-found/blank-title results use the honest **Recipe title unavailable / Titre de recette indisponible** fallback rather than a numbered or invented title. A known ID retains its original-review link. A failed ID is not automatically retried in a loop; a later deliberate reopen can retry it with deduplication.

Capture the absolute selected week, household/demo session and current contributor membership for each resolution. A week change or session reset retires that resolution scope and its cache; a late result cannot install titles into another week/session. Within a week, reconcile against the latest contributor IDs when grocery data refreshes, ignore results for departed contributors and resolve newly missing IDs only while their disclosure is open. Cancel where supported; otherwise ignore retired results. Prefer current nonblank schedule names over cached detail names so a subsequent authoritative schedule read can show a rename. Do not claim titles are live-current before a relevant fresh read or replace optimistic Planner cards merely to refresh names. Keep disclosure focus/expanded state stable during resolution.

Trade-off: an exceptional missing contributor needs a small lazy detail read and an honest loading/error state. The benefit is no new backend contract or second metadata projection, and no added request for normal loaded sources. A response title map would avoid these exceptional reads but expands schedule/publication/client ownership; the requested UI does not require that stronger zero-extra-request guarantee. Missing titles remain recoverable without blocking groceries, clearing warnings or acknowledging checks.

Link text is the resolved title itself, with an accessible original-quantity-review description; do not repeat Review recipe before every source. Keep `reviewAmounts=true` and original-source access. This explicit review context suppresses automatic assignment targets/footer even if a background date recommendation finishes; it opens original quantities by default, and no preview replaces that evidence on arrival.

All recipe-derived rows with IDs get the compact book disclosure, including complete rows. This makes source discovery consistent; warnings no longer need to carry the entire navigation affordance. The book control has a 48 px hit area, ingredient-specific accessible name, `aria-expanded`/`aria-controls` and visible focus. Retain one expanded row if convenient; this does not create a persistent preference. The separate Tag retains changing-aisle meaning. Disclosure/source consultation never calls a grocery write or acknowledges prior unknown amounts.

Warning presentation remains visible when collapsed: incomplete numeric values are known subtotals; prior unknown checked amounts retain review feedback even when today's total is complete. If both apply, concise distinct text communicates each meaning. Keep list-level prior-check feedback and successful grocery-update explanation under their existing rules; do not add repeated generic Review recipe labels or obscure warnings in a tooltip/icon alone.

## State, Concurrency and Recovery

- Notes: preserve the 800 ms pause, one write per recipe, current-text/acknowledged-text distinction and tab-lifetime drafts. Initial reads cannot overwrite newer edits; close-time flush cannot declare failed text saved. Preserve error on reopen and explicit retry; localize existing close-time failure feedback. No new cross-device text merge or durable offline guarantee is introduced.
- Footer: planning and preview state remain separate. Retain captured absolute date/occurrence, guard tokens, pending/read failure, identical-target View plan, completed/voting Review plan, staged disposition, uncertain outcome and post-persistence refresh recovery. Never derive assignment/preparation arguments from preview DTOs.
- Portions: reuse the existing local draft, date-specific validation, session restoration, atomic batch/version guards and grocery freshness state. Joined control styling does not replace numeric input or broaden count bounds. A blank usual count remains null/unconfigured; explicit overrides survive. Save-and-continue proceeds after persistence acknowledgement, without waiting for grocery refresh; unknown persistence reconciles before replay/navigation. Keep editing preserves destination/draft; Discard changes uses the saved baseline.
- Grocery: source disclosure and missing-title read state are local UI state, scoped to the selected absolute week/session and current contributor IDs. Loaded names win; one in-flight existing recipe GET per missing ID serves duplicate rows. Week/session changes and departed contributors retire late results. `quantityComplete=false` and `checkReviewReason=prior_amount_unknown` remain independent. Only existing explicit positive-check mutation can acknowledge the prior marker. A GET, expansion, title lookup or recipe visit cannot clear it; concurrent checks keep their existing coordinator rules.

## Persistence and Side Effects

Preview and existing recipe GET title resolution are reads: no calendar/default/override/recipe/preparation/grocery writes, workflow enqueue or side-effectful snapshot materialization. Add integration assertions over saved rows, grocery check state and refresh jobs before/after repeated preview reads; grocery disclosure acceptance must also show only permitted existing reads. Yield correction, note writes and Planner Done retain their existing separate mutation boundaries and post-commit recovery; avoid presenting them as part of the preview read.

## Compatibility, Rollout and Reversal

The ingredient-preview contract addition is additive. Retain old dated projection request/response semantics and recipeIds, absent-field compatibility, original evidence and prepared metadata. For the preview slice, regenerate Kiota and synchronize real API and stateful mock handlers/builders in the same slice. Grocery source resolution uses existing GET recipe and schedule/SSE contracts unchanged; its mock acceptance covers those existing handlers and evolving contributor state without new payload fields. No migration or new feature flag is proposed. UI reversal can remove the new presentation/preview consumer while leaving the additive preview read unused; it must not reset saved notes, portions, prepared history or groceries. Separate later implementation/deployment approval from artifact readiness. DV deployment and device review occur only after that authorized implementation and its required checks.
