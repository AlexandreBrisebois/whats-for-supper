# Design

## Context and Existing Ownership

- **Startup migration vs. offline CLI operator**: `RecipeStartupMigrator.MigrateAsync` (`api/src/RecipeApi/Services/RecipeStartupMigrator.cs`, invoked in `Program.cs` before `app.RunAsync()`) upgrades every non-placeholder recipe lacking `CanonicalContent` or `ContentSchemaVersion == 2` in a single transaction and recomputes affected planner weeks. Meanwhile, `Program.cs` still intercepts `args[0] == "--canonical-migration"` to invoke `CanonicalRecipeMigrationOperator.RunAsync` (`CanonicalRecipeMigrationOperator.cs`), backed by unreferenced offline manifest/execution/week-rebuild partials (`CanonicalRecipeContentStore.MigrationExecution.cs`, `MigrationInventory.cs`, `MigrationAdmission.cs`, `GroceryRecomputeService.Migration.cs`, `GroceryRowState.Migration.cs`). Separately, `CanonicalRecipeMigrationReceipt` (`CanonicalRecipeMigrationReceipt.cs`, `CanonicalRecipeMigrationReceipt.Presentation.cs`) and `CanonicalRecipeMigrationManifest` are still referenced by live vocabulary inventory and presentation-epoch owners (`FoodVocabularyInventoryQualification.cs`, `FoodVocabularyStore.Presentation.cs`, `GroceryRowState.Receipt.cs`).
- **Ingredient projection vs. source-capture ingestion**: `SupperIngredientProjection.Read` (`SupperIngredientProjection.cs`) branches on `CanonicalRecipeContentStore.Read(recipe)` (`ReadCanonical`), but retains a 55-line V1 fallback (`ScaleAmount`, `BindSupplies`, `ObserveBoundLegacy`, `ReadQualifiedSource`, `IntentionallyUnquantified`, `Metadata`, `Text`, `Number`, `NumericToken`) that projects legacy `recipe.Ingredients` strings and `recipe.RawMetadata.supply`. Four live read/prepare owners call `SupperIngredientProjection.Read`: `IngredientProjectionService` (`/ingredient-preview` and `/ingredient-projection`), `SupperProjectionInputs.ReadWeekAsync` (`GroceryRecomputeService`), and `ScheduleService.PrepareSupperAsync`. A fifth internal caller, `CanonicalRecipeContentStore.ConvertLines` (`CanonicalRecipeContentStore.cs:282`), calls `SupperIngredientProjection.Read(recipe, null)` on newly extracted JSON-LD (`PrepareFreshSource` / `PrepareReviewedSource` during URL, photo, and PDF capture) and during `ConvertAsync` / `ValidateOriginalOperation` (`Kind == "convert"`). In addition, ~20 pre-v2 supper and grocery test files in `RecipeApi.Tests` still seed `new Recipe { Ingredients = ..., RawMetadata = ... }` directly into `RecipeDbContext` without `CanonicalContent` because `TestWebApplicationFactory` does not run `RecipeStartupMigrator` on mid-test `db.Recipes.Add(...)` calls.
- **One-time V1 attestation and transition helpers**: Twenty-two service files (`CanonicalRecipeContentStore.Attestation.cs`, `V1ExactSourceAdmission*.cs`, `V1RecoveryHistoryContext.cs`, `V1MigrationSource.cs`, `V1SourceCoveragePolicy.cs`, `V1MigrationPrewritePolicy.cs`, `V1AuthorityTransition*.cs`, `V1AuthoritySuccessorPolicy.cs`, `RecoverySnapshotService.V1*.cs`) plus optional attestation/transition parameters on `FoodVocabularyInventoryQualification`, `FoodVocabularyStore`, `RecoverySnapshotService.Vocabulary*`, `CanonicalRecipeContentStore.MigrationPreparation`, and `RecoveryBoundary.Maintenance` exist solely for the completed 46-receipt V1 attestation chain and are invoked only via reflection in `V1*Tests`. General operation-history validation in `CanonicalRecipeContentStore.History.cs` (`ValidateOriginalOperation`) remains used by live recovery/workflow obligation checks (`CurrentRecoveryHouseholdState.Obligations.cs`).

## Decisions and Tradeoffs

1. **Fail-closed canonical v2 requirement in `SupperIngredientProjection.Read` with empty-placeholder support**
   - **Decision**: `SupperIngredientProjection.Read(recipe, target)` delegates exclusively to `ReadCanonical` when `CanonicalRecipeContentStore.Read(recipe)` returns `ContentSchemaVersion == 2` (throwing `InvalidDataException` on unsupported schema versions). When `CanonicalContent` is `null`, it returns `[]` only if the recipe also has no legacy ingredient strings or raw metadata (`RecipeService.DeserializeIngredients(recipe.Ingredients).Count == 0 && string.IsNullOrWhiteSpace(recipe.RawMetadata)`), such as an unready capture placeholder; otherwise it throws `InvalidDataException`.
   - **Alternative & Tradeoff**: Silently returning `[]` for any `CanonicalContent == null` row would mask unmigrated V1 fixtures or corrupted rows as empty grocery lists. Failing closed on populated non-canonical rows enforces structured v2 authority and immediately surfaces legacy test fixtures while keeping unready capture placeholders safe.

2. **Keep JSON-LD `supply` binding private to `CanonicalRecipeContentStore.ConvertLines`**
   - **Decision**: Move the unscaled `recipeIngredient`-to-`rawMetadata.supply` binding helper out of `SupperIngredientProjection` into private static helpers inside `CanonicalRecipeContentStore` used solely by `ConvertLines` (`PrepareFreshSource`, `ConvertAsync`, and retained `convert` operation verification).
   - **Alternative & Tradeoff**: Replacing `ConvertLines` with `RecipeStartupMigrator`'s regex parser would alter fresh URL/photo/PDF capture conversion and break byte-exact replay verification in `ValidateOriginalOperation` / `ValidateOriginalOperationV2`. Isolating the exact ingestion binder inside `CanonicalRecipeContentStore` removes live V1 projection fallback without changing capture or operation-history invariants.

3. **Preserve persisted v2 fingerprint and version hashes; keep OpenAPI wire schema unchanged**
   - **Decision**: Remove `GroceryRecordedNumberToken` from `IngredientProjectionLineDto`, but retain `GroceryRecordedNumberToken = (string?)null` inside `GroceryRecomputeService`'s anonymous `InputFingerprint` payload and leave `SupperProjectionInputs.IngredientVersion` unchanged. Keep `specs/openapi.yaml` (`IngredientProjectionLine.issues`), generated Kiota client, and `pwa/e2e/mock-api.ts` untouched.
   - **Alternative & Tradeoff**: Dropping the `null` property from the serialized `InputFingerprint` object would change SHA-256 digests in `weekly_plans.grocery_demand_evidence` for existing v2 households and trigger spurious check-baseline mismatches. Retaining the exact canonical hash shape and wire enum avoids unnecessary household state churn and out-of-scope frontend/contract edits.

4. **Retire offline operator and V1 attestation stack while preserving historical receipt readers and handoff links**
   - **Decision**: Delete `CanonicalRecipeMigrationOperator`, `--canonical-migration` in `Program.cs`, the five dead offline migration partials (`MigrationExecution`, `MigrationInventory`, `MigrationAdmission`, `GroceryRecomputeService.Migration`, `GroceryRowState.Migration`), and all 22 V1 attestation/continuation/transition files plus their optional parameters in vocabulary/recovery services, while keeping `CanonicalRecipeMigrationReceipt` (and `CanonicalRecipeMigrationManifest` helpers it calls) for `FoodVocabularyInventoryQualification` and `FoodVocabularyStore.Presentation`, keeping `CanonicalRecipeContentStore.History.cs`, and keeping `docs/handoffs/dependable-portions-next-slice/` files referenced by `HANDOVER.md`.

## First Observable Slice

Retire V1 string-ingredient fallbacks in `SupperIngredientProjection` first: add unit and PostgreSQL HTTP tests verifying structured v2 scaling, empty unready placeholder handling, and fail-closed rejection of populated V1 recipes across `SupperIngredientProjection.Read`, `GET /api/recipes/{id}/ingredient-preview`, `GET /api/recipes/{id}/ingredient-projection`, and `GroceryRecomputeService`; localize `ConvertLines` ingestion binding in `CanonicalRecipeContentStore`; and migrate legacy-seeded supper/grocery test fixtures to structured v2 `CanonicalRecipeContent`. Subsequent slices independently remove `CanonicalRecipeMigrationOperator` (and its dead offline partials) and the obsolete V1 attestation/transition helper stack.

## Persistence and Side Effects

No database schema migrations, startup data writes, or recovery archive format changes are introduced. Existing v2 `recipes.canonical_content`, `weekly_plans.grocery_demand_evidence` fingerprints, `calendar_events` preparation versions, current snapshot formats (v3 household / v4 demo), and retained `canonical-recipe-migration-receipt-v1` maintenance records remain fully compatible.

## Compatibility, Rollout and Reversal

`RecipeStartupMigrator` already guarantees all household recipes are upgraded to `ContentSchemaVersion == 2` before HTTP requests or background workers execute. Retiring `--canonical-migration` removes only an unscheduled manual CLI flag for disposable database copies. Reversal is a clean code revert requiring no data migration.
