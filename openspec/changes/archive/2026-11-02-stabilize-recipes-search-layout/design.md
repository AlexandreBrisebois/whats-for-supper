# Design

## Context and Existing Ownership

`pwa/src/app/(app)/recipes/RecipesExperience.tsx` owns toolbar order, disclosure, planner banner and both result views. Its toolbar uses `justify-end`: local rendered measurements put Search at x=64.98 CSS px with All and x=14.59 with Discovery at 393×852, a 50.39 px shift. The root has `height: calc(100dvh - 7.25rem - safe-area-insets)` and the list has its own scroll container. `pwa/src/components/common/Layout.tsx` also reserves bottom padding, while `Navigation.tsx` fixes a content-dependent dock to the viewport bottom. At normal 393×852, the list scroller ends at y=728 and the dock begins at y=737.5; with enlarged text the fixed rem allowance diverges from the actual dock. The Android screenshots show perceived unused space and the tall dock, but do not reveal computed Android viewport geometry.

The planner banner follows Search controls and is 82 CSS px high in local 393×852 and 320×640 renders. An isolated 50 px compact-row experiment moved the first list card up 32 px. `AppRouteLayout` hides the shared `Header` on `/recipes`; its Recipes title is not visible, so there is no title slot to replace. Planner target parsing, Cancel-to-Planner, conditional calendar Retry, detail assignment and occupied-slot recovery already live in the unified controller and related planner owners. The `unify-recipe-browse-search` deltas own session and request state; `refine-recipes-visual-language` owns the current width and Search visual language.

## Decisions and Tradeoffs

1. **Pin Search within the toolbar.** Keep Search first in DOM and give that button the toolbar's left gutter and flexible space to its right. Let the remaining controls keep their existing order and wrap at their intrinsic sizes. This corrects scope-dependent movement without a fixed overlay, duplicated button or route change. At narrow widths the first row still starts with Search; no target shrinks below 48 CSS px.
2. **Use one dock boundary for Recipes.** Scope the correction to the Recipes shell. Replace its independent fixed `7.25rem` height and duplicated bottom reservation with a single effective visible bottom boundary derived from the rendered dock and visual viewport. The app shell should expose the dock's measured top/height to Recipes, updating for dock resize, browser `visualViewport` resize/scroll, window resize and text enlargement; use a stable first-render fallback and avoid an extra permanent gap. The list or stack flex region then fills to 0–8 CSS px above that boundary. If controls consume the available height, the controls and results must be scrollable as a coherent pane rather than forcing the inner scroller over the dock. Preserve the current list scroll ref and stack position when switching between fitting and overflow layouts. The alternative of shortening `7.25rem` by a constant would improve one device while leaving keyboard, safe-area and 200% cases brittle. Moving the shared dock into document flow across every route would broaden this change.
3. **Replace only the planner banner's presentation.** Keep the existing `planning-mode-banner` and `planning-mode-cancel` semantics, but render a compact Solar Earth context row above the toolbar. Search field and Filters continue to open directly below the toolbar as the unified flow requires. Use a localized “Choosing for {{day}}” heading with the current numeric fallback, existing Cancel-to-Planner button and conditional Retry. Target 48–52 CSS px for a one-line ordinary phone row; allow French and 200% text to grow or wrap. Separating it from Filters keeps the target identifiable when filter count or disclosure changes. A new Change-day action is excluded because the current action already cancels to Planner; enabling the shared Header would add height and require unrelated header behavior changes.
4. **Keep data and navigation untouched.** No API, mock response shape, ranking, persistence, member preference, Go-To, Discovery voting or planning assignment logic changes. The former `topPick` stays one ordinary result. The existing preview with 204 recipes is a later local verification target only after implementation approval and green checks.

## First Observable Slice

At 393×852, open `/recipes` with a selected member, measure Search's left edge, toggle All/Discovery, expand/hide Search and switch stack/list. A test first observes the 50.39 px shift; the toolbar change makes the left edge invariant within 1 CSS px while retaining button order, 48 px targets and focus. The seam is app route → shared Layout → `RecipesExperience` toolbar → Navigation. Browser route mocks remain at `pwa/e2e/mock-api.ts`; no backend seam changes.

## State, Concurrency and Recovery

Geometry changes must not drive collection changes. Search disclosure continues to preserve query, Similar, applied filters/preferences, scope, results, POST cursor, pending debounce/in-flight requests, list position and presentation; Explore keeps its separate GET page/history state. On viewport or keyboard resize, measure only layout and avoid remounting the collection. Planner context remains independent of disclosure and filter drafts. Cancel and calendar Retry retain their current actions; detail selection and occupied-slot recovery retain their existing request ordering and destination. A measurement unavailable on the first frame uses the current safe fallback until the dock is known, then reflows without clearing state or stealing focus.

## User Experience

The Search action is found at the same left position as scope and view change. The compact planner row says what day the recipe will fill without delaying the first card by a large alert-style block; its secondary Cancel and conditional Retry remain discoverable and keyboard reachable. The row uses the existing cream, warm terracotta and Outfit/Inter hierarchy without inventing a new surface system. Search field, filter count, active marker, ordinary Results heading, loaded/empty/error recovery, safe areas and reduced-motion behavior remain. At 320×640 with 200% text, a complete card cannot fit beside all enlarged controls and dock; intentional scrolling must reveal its image, title and action while keeping the dock clear. Actual Android Chrome measurement is required to distinguish browser chrome from a code-level bottom gap before claiming device acceptance.
