## Decisions and Tradeoffs

### 1. Repair alignment at the shared projection owner

Use one conservative, deterministic resolver inside the existing projection owner; no new library, AI read, persisted repair job or UI-only scaling. Retain exact agreement between current ingredient strings and the retained source basis. Resolve each structured supply to a source line using verified line identity where available; for current legacy records use only unique normalized whole-name/token-boundary matches against that unchanged source. Normalization is limited to Unicode canonical form, case and whitespace, retaining accents and substantive words; no stemming, translation or synonyms. Build candidates for all lines/supplies before accepting any; only mutually unique one-to-one bindings qualify. Preserve order in output. No fuzzy similarity, substring without token boundaries, guessed ordinal, or multiplication of numbers parsed out of fallback text. Equal array lengths alone do not prove a binding. Ambiguous same-name duplicates remain unresolved.

Keep the structured amount/unit untouched and scale from it on every read. Omitted lines receive their own unresolved/unquantified status. Recognized to-taste/for-frying directions remain ordinary content. Bare sel/poivre without reliable amounts must not be silently relabeled numeric or complete; the shells fixture remains partial even though its seven reliable lines scale. Other line failures do not invalidate trusted bindings. A source edit invalidates old bindings; no normalization may hide substantive text edits.

This narrowly repairs the observed legacy shapes without rewriting saved recipes or requiring a reimport. A broader ingredient parser could recover more recipes but adds uncertainty and is excluded. Tests must include competing matches, duplicate names, reordered supplies, omitted middle ingredients, Unicode/French names, package sizes and unchanged originals. If the conservative rule cannot establish a binding, keep original text and report unresolved; do not expand matching heuristics merely to make a test green. Existing projection DTOs already express per-line status and partial totals, so no new preview endpoint/field is needed.

Shared consequences are intentional: previews, dated reads, cooking and recomputation must agree. Newly usable contributions may change a future grocery subtotal on normal recomputation; preserve check reset/prior-unknown policy. No GET triggers recomputation or persistent data repair. Existing projection versions include lines; corrected results receive a different semantic version. Audit stored pending/applied week freshness on activation through the existing reconciliation path so changed derivation is not labeled current against old totals.

### 2. Keep preview intent separate from read freshness

Store selection by recipe identity and deliberate target-context identity, not readAttempt. A routine schedule object replacement with unchanged date/occurrence/recipe/default semantics must not clear it. Resume or genuine source change can invalidate the cached response and re-read the same selected target; stale ingredients cannot be presented as fresh while loading. Keep request identity/version guards and retry separate from planning recovery. Deliberate Change day, recipe replacement and Original/Planned quantities reset preview as before. Do not stop listening to real invalidations to preserve selection.

### 3. One explicit/automatic usual owner

Settings owns configuration; Planner only edits date exceptions. Derive an automatic count from persisted FamilyMembers count, not selected identity, frontend roster cache or recipe yield. Four members means four default portions until a human chooses another total. A saved positive value is explicit even if equal to family size; do not infer provenance from numeric equality. Save null means deliberately return to automatic; omission means leave mode/value unchanged.

Reuse `GET/PUT /api/schedule/servings` for Settings default-only batches: capture current reference week/version and submit no date edits. Add required `defaultServingsSource: explicit | family` to the response contract; `defaultServings` becomes the effective nullable usual. For family source, positive value is current derived count; null means no available positive family count. Existing `GET /api/family` supplies Settings' roster context; no new setting key or grocery response field. Document sparse PUT null semantics and explicit-equal-to-current saves as source changes, not numeric no-ops. Update OpenAPI first, regenerate Kiota, then consumers and method-sensitive mocks.

Reuse a single effective-usual resolver at every current DefaultCount seam, including preparation, projection inputs, recovery/demo and save/version generation. A mode or effective automatic-count change participates in the portions baseline version. Explicit defaults need not conflict merely because the roster changes; automatic defaults must. Use the existing guarded serving-input transaction discipline to serialize membership mutations with portion/preparation writes; incorporate roster/count into the same coherent read rather than a second unguarded query. Do not copy family-size fallback into each consumer.

Membership add/delete in automatic mode snapshots/materializes applicable inherited future values and enlists affected saved weeks for existing quiet grocery refresh in the same committed change. Publish after persistence, reusing projection/SSE ownership and recovery. Explicit mode, overrides, past, Cooked, prepared and non-cooking protections remain. Empty roster resolves null, not one; roster read failure is retryable, not proof of zero. Settings' explicit value remains usable despite roster display failure. No habitual count travels when a recipe moves dates.

### 4. Quiet UI restoration with clear consequences

Use the historical Rating alignment and single Notes field as composition anchors. Keep current localized labels/pressed state, modern readable sizes, focus and 48 px targets. Use a subtle selected surface/emphasis without border boxes; avoid opacity that makes enabled labels appear disabled. Notes gets one visible Notes label/heading tied to its textarea, no enclosing card or repeated Family notes title. Its accessible region/shortcut can remain Family notes. Retain debounce, close flush, error retention, serialized newer text and retry; styling must not replace the store.

View Original uses warm cream translucent material, lower-right placement, rounded capsule and modest shadow/blur. Prefer dark charcoal on sufficiently dense warm material; tune opacity/scrim after actual light/dark photo contrast measurements. Do not blindly restore white20%/white text. Bright/missing images and hover/focus/pressed states must remain readable.

Remove native Serving details and its duplicate list. Show known original yield once as quiet context beside the portion controls. Returning to Original quantities uses the existing single ingredient list and original source access. Dated review can deliberately inspect original evidence without losing the saved date context; Planned quantities returns to it. Preserve warning feedback outside this switch. Unknown basis keeps Set original yield, an explicit saved correction with its existing grocery consequences, never an automatic family-based basis.

## State, Concurrency and Recovery

- Settings has loading, explicit, automatic-with-count, automatic-unavailable, dirty, saving, acknowledged, conflict and uncertain states. Never render a failed roster request as automatic 0 or overwrite a newer default with an old form. Invalid counts retain input. A default-only save and a date-batch save use the same version check. Changing only source explicit↔family is meaningful even if both resolve 4.
- Planner numeric reset clears only the date override in its draft. The button face is 4; accessible label identifies date, action and target. After reset, a quiet status can say Using usual 4 portions; this explains inheritance when the displayed number is unchanged. Done persists; Cancel discards. An unknown usual count has no fake numeric target. Existing dirty-exit primary/secondary/text hierarchy remains.
- Library dated footer: Plan for date and Change day form a row; Change day shows only ArrowRightLeft, with its localized accessible name and tooltip; Cook follows separately. Alex explicitly chose icon-only Change day to leave more room for the dated Plan label. Keep 48 px targets and adapt/wrap the row when constrained without shrinking the remaining labels. Planner source retains date/Cook/Plan another day. Busy/retry/conflict/recovery/edit/load/error/completed variants retain their owners and disabled rules.
- Grocery source review initially stays original, with a quiet Plan transition and Cook. Plan changes only local/navigation context into existing RecipesExperience target resolution. Fetch a fresh normal recommendation; never reinterpret the source shopping week as a saved target. Expose dated Plan only after checks, including same-recipe View plan, completed/voting Review plan and replacement/non-cooking confirmation. Preserve source-week return/navigation state, unsaved notes and original evidence. Transition is no write; assignment remains a separately activated guarded action. Nested cooking/capture review does not gain planning incidentally.
- Source disclosure resets with ingredient/week/session identity; collapsed Used in and links are absent from focus/accessibility tree. Reuse loaded names and lazy missing-name GET with existing deduplication/late-result protections. No title contract change.

## Persistence and Side Effects

No quantity metadata must be rewritten to qualify the legacy example; derive safe bindings read-only. Avoid schema changes solely for alignment. For usual migration, preserve positive existing family setting values as explicit; missing/null becomes family mode by interpretation, with the new source serialized on reads. Retain the existing stored positive-or-null representation rather than add a mode marker: positive means explicit and null/missing means automatic. Recovery/export/demo must roundtrip that choice, not the currently derived count. Capture pre-upgrade original-basis historical/prepared context; never backfill family size into those null snapshots. Current/future inherited dates adopt the new automatic rule and refresh saved affected grocery weeks through existing durable work, not a read side effect. Source transition, disclosure and preview do no persistence.

## Compatibility, Rollout and Reversal

Review and apply against the effective unarchived baseline in order; do not edit predecessor completion evidence or silently sync deltas. New API response source and changed null semantics require coordinated API/client/mock deployment, not a staggered old-client promise. No archived/main specs are synchronized during planning.

Migration matrix: positive 7 → explicit 7; positive4 with family4→explicit 4; null/missing with family 4 → family 4 for editable future only; null with zero → family unavailable/original; overrides/prepared/history→unchanged. Test legacy positive/null recovery exports and restores, automatic mode membership transitions and demo isolation. Default provenance cannot be recovered from timestamps or count equality; preserve every positive value rather than guess.

Derived quantity correction is reversible by application rollback because raw metadata is untouched. Default behavior rollback must retain explicit settings, date overrides and original/prepared snapshots; any already recomputed grocery checks require the existing backup/recovery procedure, not an assertion that rolling images back rewinds data. Implementation/deployment approval and an ordinary local DV backup remain future work; no deployment occurs in this planning task.

## User Experience

High signal-to-noise: one recipe ingredient list, one Notes field, three calm rating choices, one date target with a separate change action. Settings uses Usual portions / Portions habituelles and an explicit Use family size / Utiliser le nombre de membres option. Automatic context can read4 family members /4 membres de la famille; do not equate that with attendance. Planner reset visually shows4, with localized accessible name Use usual 4 portions for Sunday / Utiliser les 4 portions habituelles pour dimanche. Used in / Utilisé dans appears only after source expansion. Plan / Planifier in grocery review denotes the transition; the following dated action states its target. Final copy must use the locale's date/plural utilities rather than concatenating English.

Rendered acceptance: matched real food photos (light/dark),320/390px phones, short-height landscape and tablet, EN/FR, ordinary then long text,200% text, keyboard and reduced motion. Check equal borderless rating spacing, obvious selected state, single-field Notes with focused/empty/error content, warm hero capsule, adjacent Plan/Change day, editor/photo/count/reset alignment and source disclosure. Measure actual 4.5:1 text/3:1 meaningful indicator contrast; a large hit target need not be a large visible border. Notes must scroll above keyboard/footer/safe area; Tab/focus return, expanded semantics and live save/error feedback need interaction checks. Physical phone/assistive-technology validation must be reported separately from browser emulation on the eventual approved DV deployment.

## Risks and Deferrable Questions

No product decision remains blocked: Alex confirmed explicit usual survives membership changes and clarified the numeric button belongs in Planner. The conservative legacy match rejects ambiguous amounts intentionally; do not promise complete previews for all 12 sampled recipes, ten of which lack a numeric original yield. Final capsule opacity and bilingual microcopy are bounded design refinements subject to the acceptance matrix, not permission to change behavior. If source inspection during implementation reveals a required new persistence/contract boundary beyond this design, report it before expanding scope.
