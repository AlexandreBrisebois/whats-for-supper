# Design

## Context and Existing Ownership

Source inspection across `api/`, `pwa/`, `specs/openapi.yaml`, and `scripts/ci/` established the following verified ownership and call-graph facts:

- **Offline migration scaffolding (dead — zero live production callers)**:
  - `api/src/RecipeApi/Services/StructuredRecipeMigrationManifest.cs` has only one remaining production reference: a one-line `StructuredRecipeMigrationManifest.Require(condition, message)` call in `api/src/RecipeApi/Services/GroceryRowState.Receipt.cs`.
  - `api/src/RecipeApi/Services/StructuredRecipeMigrationReceipt.cs` and `api/src/RecipeApi/Services/StructuredRecipeMigrationReceipt.Presentation.cs` define `CommandType = "canonical-recipe-migration-receipt-v1"`. The offline migration operator that wrote those receipts was already removed (verified by `api/src/RecipeApi.Tests/Services/BilingualStartupMigrationTests.cs`). Only two passive reader hooks remain: `FoodVocabularyStore.Presentation.cs` (`BindPresentationEpochAsync`, which queries `maintenance_commands` and `maintenance_command_lifecycle_records` and returns `prior` unchanged when zero receipt rows exist) and `FoodVocabularyInventoryQualification.cs` (two `CommandType == StructuredRecipeMigrationReceipt.CommandType` branches).
  - `api/src/RecipeApi/Services/StructuredRecipeContentStore.MigrationPreparation.cs` and `ConvertAsync` / `ConvertCoreAsync` in `api/src/RecipeApi/Services/StructuredRecipeContentStore.cs` have **zero production callers**. Legacy recipes are now migrated automatically at startup by `RecipeStartupMigrator` (`api/src/RecipeApi/Program.cs`). Seven test files still call `ConvertAsync` to seed structured recipes or V2 operation rows before testing editing, recovery, demo capture, or physical retirement.
  - V1 `Record(...)` (`StructuredRecipeContentStore.cs`) and `CaptureOriginal(...)` (`StructuredRecipeContentStore.History.cs`) have **zero callers** anywhere in production or tests.
- **Retained read-only history validation (active — do NOT delete)**:
  - `StructuredRecipeContentStore.ValidateOriginalOperation` (V1) and `ValidateOriginalOperationV2` (`request.Kind == "convert"` branch) are actively exercised by `ReadValidatedRetainedResult`, `VocabularyReferences`, `Replay`, `RecipePhysicalLifecycle.VocabularyReferences`, and SHA-256 verified golden fixtures (`api/src/RecipeApi.Tests/Fixtures/canonical-old-authority-v1-v3.json`, `physical-retirement-old-v1.json`, `physical-retirement-core-v1.json`) in `FoodVocabularyTests.cs` and `FoodVocabularyReferenceInventoryTests.cs`.
- **PostgreSQL schema & recovery snapshots**:
  - `Recipe.CanonicalContent` already maps explicitly via `[Column("canonical_content", TypeName = "jsonb")]` (`api/src/RecipeApi/Models/Recipe.cs`), and `StructuredRecipeOperation` already maps via `[Table("canonical_recipe_operations")]` (`api/src/RecipeApi/Models/StructuredRecipeOperation.cs`).
  - `RecoverySnapshotService.SchemaAsync` hashes `information_schema.columns` (`table_name`, `column_name`, types, defaults) and `pg_constraint` into `manifest.Schema`. Exact snapshots (v1/v3) and demo baselines (v2/v4) also validate `tables/canonical_recipe_operations.json`, `tables/recipes.json` column sets, and `dispositions.json` entries against the live database schema.
- **Persisted JSONB history records protected by SHA-256 hashes**:
  - `RecipePublicationFields.CanonicalContent` is embedded inside `canonical_recipe_operations.original_request` (`OriginalRequestV2.Baseline` + `BaselineHash`) with `UnmappedMemberHandling = Disallow`.
  - `WorkflowLifecycle.RetainedPayload.CanonicalOperations` is serialized into `workflow_lifecycle_records.payload` (`"canonicalOperations"`) with `PayloadHash` and strict member checks (`RequireMembers("canonicalOperations", ...)`).
  - `WorkflowProcessorHistory.Outcome.CanonicalOperations` is serialized into `workflow_processor_attempts.outcome` (`"canonicalOperations"`) with `OutcomeHash` and `UnmappedMemberHandling = Disallow`.
  - `RecipePhysicalLifecycle.RecipeFacts(db, recipe)` derives JSON keys dynamically from EF property names via `JsonNamingPolicy.CamelCase.ConvertName(x.Metadata.Name)`, and `RetainedRecipe.CanonicalContent` + `PhysicalHistory.CanonicalOperations` + `RetainedPayload.CanonicalOperations` are serialized into `recipe_physical_deletions.payload` with `RecipeHash`, `HistoryHash`, and `PayloadHash` (verified against immutable v1 fixtures).
  - `FoodVocabularyRecipeObservation.CanonicalContent` and `HistoryOwners` (`"canonical-operation"`) are serialized into `vocabulary/history-observations.json` with per-row `RawSha256` and `ContextId` hashes.
- **PWA editor audit (`RecipeDetailSheet.tsx`, `editor-draft.ts`, `instruction-draft.ts`)**:
  - Audited for unreachable pre-cutover/gated branches: no feature-flag gate exists. `canonicalEditing` is derived purely from `editorSession?.baseline.canonical ?? recipe?.contentSchemaVersion === 2`.
  - The `contentSchemaVersion !== 2` (legacy) branch remains live and tested because OpenAPI `RecipeDto.contentSchemaVersion` is nullable, in-flight/unmigrated captures and `pwa/src/testing/builders.ts` default to `contentSchemaVersion: null`, `RecipeService.UpdateRecipe` still accepts legacy updates when `StructuredContent` is null, and `RecipeDetailSheet.refinement.test.tsx` + `editor-draft.test.ts` + `instruction-draft.test.ts` explicitly test recovering a legacy `sessionStorage` draft across a format upgrade.
- **OpenAPI & CI suite inventory**:
  - `specs/openapi.yaml` has stale pre-cutover prose on `UpdateRecipeDto` (`At canonical cutover...`, `Canonical writes remain gated...`) and `POST /api/recipes/{id}/originals` (`Canonical owners remain fenced until activation` — verified false in `RecipeService.AddOriginalImageAsync`, which never fences structured recipes).
  - `scripts/ci/e2e-suites.cjs` and `scripts/ci/e2e-suites.test.cjs` register `'canonical-package'` and must stay synchronized when `pwa/e2e/canonical-package.spec.ts` is renamed to `pwa/e2e/structured-package.spec.ts`.

## Decisions and Tradeoffs

### 1. Database identifiers: preserve physical PostgreSQL names via EF Core mappings

- **Decision**: Keep physical PostgreSQL identifiers (`recipes.canonical_content`, `canonical_recipe_operations`, `guard_canonical_recipe_content()`, and trigger `canonical_recipe_content_guard`) unchanged, mapped explicitly via `[Column("canonical_content", TypeName = "jsonb")]` on `Recipe.StructuredContent` and `[Table("canonical_recipe_operations")]` on `StructuredRecipeOperation`. Clean up stale pre-cutover comments only in `api/database/schema.sql` and `api/database/compatibility.sql` (replacing "Dormant canonical owner: no automatic conversion or public write activation" / "Canonical conversion remains an explicit gated operation").
- **Credible alternative considered**: Rename the column, table, trigger function, and trigger in `api/database/compatibility.sql` (`ALTER TABLE ... RENAME ...` guarded by `information_schema` checks) and `api/database/schema.sql`, and update raw SQL + `RecoverySnapshotService` table/column lists.
- **Tradeoff rationale**:
  - Renaming physical PostgreSQL identifiers changes `RecoverySnapshotService.SchemaAsync(...)` and `manifest.Tables` / `dispositions.json`. Every existing exact backup snapshot (v1/v3) and demo baseline (v2/v4) captured before the rename would fail restore validation unless we either forced operators to recapture all snapshots/demo baselines or bumped snapshot formats to v5/v6 and built a cross-version SQL/JSON schema-translation layer.
  - Furthermore, `ALTER TABLE recipes RENAME COLUMN` and `ALTER TABLE canonical_recipe_operations RENAME TO` acquire `ACCESS EXCLUSIVE` locks during migration and expand `sqldef` reconciliation surface for zero runtime benefit.
  - Preserving physical identifiers with EF Core `[Column]`/`[Table]` mappings keeps deployments zero-downtime, preserves 100% compatibility with all existing v1–v4 snapshots and demo baselines, and achieves clean "structured" naming across all C# application code.

### 2. Persisted JSONB snapshot wire keys: rename C# properties, pin JSON property names explicitly

- **Decision**: Rename C# properties cleanly (`Recipe.StructuredContent`, `RecipePublicationFields.StructuredContent`, `FoodVocabularyRecipeObservation.StructuredContent`, `FoodVocabularyInventoryFacts.StructuredOperations`, `WorkflowLifecycle.RetainedPayload.StructuredOperations`, `WorkflowProcessorHistory.Outcome.StructuredOperations`, `RecipePhysicalLifecycle.RetainedRecipe.StructuredContent`, `PhysicalHistory.StructuredOperations`, `RetainedPayload.StructuredOperations`), while keeping persisted JSONB wire names explicitly pinned for hash-verified records:
  - Add `[property: JsonPropertyName("canonicalContent")]` on `RecipePublicationFields.StructuredContent`, `RecipePhysicalLifecycle.RetainedRecipe.StructuredContent`, and `FoodVocabularyRecipeObservation.StructuredContent`.
  - Add `[property: JsonPropertyName("canonicalOperations")]` on `WorkflowLifecycle.RetainedPayload.StructuredOperations`, `WorkflowProcessorHistory.Outcome.StructuredOperations`, `RecipePhysicalLifecycle.PhysicalHistory.StructuredOperations`, and `RecipePhysicalLifecycle.RetainedPayload.StructuredOperations` (and retain anonymous serializer property name `canonicalOperations` in `WorkflowLifecycle.RetainAsync` and `RecipePhysicalLifecycle.DeleteAsync` / `VocabularyReferences`).
  - In `RecipePhysicalLifecycle.RecipeFacts(db, recipe)`, map EF property `nameof(Recipe.StructuredContent)` explicitly to JSON key `"canonicalContent"` (rather than relying on `JsonNamingPolicy.CamelCase.ConvertName(x.Metadata.Name)`, which would otherwise emit `"structuredContent"` and break `RetainedRecipe` deserialization and `RecipeHash` stability against existing rows and golden v1 fixtures).
  - Keep `"canonical-operation"` as the serialized `OwnerKind` string in `FoodVocabularyInventoryQualification.cs` and `FoodVocabularyInventory.Serialization.cs` (with an inline comment explaining it is a persisted snapshot wire identifier).
- **Credible alternative considered**: Change persisted JSON keys to `"structuredContent"`, `"structuredOperations"`, and `"structured-operation"` and bump retained-record schema versions across 5 independent tables/artifacts (`workflow_lifecycle_records`, `workflow_processor_attempts`, `recipe_physical_deletions`, `canonical_recipe_operations`, `vocabulary/history-observations.json`) with dual-key readers.
- **Tradeoff rationale**: Dual-version readers across five hash-verified persistence formats add substantial complexity and risk subtle SHA-256 verification bugs for zero user-facing value. Explicit `[JsonPropertyName]` attributes isolate the persisted wire format cleanly from C# naming while keeping all golden SHA-256 fixtures and live retained DB rows valid untouched.

### 3. Dead migration/conversion removal vs retained read-only history validation

- **Decision**:
  - Delete `StructuredRecipeMigrationManifest.cs`, `StructuredRecipeMigrationReceipt.cs`, `StructuredRecipeMigrationReceipt.Presentation.cs`, and `StructuredRecipeContentStore.MigrationPreparation.cs`.
  - Inline a private one-line `Require(bool valid, string message)` helper in `api/src/RecipeApi/Services/GroceryRowState.Receipt.cs`.
  - Remove the `StructuredRecipeMigrationReceipt.BindPresentationEpochAsync` call from `FoodVocabularyStore.Presentation.cs` and the `CommandType == StructuredRecipeMigrationReceipt.CommandType` branches from `FoodVocabularyInventoryQualification.cs`.
  - Delete `ConvertAsync`, `ConvertCoreAsync`, and unused V1 `Record(...)` from `StructuredRecipeContentStore.cs`, and unused V1 `CaptureOriginal(...)` from `StructuredRecipeContentStore.History.cs`.
  - **Retain** pure read-only `ValidateOriginalOperation` (V1) in `StructuredRecipeContentStore.History.cs` and the `request.Kind == "convert"` read-only validation branch in `StructuredRecipeContentStore.Vocabulary.cs` (along with the private pure helpers `PrepareEdit`, `ConvertLines`, `ReadSourceSupplyObservations`, `BindSupplies`, `ObserveBoundSourceQuantity`, `ReadQualifiedSource` they call) solely so existing retained `canonical_recipe_operations` / `recipe_physical_deletions` rows and golden fixtures continue to validate cleanly.
  - Delete `api/src/RecipeApi.Tests/Services/CanonicalRecipeMigrationManifestTests.cs`. In `api/src/RecipeApi.Tests/Services/CanonicalRecipeMigrationExecutionTests.cs` (renamed to `RecipeStartupMigrationExecutionTests.cs`), remove reflection-only tests for deleted `PrepareMigrationConversionAsync`/`ConvertCoreAsync`/`StructuredRecipeMigrationReceipt`, keep `StartupMigrator_UpgradesDatabaseRowsWithoutUnwrappingDiskWrappersOrDeletingPublications`, and retain `MaintenanceCommand` prune/retention closure coverage using an ordinary maintenance command (`PruneWorkflows`) validated directly through `MaintenanceCommandLifecycle.ReadValidatedRetainedCommand`.
  - Update `BilingualStartupMigrationTests.RecipeApiAssembly_DoesNotExposeOfflineMigrationOperatorOrExecutionMethods` to also assert `StructuredRecipeMigrationManifest`, `StructuredRecipeMigrationReceipt`, `ConvertAsync`, `ConvertCoreAsync`, and `PrepareMigrationConversionAsync` are absent from the assembly.
  - Migrate the 7 integration/unit test files that previously called `store.ConvertAsync(...)` (`CanonicalIngredientEditPostgresTests`, `CanonicalIngredientConversionPostgresTests`, `CanonicalIngredientDuplicateInputTests`, `CanonicalRecipePersistencePostgresTests`, `DemoShowcaseLoopPostgresTests.VocabularyCompatibility`, `OnlineRecoveryPostgresTests.Canonical`, `FoodVocabularyReferenceInventoryTests`) to seed structured v2 recipes via active production paths (`RecipeStartupMigrator` or `StructuredRecipeContentStore.FromSchemaOrg` + `FoodMappingQualification.Prepare`) and exercise V2 operation recording/replay/snapshot persistence via `store.EditAsync(...)`. Retire only the tests in `CanonicalRecipePersistencePostgresTests` whose sole subject was the deleted `ConvertAsync` method (preserving `EditAsync` persistence, replay, conflict, and DB trigger guard tests).
- **Pre-deletion verification**: Confirm zero live production callers in `api/src/RecipeApi/` and zero retained `canonical-recipe-migration-receipt-v1` production rows before removing receipt hooks.

### 4. PWA legacy branches, symbol renames, and transient draft compatibility

- **Decision**:
  - Retain the `contentSchemaVersion === 2` vs legacy (`null`) branches in `RecipeDetailSheet.tsx`, `editor-draft.ts`, and `instruction-draft.ts` because they remain live for unmigrated/in-flight captures, mock builders, and legacy-to-structured draft recovery.
  - Rename internal symbols: `canonicalDrafts` → `ingredientDrafts`, `canonicalEditing` → `structuredEditing`, `draftCanonical` → `draftStructured`, `EditorBaseline.canonical` → `structured`, `canonicalInstructionInput` → `structuredInstructionInput`, and `canonical: boolean` parameters → `structured: boolean`.
  - Rename E2E/mock modules and symbols: `pwa/e2e/canonical-editor.ts` → `pwa/e2e/structured-editor.ts` (`applyStructuredEditorPatch`), `pwa/e2e/canonical-content-input.ts` → `pwa/e2e/structured-content-input.ts` (`structuredRecipePatchIsValid`), `canonicalEditor` mock option → `structuredEditor`, `canonicalIngredientText`/`canonicalIngredientLines` → `structuredIngredientText`/`structuredIngredientLines`, `pwa/e2e/canonical-package.spec.ts` → `pwa/e2e/structured-package.spec.ts`, Vitest files `pwa/src/lib/api/canonical-*.test.ts` → `structured-*.test.ts` and `pwa/src/testing/canonical-*.test.ts` → `structured-*.test.ts`, and update `scripts/ci/e2e-suites.cjs` + `scripts/ci/e2e-suites.test.cjs`.
  - For transient browser `sessionStorage` drafts (`wfs.recipe-editor-draft.<id>`): `readEditorDraft` validates `EditorBaseline.structured` and `EditorFields.ingredientDrafts`. Any in-progress pre-rename draft in an open browser tab fails validation cleanly as `status: 'incompatible'` (existing fail-closed behavior) rather than corrupting editor state.

### 5. OpenAPI prose updates and exclusions

- **Decision**: Update only prose comments/descriptions in `specs/openapi.yaml` (lines 272, 397 non-math phrases, 566, 1085, 1810, 2855, 3267, 3556, 3575) with zero schema property, route, status code, or wire-format changes, then run `task gen:client` so Kiota-generated JSDoc comments stay in sync (`task gen:client:check` passes).
- **Exclusions preserved**: `QuantityMath.IsCanonical` / `IsCanonicalRational`, mathematical "canonical exact rational" wording in OpenAPI line 397, `GrocerySections.IsCanonicalName` / `TryGetCanonicalName` (`AisleMapper.cs` and controllers), and non-portions search-index / calendar-week wording.

## Compatibility, Rollout and Reversal

- **Database & snapshots**: Zero physical DDL changes; `api/database/schema.sql` and `api/database/compatibility.sql` remain byte-compatible with deployed databases and v1–v4 exact recovery snapshots and demo baselines.
- **Retained JSONB records**: `[JsonPropertyName("canonicalContent")]`, `[JsonPropertyName("canonicalOperations")]`, `"canonical-operation"`, and `RecipePhysicalLifecycle.RecipeFacts` key mapping preserve exact SHA-256 hash compatibility with every previously persisted row and golden fixture.
- **API & clients**: Zero wire-format changes in `specs/openapi.yaml` or `UpdateRecipeDto`/`RecipeDto`. Older PWA tabs continue talking cleanly to the updated API; an unsaved in-tab `sessionStorage` draft from before a reload is cleanly marked incompatible and reset to saved server state.
- **Reversal**: Fully reversible via standard git revert because no irreversible database migration, data rewrite, or snapshot format bump occurs.

## Risks and Deferrable Questions

- **Risk — `RecipePhysicalLifecycle.RecipeFacts` dynamic EF property naming**: `RecipeFacts` currently uses `db.Entry(recipe).Properties.ToDictionary(x => JsonNamingPolicy.CamelCase.ConvertName(x.Metadata.Name), ...)`. Renaming `Recipe.CanonicalContent` to `Recipe.StructuredContent` without mapping that key to `"canonicalContent"` would break `RetainedRecipe` deserialization (`UnmappedMemberHandling = Disallow`) and fail `FoodVocabularyReferenceInventoryTests`. Mitigation: explicit key mapping in `RecipeFacts` + verification via `FoodVocabularyReferenceInventoryTests` and PostgreSQL recovery tests.
- **Risk — Unintended edits to excluded "canonical" domains**: Automated search-and-replace could accidentally rename `QuantityMath.IsCanonical`, `GrocerySections.TryGetCanonicalName`, or mathematical "canonical exact rational" prose. Mitigation: targeted symbol-level edits plus a final grep audit confirming excluded symbols are untouched and no portions-era "canonical" symbols remain.
- **Risk — Dirty worktree overlap**: Pre-existing uncommitted edits from `retire-transitional-recipe-wrapper-readers` touch several overlapping backend files (`StructuredRecipeContentStore*.cs`, `RecipeStartupMigrator.cs`, `ManagementService.cs`, `WorkflowProcessorHistory.cs`, `FoodVocabularyInventoryQualification.cs`, `CanonicalRecipeMigrationExecutionTests.cs`). Implementation must inspect `git status --short` and preserve those edits when applying this change.
