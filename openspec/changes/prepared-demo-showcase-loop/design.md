- Current `GroceryCheckCoordinator` serializes normal grocery-map writes on one instance. It does not fence demo reset, cross-process work or old-generation recompute. Recent check reliability is a preservation boundary; reset acceptance must race checks and recomputation explicitly.
- Current Discovery uses authoritative session convergence and the existing green `SuccessCard` for "Menu's in!" / "See your matches", then opens that round's absolute week. This does not assign meals or close voting. The demo must exercise that distinction and reuse #339's eventual Home entry, without implementing it here.

### What works, and what this review changes

The existing proposal correctly treats reset as intentional, inventories all 19 tables, includes extras/PDF/search/feature overrides, identifies direct embedding/hero calls, and reuses recovery/workflow ownership. Current main adds no new table or missing snapshot category to this inventory. The gap is experience and proof: a complete reset list alone does not give a visitor a playable voting round, truthful AI alternatives or a clear recovery after reset. The additions below make those observable without a new tour, state framework or deployment project.

## Decisions and Tradeoffs

### Proposed choices requiring review

1. **Calendar:** recommend relative deployment-calendar weeks instead of frozen dates. Pin `DeploymentCalendar.Capture` and injected `IClock` once per reset; preserve `Calendar:TimeZone` and UTC cron. Map plan/event/extra/history week keys together; classify recipe cooked/rotation/defer dates, deletion/retention and New/CreatedAt eligibility individually. Preserve genuine audit time; do not silently rejuvenate timestamps or suspend purge. Review fixture eligibility across long periods, midnight, DST and week/year boundaries. Absolute replay is simpler but ages the showcase out of its intended state.
2. **Votes, reports and fixtures:** recommend fresh votes and no import reports, with synthetic aggregate history and prepared plans. Keep exactly one deliberately playable open round with remaining slots and eligible recipes; fresh identities must agree across round owner and plan status. Several visitors may switch existing synthetic members to participate; do not seed votes as if visitors had cast them or lower consensus thresholds for the demo. A separate prepared-vote/report example is an alternative needing explicit attribution and normalization. Approve a deterministic fixture content/privacy policy before publication; never capture an actual household as public sample data by default.
3. **Maintenance:** preserve reset scheduling and only reviewed deterministic work; exclude AI and old visitor jobs. Recommend no automatic dreaming/search-repair dispatch until a model-free path is qualified; retain recipe rotation through prepared facts and existing local behavior where safe. Existing exact recovery exempts dreaming and demo-restore; copying that exemption unchanged is unsafe. Approve a concrete allowlist and cancellation/fencing ownership before implementation.
4. **Legacy baseline:** recommend fail-closed recapture instead of a partial converter. Upgraded rich reset requires all collections/assets; current version-1 presence checks cannot establish completeness.

5. **Operator authority:** the current capture endpoint uses shared household authorization, not a separate operator role. The new boundary is intentional; choose the smallest existing deployment/management control that keeps capture and baseline selection unavailable to visitor credentials. This is not a claim that operator separation exists today or permission to change live authentication.

6. **Reset scope, quiescence and partial failure:** recommend replacing all declared household facts, with a bounded publication pause and stale-worker/write fencing, while preserving the host/operator rows and files explicitly inventoried above. If work cannot drain or be fenced, fail before publication and keep the prior generation available. After ambiguous commit, keep household traffic in recovery until a complete generation is selected. Alternative: a destructive offline reset with an availability window; simpler, but a different visitor/operations contract. Neither partial table replacement nor continued mixed-state serving is acceptable under this proposal. Approve this availability/recovery policy before dependent tasks.
7. **Manual recurrence:** recommend operator manual reset is one-shot; recurring successors are eligible only when configured demo mode is enabled. Automatic reset remains intentional and survives terminal failure through the existing acceptance/reconciliation owner. Current management restore accepts outside demo mode and its YAML reschedules; this is a real policy change requiring a complete modified restore-acceptance requirement, workflow tests and contract review after approval. This draft records the choice without silently changing that canonical requirement yet.

These decisions are consequential. The proposal is intentionally **not apply-ready**. The current tasks cover decision resolution and artifact readiness, not a pre-approved implementation backlog. The CLI reporting planning artifacts complete only means files exist; it is not design or implementation approval.

### Reuse, not a parallel framework

Extend the current demo owner with the minimum demo-specific baseline policy and format. Reuse existing recovery coordination, safe staging, manifest validation, durable file generation activation and journal reconciliation. Preserve exact recovery's external contract and independent-root safety constraints. Do not blindly call exact restore: its excluded votes/search, absolute dates, table set, PostgreSQL/Linux durability prerequisites and AI-capable derived repair require a demo-aware integration. Determine the smallest policy seam only after the above review decisions; do not add a generic plugin/provider abstraction for hypothetical future snapshots.

`RecoveryBoundary.Enabled` currently depends on `Recovery:BackupRoot` or an existing recovery journal and otherwise returns an empty lease; middleware and worker participation are conditional. Reuse alone does not activate reset coordination. The accepted design must name the smallest demo integration that enables the required boundary without changing live configuration or requiring a deployment redesign. Existing source preflight/publication primitives are useful components, not qualification that every demo writer participates.

### Zero AI is a serving invariant

Pinned source paths: `api/src/RecipeApi/Program.cs`, `Services/RecipeSearchService.cs`, `Services/GeminiEmbeddingProvider.cs`, `Services/Agents/RecipeHeroAgent.cs`, `Services/SearchIndexWorkflow.cs`, `Services/DreamingWorkflowSeeder.cs`, `Services/RecipeService.cs`, `Controllers/RecipeController.cs`, and `Workflows/dreaming.yaml` / `recipe-hero-regeneration.yaml` (service/controller/workflow paths relative to `api/src/RecipeApi`). Ten core files were reread at the research SHA; no provider calls were made. `WFS_ENABLE_SEMANTIC_RETRIEVAL=false` controls serving search, not indexing or direct image generation. Existing isolated bypass/fake-provider tests do not establish end-to-end zero egress.

The five named worker bypasses and decorated chat client remain defense layers, not the proof boundary. Semantic text search has a native embedding path; hero generation uses a direct Google client; recipe edits dispatch indexing; dreaming/reconciliation can invoke embeddings and categorization. Cover synchronous APIs, workers, retries and startup at every outbound model boundary even if credentials are available. Missing credentials are optional deployment defense in depth, not the mechanism and not an authorized credential change.

Typed visitor search uses lexical retrieval. Similar may use already stored compatible vectors or lexical source facts, never request a new vector. Editing searchable facts regenerates lexical state and invalidates incompatible vectors locally. Prepared hero/content is retained when generation is unavailable. UI and workflow results must not misrepresent a bypass as completed extraction or generation.

## First Observable Slice

After decisions are accepted, the first implementation slice should prepare a small but representative household through the real API/database seam, capture through the management workflow, mutate a plan and grocery extra as a visitor, reset through the same workflow, and read back the prepared plan, extra lineage and verified recipe asset. Run with provider-boundary spies that fail on any outbound model request.

This crosses management acceptance, persisted workflow tasks, demo/recovery owner, PostgreSQL rows, file generations and ordinary household reads. Keep content small, not reset coverage partial: classify every supported state owner, using explicit empty collections where the fixture has no content. The fixture needs a local original PDF and hero, one saved meal, one non-cooking day, one checked recipe grocery line and one extra with lineage, plus sufficient ready recipes and synthetic members for the open round. Browse/Search → real votes → confirmed matches → explicit save → groceries → cooking stays ordinary product behavior, not a scripted simulation or a special demo consensus rule.

Qualify missing-directory preflight, prior-baseline preservation, publication recovery and provider blocking as prerequisites to this slice. A separately reviewed preflight-only fix can reduce #245 risk sooner but delivers no showcase or universal safety/cost promise. Exclude a general snapshot framework, onboarding tour, capture simulation engine, all AI feature replicas, host changes and unrelated UX work. Do not call the first passing happy path a full zero-cost qualification: every provider row below and reset/failure scenario still needs evidence before that claim.

|---|---|

Use deterministic local documents, images and synthetic vectors with declared compatibility metadata; never call a model to make test fixtures. Provider doubles/transport traps sit at the actual outbound edge, including the directly constructed image client, and fail any attempted outbound AI send. Dummy credentials exercise presence without real secrets. Disable external network in qualification so an omitted boundary fails locally; no real AI requests or user telemetry. UI-disabled buttons or an absent key are not proof. Separately test ordinary non-demo delegation with doubles.

## State, Concurrency and Recovery

Use one baseline ID, reset publication generation and pinned calendar anchor per attempt. Drain/co-ordinate cooperating mutations, fence stale visitor workers and optimistic writes, stage and validate data/assets, publish through the existing recoverable boundary, rebuild deterministic state, then release household operations and emit invalidation. Health/recovery diagnostics stay available. A bounded quiescence timeout fails safely rather than serving mixed state.

Race acceptance includes recipe asset writes, grocery recomputation, individual/bulk grocery checks, extra check/edit/carry/remove requests, votes and close, uploads/reimport, maintenance and active workers. Stable recipe/member/extra identity is for relationships, not authority: regenerate server write generations as well as round/close identity so old extra versions and late browser responses cannot become valid again after reset. Reconnect/normal reads must reconcile missed reset events; opening a stale tab cannot silently replay visitor edits.

Capture failure leaves the old baseline selected. Preflight failure leaves live state intact. Interruption around file activation/database commit selects a complete prior or committed generation before resuming traffic. A reset retry does not duplicate aggregate history or extras. SSE alone is insufficient: stale clients and missed events must be rejected/reconciled using server generation checks. Public visitor capture must not overwrite the operator's baseline; retain the existing authorized management seam and explicitly separate baseline authority from visitor experiments.

Recurrence must not depend solely on reset success. Extend existing workflow acceptance/reconciliation with a durable successor identity and future UTC cron occurrence, preserving retry semantics and preventing duplicate effective resets. Invalid cron and failed acceptance remain visible; no busy loop or immediate catch-up is proposed. This is demo-specific lifecycle composition, not a rewrite of general workflow semantics.

## Compatibility, Rollout and Reversal

No runtime rollout occurs in this PR. Future implementation must update affected OpenAPI behavior/status schemas before code, regenerate the Kiota client and synchronize management/search/recipe consumers and method-sensitive mock handlers. Exact status-code and diagnostic-field decisions belong in that accepted contract slice, not invented here.

Capture the new complete baseline before activating upgraded reset. Preserve the previous artifact during validation and offer explicit recapture guidance for legacy content; do not silently migrate omitted state into empty collections. Rollback requires a version-compatible runtime/baseline pair and existing recovery procedures, not replaying an incompatible baseline. Non-demo installations, ordinary backup merge behavior, independent exact recovery, demo artwork and ordinary visitor household access remain unchanged. Demo baseline management gains the explicit operator-only boundary above.

## Acceptance Strategy and Operational Diagnosis

Once review choices are settled, expand tasks into bounded red/green/refactor slices using existing commands:
- `task test:api -- --filter FullyQualifiedName~Demo` plus named new capture/reset/zero-egress integration cases.
- `task test:database` for real PostgreSQL constraints, cascade membership, recovery publication, failure injection and Linux durability prerequisites; do not substitute an in-memory database.
- `task test:e2e -- <selected-demo-spec>` for prepared browse/search/planner/groceries, unsupported AI actions, mounted-client reset, stale writes, refresh and failure guidance; name the actual new test file when the contract is accepted.
- `task gen:client:check`, applicable `task prepare`, then `task verify -- <complete-reviewed-path-set>`; report exact runtime/content identity.
- Fake-clock tests around midnight, week boundary, leap/year boundaries and repeated reset; preserve UTC cron semantics separately from application-calendar mapping.
- Provider-boundary tests with credentials/flags represented, force-hero paths, uploads/reimport, text search, rating/notes/discoverability edits, startup, dreaming, reconciliation, retry and reset. Assert **zero calls**, not merely an error response. Run model-free so qualification itself cannot spend AI credits.
- Full inventory round-trip including explicit empty collections, soft-deleted dependencies, new state incompatibility, missing asset directory, partial copy, process interruption, concurrent requests/workers and failure/reschedule restart.

Reuse existing workflow IDs, task results and recovery status for diagnostics: selected baseline, format, validation failure, reset generation, completed reset versus next scheduled occurrence and last failure. Do not log credentials or captured private content. A valid cron is not scheduler health; file presence is not integrity; a 202 is not success.

## User Experience

Apply the current [designer skill](../../../.agents/skills/designer/SKILL.md), [designer identity](../../../docs/agent-designer-identity.md), [North Star](../../../docs/creative-direction-north-star.md) and optional [Everyday Household lens](../../../.agents/prompts/mere-designer.md): relief, shared choice and confidence about what happens next. This is source/document review; no rendered/device usability or accessibility result is claimed.

- **Entry and privacy:** keep ordinary member selection and navigation. A brief localized explanation says this is a shared prepared household, changes reset periodically, and personal information should not be entered. Visitors can explore or leave without completing a tour. A secondary self-hosting link uses existing project guidance and explains that AI processing in an operator-configured installation is separate from this restricted demo.
- **Recognisable household:** synthetic names and fixed relationship IDs, credible complete ingredients/instructions, varied familiar meals, ordinary non-cooking plans, preferences, history and realistic grocery extras. A locally authored recipe/PDF and illustrative media have honest provenance; no family photographs, addresses, credentials, invite/session links or copyrighted personal imports. Verify every `family_goto`, member, recipe, candidate, extra predecessor and media reference. Synthetic operational generations are deliberately fresh; content facts are deterministic.
- **Choose together:** a saved current-week meal makes Tonight/cooking meaningful, while the sole open round has unfilled dates and enough eligible choices. Visitors vote using existing profiles and reach actual convergence without traversing the whole library. "Menu's in!" means matches to review; opening matches does not save or close. The existing explicit save/close actions remain meaningful. Do not duplicate #339's Home handoff.
- **AI limitations:** recommend explicit unavailable outcomes for new photo/PDF/URL/description extraction, reimport and hero generation in the first slice, with a prepared recipe/original or return action. Explain the limitation before accepting private uploads or starting work. Viewing a prepared PDF remains useful evidence of the normal import result; it does not pretend a visitor's upload was processed. Keep local editing, lexical Search, prepared Similar fallback, voting, planning, extras/checks and cooking usable. A prepared example, if offered, is labelled as such and never changes the visitor's submitted content into a fake success.
- **Reset and interruption:** before experimenting, make periodic reset understandable without a blocking modal. During the bounded publication pause, retain navigation/context and expose retry/refresh guidance; do not claim a pending save succeeded. After reset, announce that the prepared household was restored, reconcile selected member and current week, and offer a clear return to the refreshed task. Distinguish automatic reset, ordinary save failure and an unavailable snapshot. Never autosave stale local state back over the restored generation.
- **Devices and language:** validate iPad portrait/landscape, iPhone and Pixel Phone with touch and safe-area navigation; desktop is secondary. Check text expansion and meaning in English/French, reachable actions without hover, keyboard focus/activation, status announcement, reduced motion and contrast on actual surfaces. Preserve existing Solar Earth components. No new confetti, mandatory tour, polling UI or engagement prompts.

Acceptance is a visitor completing an ordinary useful task and understanding its result, not viewing every feature. Use isolated synthetic browsers/database/files, no live demo or telemetry. On each primary device class, exercise one interrupted/returned journey and a mounted-client reset as well as the happy path. Browser emulation can establish viewport behavior; physical-device/touch qualification remains separate evidence.

### Demo context band and first-visit explanation

This selected design addition is specification-only. Use a compact purple band with white text as a separate control at the top of the ordinary app shell, respecting safe areas, suggested English label **Demo · What to know**, French **Démo · À savoir**. Keep the existing noninteractive `IdentityHint` and authentication semantics intact. The whole band is a semantic button with at least a 44 CSS pixel touch height, a generous full-width target, visible keyboard focus and a clear dialog relationship. Preserve room for French expansion and safe areas; it must not obscure navigation, failure feedback or task controls. Purple is a scoped context accent, not a global Solar Earth brand/token replacement. Measure white-text contrast at least 4.5:1 on the actual normal, pressed and focus backgrounds; do not assume a colour name establishes contrast.

Tap opens one short bottom sheet on iPhone/Pixel Phone and a compact centred dialog on iPad, reusing current sheet/dialog composition. The title and readable body explain: a sample household shared with other visitors; others may change it during exploration; changes are temporary and may be reset; avoid personal information. Suggested English body: "This sample household is shared with other visitors. They may change it while you explore. Your changes are temporary and may be reset. Please avoid personal information." Suggested French: "Ce foyer d’exemple est partagé avec les autres visiteurs. Ils peuvent le modifier pendant votre visite. Vos changements sont temporaires et peuvent être réinitialisés. Évitez d’ajouter des renseignements personnels." Primary action **Start exploring** / **Commencer l’exploration** closes the surface without navigation or household mutation. An explicitly labelled close action is equally available; no multi-step tour or full-screen celebration.

AI copy must match restrictions verified for the actual delivered slice. Current evidence establishes bounded chat/processor restrictions, not a universal AI disable. Until complete provider enforcement is qualified, use scoped wording such as "Some AI actions are restricted in this demo. Explore the prepared recipes; individual actions explain any limits." Do not claim all AI is disabled, zero cost, extraction of a visitor's upload, a guaranteed reset interval or countdown. A later verified restriction can change truthful copy without automatically replaying the explanation. This surface explains behaviour; it does not enable flags, providers, reset scheduling or authorization.

**Safe introduction:** automatically open only on the first eligible ordinary Home entry after household/member context and normal routing are ready, before the visitor starts interacting. Resolve eligibility using the existing shell/routing and task state, not a timer or new onboarding framework. A deep-link/share/import/voting handoff must reach its intended task without this automatic interruption; defer introduction to a later normal visit. If hydration or eligibility arrives after interaction starts, a task is pending or another dialog is active, withhold the automatic surface rather than opening it mid-task. The band remains usable for voluntary opening. Mark an automatic presentation in visit memory before opening so rerenders/remounts do not repeat it; routing away is not consent or a persisted dismissal.

**Remember locally:** both Start exploring and explicit close, including Escape or backdrop dismissal if supported, persist a simple acknowledgement per browser/device origin under a stable demo-specific key (for example `wfs:mode-info:demo:dismissed`). No member/household identifier, tracking ID, server write or analytics event is needed. This is device preference outside captured/restored household state, distinct from member onboarding completion. Repeated demo resets, profile switches, locale changes, ordinary navigation and cosmetic copy changes do not clear it or automatically reshow. A browser with cleared storage may see the introduction again; no cross-device synchronization is promised. Catch storage-read/write failures and keep a visit-local acknowledgement/presentation guard so denial cannot cause repeat openings during the same app visit; persistent memory across unavailable-storage reloads is not promised. Manual reopening always remains available and closing it retains acknowledgement.

**Reuse and acceptance:** existing `AppRouteLayout`, `LanguageSwitchProposal`, `onboardingStore`, `IdentityHint`, `SkipRecoveryDialog` and `InviteLinkDialog` supply shell placement, local preference and responsive-surface precedents; they are not evidence of complete modal accessibility. In particular, do not copy the language proposal's delayed timer or unguarded storage calls. Add proper dialog name/description, initial readable focus, contained keyboard focus, Escape/explicit-close handling and focus restoration to the band (or a stable shell target for auto-open). Check background interaction isolation, screen-reader reading order, zoom/text expansion, reduced motion and short-height scrolling with both actions reachable. Plan focused component/store tests and `pwa/e2e/demo-context.spec.ts` for first-ready entry, interrupted readiness, deep links, storage errors, persisted dismissal, repeated resets and reopen in EN/FR on the primary devices.

The same presentation/local-memory pattern can support a later beta explanation, with separate beta mode content and a distinct key; a demo acknowledgement must not suppress beta information or imply beta shares/reset data. Demo identity takes precedence on a beta-demo installation, retaining its existing beta-channel description; do not automatically stack a second beta introduction. Beta issue/implementation is owned separately and is not added here. This work does not require a generic mode/onboarding framework.
