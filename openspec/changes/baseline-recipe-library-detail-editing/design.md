# Design

## Context

See [proposal](proposal.md) for motivation and [delta](specs/recipe-library/spec.md) for the bounded behavior. This requested extraction design resolves cross-layer ambiguity without application design changes. A52 permits drafting only; A10 permits implementation-supported assertions and A34 defers database/runtime qualification.

## Goals / Non-Goals

**Goals:** preserve the existing library and household owners, distinguish draft normalization from stored facts, and map every scenario to inspected source and actual assertion coverage in BSL-recipe-library-008–010 of the [plan](../../../docs/openspec-baseline-plan.md).

**Non-Goals:** implementation, defect repair, contract alignment, testing application mutations, lifecycle actions or completion of adjacent capabilities. No migration or deployment is applicable.

## Decisions

1. **Append only missing behavior to the existing owner.** Main recipe-library already owns entry, retrieval, persisted facts and reading. Add nine requirements/17 scenarios without modifying any existing requirement or Purpose. Creating a separate editing capability would split the approved persisted-fact owner. Household-identity retains access/member context; no ownership check is inferred from the member header.
2. **Follow one connected observable slice.** Loaded library card → detail ID prop → GET-backed local recipe → ActionGearMenu Edit → resetDrafts → local controls → handleSaveRecipeFields → updateRecipe → generated byId PATCH/UpdateRecipeDto serializer → OpenAPI → RecipeController.Update → RecipeService.UpdateRecipe → FindAsync/non-null assignments/SaveChangesAsync → indexing attempt → ImageService.UpdateRecipeInfo → DTO return → ignored response → local submitted snapshot. Cancel before submission resets from the loaded recipe and has no PATCH. This documents the actual integration boundaries; mocks do not qualify them live.
3. **Keep draft and storage semantics separate.** Frontend trims text, removes blank ingredient rows, converts blank cuisine to null and defaults missing meal types from category or Supper. Server assigns non-null values without trimming or local name/meal validation; null/omission preserves fields, empty values replace. Blank cuisine therefore changes local presentation after success while preserving an existing server cuisine. Do not describe durable clearing. Returned total time, instructions, images, attribution, provenance, readiness and deletion are outside this field editor; adjacent hero controls do not broaden it.
4. **Describe completion as local snapshot use.** Adapter awaits PATCH and returns void. No response mapping or subsequent GET occurs; library caller has no update callback. Alternatives such as server-returned reconciliation, refreshed library or atomic save-and-refresh are unsupported. Inputs remain editable while pending; success applies the submission-time snapshot, not later input changes.
5. **Bound side effects and failure.** Update assigns UpdatedAt, marks a search sidecar pending on supplied relevant fields even when values are unchanged, saves, catches an indexing-trigger failure, then awaits the metadata-file update without that catch. File arguments include name/description but not ingredients/cuisine/meal types. No readiness/deletion mutation or explicit event publish appears in this update path. Do not infer event delivery, indexing completion, global absence of downstream effects, rollback or failure-before-commit. The generic error supports retry, not safe/idempotent retry guarantees.
6. **Keep discrepancies as review evidence.** PATCH OpenAPI documents a data object; RecipeDetailResponseDto bypasses SuccessWrappingFilter. Generated PatchResponse follows the documented shape, but the adapter discards it. Update DTO string-array meal types have no matching runtime enum/nonempty validator. Do not repair or normatively promise a disputed response envelope or universal server rejection. Missing-record 404 is not documented. U35–U37 carry these limits alongside preserved U23–U34 and the historical BSL-015 caveat.

## Risks / Trade-offs

- Source support exceeds assertion coverage → map source-only scenarios explicitly; no runtime pass claims.
- Mocked editor success looks like persistence → separate component adapter substitutions, Search browser routes and InMemory API/storage/workflow assertions from PostgreSQL qualification.
- Post-commit failure or pending dismissal can confuse completion → retain generic failure/current-draft behavior without rollback, cancellation, concurrency or fresh-state guarantees.
- Acceptance can be confused with task completion → tasks cover documentation extraction and validation only; human acceptance, promotion and archival remain separately authorized actions.
