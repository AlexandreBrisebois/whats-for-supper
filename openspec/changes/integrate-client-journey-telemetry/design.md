## Decisions and Tradeoffs

### 1. Logs only, one centralized boundary

Use a single official browser `LoggerProvider` and standard HTTP Protobuf log exporter. No browser trace provider, fetch/XHR instrumentation, metrics, all-in-one browser distro or Node/API telemetry provider. One root client bootstrap initializes once after a valid server enablement hint, shares capture state with the root navigation observer and framework error helpers, and does not depend on a feature's effect lifecycle. HMR/remounts cannot create another provider. Root-layout replacement reuses the document owner when present; a failure before initialization is an explicit capture gap, not a reason to buffer raw errors.

The authoritative navigation boundary is one Next App Router pathname observer, emitting the ordinary OTel log name `browser.navigation`. It observes committed route state, including the initial pathname, not successful screen rendering. This small centralized adapter is justified by the upstream package gaps below; it is not a custom SDK or per-screen hook. No route adds a telemetry call. No custom business events are planned. Retained `stage.name` provides the static route label that Sentrame can actually use.

The observer deduplicates unchanged route templates and effect replay, retains A → B → A, and ignores query/fragment-only changes. Unknown paths map to `other`, never a dynamic slug. Catalog from current app pages: `/`, `/welcome`, `/invite`, `/onboarding`, `/home`, `/recipes`, `/capture`, `/capture/confirm`, `/planner`, `/discovery`, `/profile`, `/profile/settings`, `/browse-all-stack`; labels reuse the historical vocabulary where meaning agrees. `/recipes` remains `search`. Unknown adjacent paths are intentionally indistinguishable. Same-route surface changes, Save, voting and clicks are not observed.

### 4. Smallest acceptance/export boundary

Proposed new server-only configuration: `WFS_CLIENT_TELEMETRY_ENABLED=true` plus `SENTRAME_OTLP_BASE` and `SENTRAME_TELEMETRY_KEY`. Only exact `true` with valid endpoint/key enables the hint and server route. Old `WFS_TELEMETRY_ENABLED`, browser/server tokens and ambient OTEL headers cannot enable or enrich this pipeline. Require HTTPS, or loopback HTTP only for isolated qualification; reject userinfo/query/fragment and define the base as an origin with no path. Fixed upstream is `${base}/v1/logs`. Exporter `url` expects a full signal URL; construct its absolute same-origin URL with `new URL('/telemetry/v1/logs', location.origin).href`, never the current page URL. Key never enters browser code, payload, cookies, query, response or log. Service is fixed `wfs-pwa-browser`; server owns bounded `service.version` from release metadata.

Root already resolves dynamic installation state: reuse that server boundary for the boolean hint. No personal consent preference is added or inferred from Demo/member/access state. Shared bootstrap rechecks via subsequent server-rendered state/forwarding denial; stale hints cannot authorize the server. On confirmed denial, stop listeners, discard queues and clear the lease; fresh reenablement starts a new visit. Environment changes require the serving process to adopt them; this is not a claim that all running processes update instantly.

There is no currently qualified forwarder to preserve. Add one Node Route Handler, `POST /telemetry/v1/logs`, carrying only ordinary OTLP ExportLogsServiceRequest/Response Protobuf. Avoid `/api`: `docker/compose/apps.yml` routes `/api` to .NET. Add an exact proxy exemption for this handler before both access and member gates so invitation/Welcome observations do not require household identity. No general public-prefix exemption or API instrumentation. The browser sends no app telemetry key and the handler never forwards browser cookies, Authorization, Referer, IP, user-agent or arbitrary headers. Inspect infrastructure access logs separately: application payload minimization does not remove transport metadata already visible to a proxy.

Validate same origin/Fetch Metadata for the qualified browser path; reject missing/foreign origin rather than enabling CORS. Require Protobuf content type, no compression, bounded streaming body and fixed method/path. Use a standard generated OTLP Protobuf decoder/schema (official opentelemetry-proto, pinned) to check names/types/counts and closed fields; no proprietary envelope or handwritten wire encoder. Reject policy violations atomically, without echo. Forward validated ordinary bytes to fixed upstream with the server key and no identity header enrichment; recheck current configuration immediately before dispatch. This validator is application acceptance policy, not a new telemetry SDK/provider. Any schema dependency must be separately pinned and tested against actual exporter bytes.

Proposed bounds: 64 records/request, 256 KiB body, one upstream request/process, 2-second request deadline, no redirects, no server retry queue. Browser standard batch processor: queue 256, batch 32, delay 1 second, export timeout 2 seconds; pre-batch budgets 100 navigation and 20 error records/minute/document. Enforce a process aggregate acceptance bound too (120 requests/minute; no IP identifiers). Bounded pressure drops/refusals are not a completeness claim. Inspect actual SDK retry/flush behavior in qualification; no custom retry transport. Propagate safe standard OTLP success/error responses, with 400 invalid, 403 disabled/origin, 413 size, 415 encoding and 429/503 pressure/upstream failure; do not turn a dropped batch into a durable-success claim. An accepted response still needs protected retained-read verification. Do not buffer requests in `after()` and return early success.

The new externally visible PWA operation needs approved HTTP documentation in `specs/openapi.yaml` before implementation, explicitly PWA-owned and unauthenticated by household credentials. Use the standard binary body/response, not an application JSON DTO. Regenerate/check Kiota mechanically; the official exporter, not a generated business client, consumes this operation. Update route-parity tooling only to model this explicit PWA owner, with real handler acceptance tests; do not pretend the .NET OpenAPI runtime serves the route or broadly suppress drift. Business mocks remain unchanged; the synthetic Next handler fixture owns this OTLP seam. This contract/tooling cost is required by repository policy, not another business endpoint.

### 5. Privacy before queues

Route classification uses pathname only and maps to a fixed catalog; it never copies actual URLs into records. Use an allowlist processor that is the sole delegate into the SDK batch processor: reconstruct a safe record, strip raw body/stack/message/resource/scope extras, arbitrary attributes and ambient span context, enforce names/severity/UUIDs/clocks/sequence/budgets, then enqueue. An independent sanitizer appended after a batch processor is insufficient. Apply the same gate to standard instrumentation and shared framework logs; unknown or throwing getters fail closed. Diagnostic callbacks cannot print raw errors. Closed exception types: Error, TypeError, RangeError, ReferenceError, SyntaxError, URIError, EvalError, BrowserError and RenderError. No arbitrary DOMException/name passthrough.

Only the approved context and static technical values enter OTLP; no action-ID or feature-result field is needed. Stable record IDs distinguish genuine repeats from exact re-export; do not deduplicate by payload hash or stack. Do not manufacture ordering or business evidence to compensate for receiver omissions.

In an isolated Next composition using real root/navigation/bootstrap/proxy/handler code, enable synthetic installation configuration and open Home, then Search, then Home. Real official SDK → same-origin Protobuf handler → disposable receiver → authenticated retained reads must show exactly three navigation occurrences in one tab, an empty captured definition, the same repeated Home stage and zero completed goals. Capture and decode wire bytes to prove the closed policy. First establish the disabled baseline and dependency resolution, then this complete path before adding error/reload cases. No real API/database/household is needed; mock ordinary product HTTP only at its existing external boundary.

## State, Concurrency and Recovery

Historical IDs existed only in a document WeakMap and deliberately did not survive reload. That policy cannot satisfy issue #326's full-document invalid-invite → Welcome transition. Proposed replacement is one versioned `sessionStorage` lease containing only random visit/tab IDs, sequence and local lease clocks; no URL, previous path, event payload or identity. Inactivity expiry is 30 minutes and absolute expiry is 2 hours. Check clocks/lease on emission; invalid clocks/state reset scope. Full navigation/reload advances the same persisted sequence before emitting; BFCache/pageshow revalidates policy and ownership before resuming. No localStorage, identity cookies, cross-tab visit joins or offline event storage.

Session storage can be copied into a new/duplicated tab. On supported secure-context browsers, acquire a nonwaiting exclusive Web Lock for the random stored tab scope before reuse; hold while active. A contending tab rotates both IDs before any emission. Reload ownership handoff may use a bounded wait (at most 250 ms), then safely rotates if uncertain. A resumed/frozen tab that lost ownership must reacquire or rotate. Web Locks are local concurrency controls, not exported identifiers. If storage/locks are unavailable, use fresh document-only IDs; same-document login remains supported, but cross-document continuity is explicitly unqualified. Never guess ownership from navigation timing, opener presence or timestamps. Test cloned tabs while the first is live, BFCache, reload races, blocked storage and lock contention; failure to isolate blocks continuity acceptance on that platform.

Every admitted record gets one UUID and positive sequence; persisted sequence is reserved before enqueue so a crash can create gaps, never reuse. Ordering scope stays one service/app/visit/tab. Late unique sequence orders evidence; duplicate/absent sequence carries uncertainty under receiver rules. New telemetry delivery never retries business actions. No raw event replay queue survives a document; abrupt termination may lose tail records. Errors refer only to supported explicit context, never nearby time. Shared boundary/native duplicate reporting uses object occurrence identity within a document where possible; unidentified occurrences remain uncertain, not fingerprint-collapsed.

## Compatibility, Rollout and Reversal

This delta changes client retirement and historical correlation policy only. Preserve the canonical requirements for independent diagnostics/Save validity and external retention/deployment boundaries unchanged. Do not sync canonical specs in this planning task. Legacy flags and dual credentials remain inert after future implementation; removal tests must still cover this.

Current Sentrame source requires fresh registration; owner must provide actual deployed source identity, fresh app key/status and endpoint separately. No migration, rotation or data deletion is included. Test only an owned fresh temporary receiver/app. Existing two-key data is neither treated as compatible nor reset. No direct cross-origin delivery fallback. Turning the new flag off prevents future accepted/not-yet-dispatched export once processes adopt configuration, but cannot recall remote retained data. Service workers must never cache opt-in policy/OTLP or queue it offline; test current `public/sw.js` behavior alongside the new route.

## Operational Diagnosis

Acceptance ledger must report each layer independently: capture (safe names/counts/context), export (actual decoded standard SDK bytes through Next), durable receipt/read (protected records and authorization), and derivation (ordered goal-free path, diagnostics, replay/restart). Deployed proxy/Tunnel and physical-device/browser lifecycle evidence are separate, never inferred from local HTTP or historical tests. Logs may report only bounded technical counters/categories, never payloads, keys, arbitrary upstream errors or request URLs.

Receiver gaps/dependencies: no retained `browser.navigation.*` selectors; no generic raw DOM/action history; raw stacks deliberately unavailable from WFS; missing scope stays unassigned; inactive means unknown outcome; capped/expired detail cannot prove a complete path. Improved Find ID, follow-scope restoration and directed occurrence hierarchy remain the separate Sentrame proposal. Public aggregate publication/rare-sequence controls from issue #326 are outside this integration and must not expose sessions through WFS. No business-persistence qualification is claimed; a later business-event proposal needs an identified unanswered question.

## Decisions and Evidence Still Needed

The proposed architecture and conservative fallback behavior above are concrete planning choices for review. No owner decision is required to finish these artifacts.
