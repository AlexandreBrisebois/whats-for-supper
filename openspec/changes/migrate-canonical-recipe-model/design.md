## Context and Existing Ownership

Current `ManagementService`, `RecipeExportContent`, `SyncRecipeProcessor`, `RecipeRepository` and online recovery owners span database, disk/media and durable workflows. Existing ordinary restore supports legacy arrays and missing artifacts; several main requirements must change together. Recipe-only fallback must not invoke general seed/disaster recovery unchanged because those owners also mutate household data.

The implemented foundation includes `CanonicalRecipeContentStore.ConvertAsync`,
the current recipe codec, `ManagementService.CanonicalBackup` and guarded
publication-backed seed/sync. Existing conversion and publication PostgreSQL
tests establish bounded behavior; they are not an operator batch entry point.
`ManagementService.CurrentRecovery` exposes inspection/preflight, not activation
of its complete staged inventory. The existing exact snapshot/recovery owner is
also reusable and distinct from ordinary merge. Local existing-operation evidence
is recorded in `.task/canonical-existing-flows-20261110/outcome.json` against its
own candidate; current release qualification remains open.

## Decisions and Tradeoffs

Default in-place preserves live recipes and stable IDs. Capture source/current facts and protected hashes, convert only proven associations with one owner per recipe and publish atomically guarded. Ambiguous trusted measurements that cannot be represented safely keep legacy read access until manual reconciliation; do not erase them for a migration completion percentage.

Current-format ordinary merge and explicitly selected exact replacement are separate. Version and timestamps cannot establish precedence. An old backup is unsupported, not implicitly convertible inside restore. The one-time forward importer accepts only its manifest's input list; legacy source readability during this process does not promise continued old-backup support. Existing historical voter privacy, extras, report state and preparation/serving recovery remain intact.

Final recovery covers persisted portions, binding, row/check, household and now
included bilingual identity contracts. The app-owned model-authored vocabulary is
a durable versioned UTF-8 JSON file on disk, not a value regenerated by AI. Stable
IDs, EN/FR labels and aliases, purchase qualifiers, revisions, provenance and every
saved mapping/override reference must survive offline full recovery. Null or
ambiguous mappings remain honest; restore performs no translation, speculative
merge, external dataset download or AI regeneration. Historical pre-adoption
inspection may retain absent optional facts, but the final new-app full format
requires its vocabulary artifact even when individual recipe mappings are null.
Final recovery acceptance waits for the actual persisted step and bilingual contracts.
Changes to the shared canonical store/publication hooks are coordinated with their
workstream A owner rather than edited by competing writers.

## Existing operations own canonical backup and seed

Dreaming’s db-backup step invokes BackupDatabase and the same `ManagementService.BackupAsync` as POST `/api/management/backup`. POST `/api/management/seed` invokes `RestoreAsync`; evolve these owners to write/read the existing version-2 canonical recipe codec. Keep the existing disk layout and management routes. Any necessary format/integrity inventory is internal to these operations, not a second recovery API or user-facing package. Whole-installation database plus asset backup remains a separate protection against disk loss and migration rollback.

Preflight canonical input before household mutation. New destination recipes retain exported IDs and exact canonical content; repeated identical seed is idempotent. A divergent current destination is not authority to overwrite newer human facts: preserve it and report conflict unless the existing captured revision/publication owner proves authority. Sync remains recipe-only and uses captured input, revision guards and durable publication/retry ownership; it must never invoke household seed or infer permission from timestamps. Legacy readability before activation is not a promise of permanent old-backup support; cutover remains fenced until the current-only boundary is qualified.

## Durable vocabulary and complete recovery integration

Reuse the existing storage and archive owners. `LocalStorageProvider` provides
DataRoot partitions and atomic flushed file publication; select the vocabulary
path/format with the bilingual owner. Validate expected existing revision/hash
before replacing a file. Do not seed over an existing valid file, silently replace
restored definitions with a newer bundled seed, or treat missing/corrupt referenced
identity as an empty dictionary. Initial creation requires captured absence.

`CurrentRecoveryArchive` already recognizes `food-dictionary` and
`household-food-overrides` artifact kinds with inventory/dependency/hash checks;
`CurrentRecoveryHouseholdState.Dictionary` validates releases, labels, aliases,
qualifiers, mappings, protected fields and references. Those implemented validators
are not proof that ordinary full snapshot capture/restore includes a live vocabulary
file. `RecoverySnapshotService` currently stages selected tables, recipe media and
history, while its restore owner allowlists known artifacts. Integrate the selected
JSON and dependent mapping/override facts into those existing capture, required-file,
staging, publication and interrupted-recovery owners; do not introduce a parallel
export framework. Keep recipe-only sync separate from full household recovery.

Capture dictionary bytes and dependent DB facts consistently under the existing
snapshot/write boundary. Preflight complete format, checksum, revision, alias
collision and reference membership before any dependent file/DB write. A missing,
corrupt, unsupported or dangling vocabulary/reference fails the complete input;
no provider/network regeneration is a fallback. Rehearse file activation/DB commit
interruption, stale replacement refusal and exact restore/re-export with stable
identity/provenance. Ordinary merge preserves newer protected destination facts;
explicit exact replacement retains its separately selected authority. Historical
old-format inspection remains available without promising routine restoration of
incomplete old backups in the new app.

## Compatibility, Rollout and Reversal

Frontend, backend and database are deployed together as one coordinated release,
as confirmed by Alex. Do not add an independent rolling-version compatibility
program or legacy string-write translation. Already-open older tabs remain possible:
reject their incompatible canonical writes atomically and retain recoverable drafts
through refresh and reconciliation. Unconverted recipe readability and current-app
review-material editing are data-transition behavior, not support for old app versions.
The deployment unit includes its schema migration; durable older workflow results
still need captured-revision validation before they can publish.

Planned downtime is accepted. Reuse `RecoveryBoundary`,
`RecoveryBoundaryMiddleware`, `WorkflowWorker` participation and the existing
`RecoverySnapshotService` durability/reconciliation owners used by the demo loop
and online recovery. Their source establishes cross-process PostgreSQL leases,
bounded busy responses and interrupted-publication reconciliation; it does not
already qualify a schema deployment across process restarts. Determine the smallest
reuse needed to hold writes/workers across shutdown/startup, preserve a verified
pre-upgrade recovery point, publish the coordinated release, read back its state
and reopen only after required checks pass. Measure the maintenance interval in
rehearsal. Reuse applicable client refresh behavior while retaining upgrade drafts;
do not invoke demo baseline replacement, activity clearing or draft-discard policy.

Use [rollout](../canonical-ingredient-correction/rollout.md). All old writers, workers, background sync and tabs must be fenced. Export unsaved drafts locally through the supported upgrade route before refresh; old full editor payloads with ingredients cannot masquerade as unrelated updates. Prepared counts, dates, history, family members, votes, assignments, human rotation/discoverability and grocery-extra lineages are protected.

### Preserve plans and rebuild every grocery list

Alex's 2026-11-12 amendment replaces the earlier no-active-list/first-new-list
premise. Preserve every planned meal and calendar event: IDs, dates, status, recipe
links, servings intent, preparation/cooked facts and non-cooking entries. Never
clear assignments/events to satisfy a cutover gate. Inventory the union of every
persisted grocery-list week and weeks implied by preserved assignments, including
past, current and future weeks; recalculate all of them using the accepted new
model. Defer unrepresentable recipe conversion honestly while retaining usable
source facts; report the actual inputs and completion of each affected rebuild.

The operation manifest distinguishes protected plan/event/household fields from
allowed grocery-derived changes: recomputed recipe rows and demand evidence,
row/list versions, serving input/applied versions and refresh status, reset-summary
state, grocery checks and checked-demand baselines. It may reset checks/baselines
only in this fenced migration epoch. New or structurally changed recipe rows must
not inherit ambiguous legacy name-level acknowledgements. Manual extra occurrence
IDs, content, recurrence/removal/history links, manual shopping/category corrections
and all other facts remain protected. The pre-rebuild backup and operation evidence
retain original historical facts; recalculation is not permission to delete plans,
events, extra history or other household records.

Bind the complete week inventory, source revisions, vocabulary revision/hash,
allowed field changes and checkpoints to one operation. Reuse existing projection,
recompute and check-coordination owners under the write/worker fence. Interruption
leaves the household held until completed weeks are reconciled and remaining work
finishes with independent read-back. Resume must not repeat a completed reset after
reopening or erase subsequent human checks. Ordinary postmigration recomputation,
locale/label changes and exact restore retain their existing check/baseline policy;
the migration reset exception does not extend to day-to-day behavior.

A verified independent pre-cutover snapshot plus exact old executable/schema is the emergency rollback pair. After new writes, simply rolling back an image is unsafe; choose compatible full-state recovery or forward fix. Fresh current-format backup after conversion is separately read back and verified before routine operations resume; it cannot protect the migration interval retroactively.

### Slice 1 persistent maintenance hold

The user extended 3.1 beyond assessment after preflight proved session leases alone
could not retain maintenance intent. `RecoveryBoundary` now recognizes
`.maintenance-hold.json` in `RecipesRootResolver.BaseRoot`, outside generation
folders. Any entry, including malformed/unreadable content or a directory, enables
coordination and blocks Write and Publish after the existing publication lease.
Read/Snapshot remain available; restore publication cannot bypass the hold. There
is no automatic timeout or parsing-based release. Existing startup activation uses
Write, so the process stays unavailable until explicit operator reopening; no
startup bypass or new public recovery API is introduced.

Operator creation acquires the existing exclusive publication lock in the actual
API database, drains writers, verifies the single-instance/data-mount boundary,
stops the old API while retaining the lease, writes/syncs the marker atomically and
reads it back. This order protects first activation with an older binary that does
not understand the marker. Exact operation/candidate identity, stopped sharing
containers and verified read-back are prerequisites to removal under the same lock.
Privileged schema tools remain coordinator-controlled while application processes
are stopped. Startup and deployed acceptance follow release; initiation is not success.

This is maintenance support, not library conversion or task 3.1 completion. Slice 1
retains the legacy library and existing volumes. Selected-ID conversion, full
protected-field/synthetic fixtures, stale-tab drafts, current-format full recovery
and grocery cutover retain their original requirements and task IDs.

## Conditional Disk Fallback

Only if in-place assessment establishes a concrete unresolvable blocker, prepare recipe-only fallback. Inventory both disk/live versions, IDs, source/media and field ownership; preserve input copies independently. No delete-all, auto-created missing IDs, soft-delete resurrection or purging database-only recipes. Household state, notes/rating/manual flags, attribution, creation/deletion, occurrences and relationship IDs stay untouched. Stage selected recipe fields only; revision-guard publication and durable derived rebuild. Record converted/deferred entries and resume input/output identities. For fallback, compare disk and database by stable recipe ID before publication; report unexpected content or membership mismatches and stop rather than choosing a winner.

Alex reports no recipe edits through the UI and says Dreaming has kept disk and database in sync. Treat matching recipe IDs/content as the expected case and verify it, allowing only documented representation differences from conversion. If an ID is missing on either side or supported recipe facts unexpectedly differ, stop/report the fallback before mutation rather than silently replacing content. No elaborate per-recipe edit-conflict workflow or general disk/live precedence selector is required solely for hypothetical UI edits. Keep revision guards against actual concurrent changes, input preservation and household protections. A timestamp is not evidence of equality. Do not overwrite source files before independent preservation and validation.

## Operational Diagnosis

Separate conversion status, committed facts, pending derived rebuild and completed verification. Record no sensitive raw recipe/provider payload in routine logs. A failure preserves prior usable content; a conflict is neither empty success nor forced replacement. Test current-format merge stale/divergent content, identical revision with different bytes, crash/restart, stale work, mixed old clients and media publication gaps before release.

## Bounded schema-only descendant continuation

The November14 selection extends the existing internal V1 admission owner with a
separately pinned continuation. The original intent/policy/approval and source
readback remain unchanged. Preserve original-column row digests by explicit
projection from the independently verified pristine catalog, while matching the
entire resulting catalog to the independently assembled expected descriptor.
Apply only extracted reviewed compatibility DDL in one transaction. Admission
independently requires complete schema, unchanged original rows/files and exact
receipts plus completion evidence; an interrupted or forged marker is insufficient.
Exact retry recognizes only pristine or fully prepared state, never partial state.
This avoids recapturing changed whole rows as authority or normalizing unrelated
old constraints. A broad schema migration is excluded because it includes data
rewrites and destructive transitions. The existing strict inventory remains the
next owner, with schema/attestation/inventory/full recovery reported separately.


## Selected attestation-bound recovery-history continuation

Reuse existing history v1 and index v1 formats. A bounded internal context carries
only the reviewed operation/generation/snapshot and exact-source attestation through
all history owners. Its canonical receipt checks require exact46 membership and
bytes, not semantic equality. Other owners retain ordinary validators. Ordinary
public entrypoints never obtain this context. No global parsing switch is added.

A separately pinned history continuation preserves both prior intents and binds the
same reviewed schema inputs/catalogs to a fresh disposable descendant. Preparation
completion binds this request hash, so old markers cannot authorize it. Stage only
history/index and separate attestation lineage with deterministic completion metadata
through Linux recovery durability. Exact retry accepts only matching existing bytes;
partial files cannot authorize reads. Fresh-process read-back requires the verified
source and regenerates a protected observation to compare every staged fact before
existing history/reference/authority/index validation. This source dependency is
explicit; hashes from an untrusted envelope are insufficient. No offline full snapshot
acceptance, full snapshot publication, restore or historical mutation is introduced.

## Proposed attestation-bound full-snapshot staging and inspection

The [full-snapshot contract](../../../docs/handoffs/dependable-portions-next-slice/V1-FULL-SNAPSHOT-PLAN.md)
now owns the prospective continuation beyond delivered history staging. Its
[separate proposed request](../../../docs/handoffs/dependable-portions-next-slice/V1-FULL-SNAPSHOT-CONTINUATION.json)
binds fresh operation/generation/snapshot/paths and completion to the immutable
original authority, qualified schema transition and predecessor history delivery.
Current runtime request dispatch must reject it until separately selected and
implemented. Old markers and predecessor approval do not authorize execution.

Reuse CaptureToAsync artifact construction under the Snapshot/table-lock boundary,
but stage internally without its final BackupRoot rename/publication. Retain
manifest3/history1/index1, exact ordered current table set and closed file inventory.
Keep lineage/completion in a sibling authority envelope because the ordinary payload
allowlist rejects those history-stage files. Only the qualified internal reader may
carry finite V1 history authority; ordinary/public/demo readers and restore stay strict.
Fresh-process inspection must reconstruct authority from pinned originals and fresh
prepared source, validate complete artifacts plus existing schema/closed-row/FK/
weekly-history checks (rollback-only TEMP writes), and reread source/artifacts around
completion. Identity-only inspection is insufficient. It remains source-dependent.

Protect all46 exact PostgreSQL-text receipts, all31 original table projections and
all1576 source files separately from the selected recovery payload; enumerate each
file/table disposition. Normalized table JSON cannot prove result::text identity.
No persistent validation writes, source sidecar changes, vocabulary adoption,
grocery reset/rebuild, publication, restore, complete source admission, activation
or deployment. Missing representation is a blocker, not permission to discard facts.
The successor contract fixes RED/GREEN, interruption/exact-retry, independent review,
actual PostgreSQL and acceptance/exclusion claims. Historical provenance remains
unproven and aggregate tasks remain open.
