## Decisions and Tradeoffs

0. **CI is fixed first, from evidence, not guesses.** Facts from the public jobs API for run 44669197408 (commit `afdb801a`): failing jobs are `API — test` (step `Test`), `PWA — E2E (planning)` (step `Run capability suite`) and `Cooking steps … (cooking)` (step `Run required servings context live`); `PWA — build & E2E` fails only as the aggregate gate over them, and `Analyze validated source` is skipped because of it. Passing jobs need no work.
   - **API test (observed from the job log, `gh run view --job 136066557357`):** 3 of 3,822 tests fail, and they are all `DeploymentCalendarTests`. `ShippedComposeTemplates_DefaultCalendarTimeZoneToTorontoWithOverrideSyntax` (for `docker/docker-compose.prod.yml` and `docker/docker-compose.nas.yml`) and `ShippedEnvironmentAndTaskfile_DefaultCalendarTimeZoneToTorontoWhileSmokeAndCodeStayUtc` throw `FileNotFoundException` for those files and for `docker/.env`. `.gitignore` (lines 62, 65, 99) ignores exactly these three, so they exist on a developer machine and not in a CI checkout. **Root cause:** the tests assert on untracked local files, so they can pass locally and never in CI. The same theory already asserts the Toronto default on tracked templates: `docker/compose/apps.yml`, `production.yml`, `production-overrides.yml` and `release-template/synology/compose.yaml` (lines 55-60), and the second test asserts it on tracked `docker/.env.example` (line 72) and `smoke.env`. **Decision:** delete the two ignored-file theory rows (`docker/docker-compose.prod.yml`, `docker/docker-compose.nas.yml`) and the `docker/.env` assertion (line 73). No shipped-default coverage is lost: they are developer-local copies, and the tracked files that ship carry the same `${Calendar__TimeZone:-America/Toronto}` and `Calendar__TimeZone=America/Toronto` lines (verified in source). Alternative rejected: skipping when the file is absent, which would silently pass in CI and test nothing there.

   - **Planning E2E (observed from annotations):** `planner-portions-refinement.spec.ts:130` expects the Portions stepper box to move < 1 px after pressing plus (4 to 5); it moved 8-10 px in both EN and FR (390 and 375 px loops).    - Ordering: CI fixes go before the UI items so that the UI work is verified against a green baseline, and so that a later red run can be attributed to this change.

1. **Pip removal keeps the pulse and `aria-label`.** The only non-motion cue for `collecting` becomes the accessible label and Discovery's pulse. Under `prefers-reduced-motion` there is then no sighted cue beyond the ochre color. Accepted per request; the spec records it explicitly so it is not rediscovered as a regression.
2. **Header row gets its own line when both buttons show.** Alternative: shrink padding or font until it fits beside Portions. Rejected: `text-xs` (12 px) is the repo's minimum text size and 48 px targets are required, so Portions + Nudge + Close cannot fit at 390 px, let alone 320 px. `meal-planning` already says these actions live "in their own row". The fix is therefore structural: when both are present, the action row takes the full line (`basis-full`), uses `flex-nowrap`, and the two buttons split the width without wrapping. With a single button (Ask the Family alone, or the converged close alone) the existing side-by-side layout with Portions is unchanged. **Proposed assumption:** with Nudge + Close visible, Portions sits alone on the line above. If you would rather keep Portions beside them, the buttons would have to become icon-only, which changes the spec.
3. **Restyle Go back with the existing `Button` `ghost` variant.** Use `<Button variant="ghost">` with a leading `ArrowLeft` icon, `text-sm`, full width and at least 48 px tall, keeping `disabled={pending}`, `onClick`, label and key `home.goBack`. Alternative: hand-tune the existing `<button>` classes. Rejected: it keeps a one-off style and still lacks focus-visible styling, while `Button` already carries the Hearth focus and contrast rules. Behavior is unchanged (returns to step 1 without mutation; disabled while pending).
4. **Ring fades via a two-phase local state, not a library.** `successDay` is kept; add a `ringFading` flag. After ~2.5 s the card swaps to transparent ring classes with a ~500 ms `box-shadow` transition (`motion-reduce:transition-none`), and `successDay` is cleared at ~3 s. One timer owner in `PlannerPage`, cleaned up on unmount, on a new `successDay`, and on context change. The ring classes stay constant-size (`ring-4` with a transparent color rather than toggling the width) so the fade causes no layout shift. Alternative: a CSS keyframe `animation-fill-mode: forwards`. Rejected because the stale `ring-sage` class would remain in the DOM, which the existing e2e assertion would read as "still highlighted".

## First Observable Slice

The ring fade, since it is the only item with new timing logic. Entry: `PlannerPage` receives a planning result and sets `successDay`. Layers: `PlannerPage` state + `PlannerDayCard` classes only. Observable result: with fake timers, the card has the ring at 0 s and 2 s, and neither the ring class nor the fade class at 3.1 s. Integration boundary: `pwa/e2e/planner.spec.ts` (the `ring-sage` check around line 1141) asserts present, then absent. The other three items are independent single-component edits and follow in any order.

## State, Concurrency and Recovery

- Superseded highlight: a new `successDay` restarts the timer; a week change clears it (existing line 423 path) and cancels the timer; unmount cancels it. A stale timer must not clear a newer day's ring (key the callback by day index or clear the previous timer).
- Replacement or spillover receipts are untouched; only the decorative ring is transient.

## User Experience

- Nav: no dot in any state; label, pulse and converged green unchanged. Both locales.
- Header: one line at 320, 390 and wide layouts, EN and FR, with Portions open and closed; targets stay ≥ 48 px with visible focus. The `Save menu & close voting` converged label (Nudge hidden) may wrap inside its own button; that case is unchanged.
- Plan B step 2: Go back reads as a clearly secondary control below the three options, with an arrow, readable `text-sm`, a 48 px target, a visible focus ring and AA contrast in both modes. Focus order is title, X, the three options, Go back. X, Escape and backdrop behavior are unchanged.
- Ring: it should read as a brief confirmation, not a persistent selection. Reduced-motion users get an instant removal, not a lingering ring.

## Risks and Deferrable Questions

- Visual only: the `ghost` variant's hover/active colors must stay legible on the cream dialog in High Contrast mode; check both modes.
- Deferrable: exact ring duration (2.5 s / 3 s) and header padding values; neither changes scope or behavior.
