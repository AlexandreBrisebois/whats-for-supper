## State, Concurrency and Recovery

The app-shell visit guard starts at first app-shell entry and persists across ordinary shell navigation/remounts until full reload. Welcome/onboarding activity is outside that guard. Capture initial shell path/query even while runtime mode is unknown. Query-bearing Home is conservatively ineligible even for unfamiliar parameters. No persistent marker is written for eligibility, presentation or routing. On a fresh eligible Home visit, require selected member, family `hasLoaded && !isLoading`, no UI loading, no pending capture recipes, no PDF selection, no competing modal and no prior pointer/key/wheel interaction. Routes for editors, cooking and planning are ineligible; Home overlays are covered by the modal/interaction guards. Verify these actual seams rather than promise a universal task detector.

Keep Demo's visit guard across mode discovery and remounts. A mode change cannot clear `presented`/`interacted` or manufacture a new safe entry. Remove open state on route/owner/mode departure; restore focus only on explicit dismissal to a still-connected band. Reopening manually is deliberate but must not discard an editor or create stacked modals: while another modal is open, its native modality owns focus and the background band cannot activate. Neither click-outside dismissal nor a new timer is proposed; retain DemoDialog's current explicit actions/Escape.

Preserve main's corrected dismissal-only focus behavior: exercise route and mode departure with a still-connected band and assert destination/editor focus stays put, alongside positive focus-return checks for Start exploring, Close and Escape. This is regression coverage for reuse, not an outstanding source defect.

Welcome owns only route-local manual-open state and mode-specific acknowledgement access. It must not initialize `eligibleEntry`, mark Home `presented`/`interacted`, or install shell pointer/key/wheel listeners. Typing, clearing, Enter, onboarding and manual-open departure without dismissal leave later first eligible Home introduction possible. Explicit Welcome dismissal sets the same Beta in-memory acknowledgement and attempts the same Beta key, suppressing later Home auto-open even if persistence fails. Welcome departure clears its open state without acknowledgement or Home presentation; the active app-shell departure rule remains no repeat in that shell visit.

Beta acknowledgement is proposed as `wfs:mode-info:beta:dismissed` with value `true`. Keep Demo's key unchanged. Read once per mode per app visit; catch both reads and writes, including unavailable `localStorage`. Set in-memory acknowledgement on explicit dismissal even if storage write fails. No ID, cookie, server synchronization, timestamp, copy hash, locale suffix or reset integration. Cross-tab instantaneous synchronization is not promised; each tab's visit guard prevents repeat interruptions. A full reload with blocked storage may introduce once again, honestly bounded to visit memory.

### Feedback template proposal — review before implementation

Propose one lightweight bilingual GitHub Issue Form, named **Beta feedback / Commentaires bêta**, rather than a technical bug-report checklist or an in-app collector. Candidate path: `.github/ISSUE_TEMPLATE/beta-feedback.yml`; candidate direct destination: `https://github.com/AlexandreBrisebois/whats-for-supper/issues/new?template=beta-feedback.yml`. Both are proposed, not present or validated. Do not ship a dead template link; form creation and direct-link wiring wait for design and implementation approval, then verify the exact filename/destination before use. The verified Issues index above is the valid fallback if the approved template is not yet available; do not imply that the fallback opens a form.

| Proposed field | Required? | Purpose |
| --- | --- | --- |
| What were you trying to do? / Qu’essayiez-vous de faire? | Yes | One short account of the task or idea; no technical reproduction steps required. |
| What happened? / Que s’est-il passé? | No | Let the visitor describe friction or a result when relevant, without forcing a suggestion into a bug report. |
| Suggestion or screenshot / Suggestion ou capture d’écran | No | Optional improvement idea or manually attached screenshot; not a required upload. |
| Device or app version / Appareil ou version de l’application | No | Whatever the visitor knows; never auto-collect or require diagnostics. |

Use a brief visible reminder that GitHub issues are public and require a GitHub account: do not include passphrases, personal information or sensitive screenshots. Preserve [CONTRIBUTING.md's security boundary](../../../CONTRIBUTING.md#reporting-security-issues): public feedback is not for vulnerability reports. No email/contact field, automatic attachment, app-data export, forced screenshot, consent checkbox or technical triage label is proposed. GitHub's ordinary title and explicit submit flow remain the visitor's responsibility.

Trade-off: one bilingual form is the smallest maintainable option but displays both languages together; separate EN/FR forms are a possible alternative at the cost of another destination and duplicated maintenance. Field wording, requiredness and language presentation remain for Alex's review. This design update adds no issue form, changes no repository issue settings and submits no feedback.
