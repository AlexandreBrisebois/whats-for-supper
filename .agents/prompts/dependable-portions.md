# Deliver the first dependable-portions increment

Act as delivery coordinator for this repository. Read AGENT.md and its loading
rules, then the accepted release baseline in
[canonical-ingredient-correction/proposal.md](../../openspec/changes/canonical-ingredient-correction/proposal.md),

OpenSpec apply workflow. This prompt selects the implementation increment below;

## Outcome and accepted decisions

Build on existing locally qualified URL/photo intake and manual correction. Finish
the missing ordinary ingredient-to-step relationship path so a recipe can be
imported, edited, scaled and cooked with consistent supported quantities and one
ingredient-derived grocery demand. Do not rebuild the existing exact arithmetic,
guarded editor, projection engine, grocery checks or qualified photo publication.

- Automatic relationship maintenance applies both to import and saved ingredient
  or step edits. Reuse deterministic revalidation; an AI task in the existing
  workflow system may propose relationships when needed.
- The server validates association, numeric role, source evidence and current
  revisions. AI confidence or a `validated` label is not proof. Task 0.1 defines
  the bounded evidence inlet; do not substitute assumptions for this engineering work.
- AI reevaluation changes relationships only, never saved ingredient descriptions,
  quantities, units or instruction wording. Preserve human edits and explicit clears.
- No special markup or manual linking screen. Uncertain relationships retain original
  readable wording. Reads, projection and grocery recomputation make no AI calls.
- Retain supported whole/absolute/fraction/remainder/fixed/per-item behavior. Start
  with one whole-use tracer; do not call that completion of all supported forms.
- Frontend, backend and database deploy together. Older tabs refresh and reconcile
  recoverable drafts. No permanent legacy-string write adapter for canonical records.
- Planned maintenance is accepted. Reuse existing demo/online-recovery coordination
  with migration's data/draft preservation policy. Do not perform a demo reset or
  invent a parallel maintenance system. Deployment/restart rehearsal is separate
  from existing lease/reset tests.
- Bilingual catalogue/merging and Similar UI are deferred. Preserve existing fallback
  behavior and any references already persisted. Selective ingredient repair is superseded.
- PDF, synthesis, shared-recipe intake and general protected reimport are later
  bounded increments. Preserve their existing behavior and publication fences now.

## Acceptance and delivery rhythm

Complete one working path before widening it:

URL/photo import → saved canonical facts → ingredient edit → validated relationship
maintenance → step edit → optional workflow reevaluation → one coherent projection
at changed portions → explicit active-Cook refresh → one grocery demand.

Use real API/workflow/PostgreSQL and generated-client/browser seams; double external
providers only. Include ambiguous/repeated/Unicode spans, unrelated numbers, explicit
clears, unchanged/unrelated edits, stale completion after another edit, duplicate
delivery, provider failure and retained cooking state. Reuse existing allocation,
prepared/count and grocery baseline tests. Add meaningful red tests before missing
logic; don't manufacture red for already-correct behavior or weaken an oracle.

Workers run focused feedback using Taskfile owners. The coordinator reviews code,
contracts, test selection and exact result files, then runs applicable preparation
and one combined verification boundary on stable integrated source. Required live/
database cases have zero required skips. Report source/build/configuration identity,
first-attempt results, retries, failures, blocked and never-run stages separately.
Local success is not hosted success; preserve any required hosted gate as outstanding
unless it actually runs on the exact candidate.

## Completion and stopping boundary

Update the existing owner task records with implementation state, scenario coverage,
next action and evidence identity. Close a checkbox only when all its criteria pass.
Do not archive, synchronize main specs or claim the whole feature is done from this
increment. Do not deploy, mutate production/DV, push, merge or commit without separate
session authorization. Keep the changes reviewable and preserve unrelated work.

Finish with: delivered user behavior, remaining blockers, exact passed/failed/
blocked/not-run checks, changed paths and the next bounded assignment. Do not ask
again about accepted product decisions or routine engineering choices. Ask one
question only if a newly discovered consequential ambiguity cannot be resolved
from the accepted specs; keep independent work moving while it is pending.
